# Приватность и хранение данных (retention)

> Last reviewed: 2026-08-21

Что приложение хранит, где, как долго и как удаляет — с упором на **финансовые ПДн** (банковские
выписки: счета, суммы, контрагенты, назначения). Слайс #245; смежное — приватный feedback-репо #284.

## Принцип: выписки у себя не храним

Источник правды по операциям/сделкам/инвойсам — **Bitrix24-портал клиента**. В нашей БД **нет
таблицы выписок/операций**: разобранные операции пишутся **делами в CRM портала** (`crm.activity.todo.add`),
дедуп — маркером в самом B24 (#259). Содержимое выписки проходит через нас **транзитно** (очереди),
не оседает в долгом хранилище.

## Что реально лежит в нашей Postgres

| Таблица | Что | ПДн? | Чистка |
|---|---|---|---|
| `portal_tokens` | OAuth-токены портала (refresh — AES-256-GCM) | нет выписок | удаление на `ONAPPUNINSTALL` |
| `portal_tombstone` | метка удаления портала (порядок событий #77) | нет | остаётся (анти-воскрешение) |
| `bank_tokens` | банк-OAuth токены счёта (refresh шифрован) | нет выписок | удаление на `ONAPPUNINSTALL` (ручное «Отключить» адресуется неизменяемым `id`, #517) **+** свип брошенных `~pending:`-подключений без выбранного счёта (#485, на тике `statementSweep`): доказанная смерть (истекло согласие банка либо вышел измеренный срок refresh) — сразу, иначе по возрасту `PENDING_MAX_AGE_DAYS` (дефолт 2 суток, кламп [1, 30]). ⚠ Строку с ВЫБРАННЫМ счётом свип не трогает никогда |
| `import_result` | сводка **последнего** прогона (счётчики) | агрегаты, не операции | удаление на `ONAPPUNINSTALL` |
| `import_batch` | итог **конкретной** ручной загрузки (#417): счётчики + **имя файла** + id загрузившего | агрегаты **плюс имя файла** — единственное неагрегатное поле | свип **каждые 6 часов** удаляет старше 3 дней (`IMPORT_BATCH_TTL_DAYS` — **константа в коде**, `server/plugins/queue.ts`, не env) **+** удаление на `ONAPPUNINSTALL` |
| `metrics_counter` | пожизненные счётчики портала | агрегаты | удаление на `ONAPPUNINSTALL` |
| `portal_app_rating` | когда порталу показывали попап «оцените приложение» (#204) | нет данных клиента — только `member_id` и метки времени | удаление на `ONAPPUNINSTALL` |
| `single_flight_lease` | какая долгая операция сейчас идёт для портала (#538): ключ вида `provision-sp:<member_id>`, случайный токен и срок | нет данных клиента — только `member_id` внутри ключа и метка времени | удаление на `ONAPPUNINSTALL`; свипа нет намеренно — просроченную строку живого портала перезаписывает следующий же захват, а у удалённого захвата не будет никогда, отсюда и явная чистка |

**Удаление приложения (`ONAPPUNINSTALL`) стирает ВСЁ** по порталу (`deletePortal`): токены, факты,
статус, метрики, банк-токены. Флаг «очистить данные» не смотрим — чистим всегда.

## Транзитные ПДн: payload'ы очередей в Redis

Само содержимое выписки живёт **недолго в Redis** как payload джоба:

- `file-parse` — загруженный **файл** выписки (base64, ≤ ~2.7 МБ);
- `crm-sync` — нормализованный `StatementItem[]` (контрагент / счёт / сумма / назначение).

Оба enqueue'ятся с **ограниченным по возрасту** удержанием (`STATEMENT_JOB_RETENTION`,
`server/queue/producers.ts`, #245): выполненные — **1 час** (кап 50), упавшие — **сутки** (кап 200, для
отладки). То есть финансовые ПДн **не копятся** под count-дефолтом (1000/5000 payload'ов), а вытесняются
по возрасту **или** капу — что раньше. ⚠ Удаление у BullMQ **ленивое** (не по таймеру): чистка состояния
срабатывает, когда в этой очереди **завершается следующий** джоб. Поэтому на **простаивающем** портале
«последние» ≤50 completed / ≤200 failed payload'ов могли бы полежать дольше 1 ч/суток — до следующего
завершения в очереди. **Эту ленивость закрывает периодический sweep** (`server/queue/statementSweep.ts`,
крон-инстанс, `runStatementSweep` каждые `STATEMENT_SWEEP_INTERVAL_MIN` мин, дефолт 30): он **явно** зовёт
`queue.clean(grace, …)` по тем же грейс-периодам, что и ленивый `age` (completed > 1 ч, failed > сутки),
для обеих statement-очередей — то есть удаление финансовых ПДн получает гарантию **по стенным часам**, а не
«до следующей джобы». **Верхняя граница удержания = грейс + `STATEMENT_SWEEP_INTERVAL_MIN`** (worst-case
completed ≈ 1 ч + 30 мин, failed ≈ сутки + 30 мин): sweep не укорачивает грейс, а лишь ограничивает сверху
хвост ленивого вытеснения. Большой интервал ослабляет гарантию (при `INTERVAL_MIN` ≫ грейса верхняя граница
растёт до `~интервал + грейс`), поэтому держим период коротким относительно грейса. Включён по умолчанию
(privacy-posture); отключается `STATEMENT_SWEEP=0`.

`bank-fetch` содержимого выписки не несёт (payload = «наш счёт + окно дат»; наш счёт, не контрагент) —
остаётся на count-дефолте. **`b24-events`** несёт в install-payload **OAuth access-токен портала в
открытом виде** (+ refresh шифрован): раз событие применено (токен сохранён), удерживать креды незачем,
поэтому completed-джоб удаляется **сразу** (`CREDENTIAL_JOB_RETENTION`, `removeOnComplete: true`), failed —
ограниченно (сутки/200) для отладки установок. Access-токен короткоживущий (~1 ч), refresh — шифрован.

Redis — на изолированной сети `queuenet` (`internal: true`), наружу не смотрит.

## Логи

Внешние поля (счёт/назначение/имя контрагента) при логировании прогоняются через `logSafe`
(control-char-стрип) — от инъекции строк лога. В диагностических логах операций
(`[fetch]`/`[op]`/`[recognize]`/`[resolve]`/`[allocate]`) фигурируют **счёт + docId + счёт
контрагента + валюта + направление + распознанные идентификаторы** (извлечённые из назначения
платежа — номера заказов/оплат/счетов); **суммы в логи не пишутся**. ⚠ `currency` у Альфы и
Приора — сырой проброс из JSON банка, поэтому он тоже проходит `logSafe` (в отличие от
`direction`, который нормализаторы вычисляют сами и который замкнут на два значения).
Хранение/ротацию логов контейнеров задаёт хостовый docker (`json-file`) — настроить ограничение
размера/срока на сервере (runbook — `OPERATIONS.md`).

⚠ **`[bank-keepalive]` — единственная строка, которая проходит по счетам ВСЕХ порталов сразу**
(раз в час, крон-инстанс, #489). Она печатает провайдера и **номер подключённого счёта** — наш
собственный, не контрагента, — когда обновление не удалось или подключение требует человека.
Санитизация строже общей (`logSafeKey`: allowlist символов + обрезка), список имён капнут
(`MAX_NAMED_IN_LOG`), чтобы одна строка не выросла в стену. Токенов и сумм в ней нет.
Портальный близнец `[keepalive]` (#175) счетов не касается вовсе — только `member_id`, и печатает
он его **в открытом виде** (`logSafeMember` — это САНИТИЗАЦИЯ: стрип не-словарных символов и обрезка
до 64, а не хеш). Раньше здесь стояло «хеш-безопасный `member_id`» — неверно; правило ниже заведено
в том числе потому, что незаписанное правило именно так и расходится с кодом.

⚠ **`[bank-keepalive] … ensureBankToken: … account was disconnected mid-refresh` (#505)** несёт **только провайдера**
(`alfa-by`/`prior-by`) — ни номера счёта, ни `member_id`, ни токенов. Печатается, когда обновление
вернулось из банка, а подключение за это время отключили: токен намеренно не записан. Отдельно от
`[bank-keepalive]` потому, что появляется на любом пути, который зовёт `ensureBankToken` (опрос,
экран сверки счетов), а не только в часовом кроне.

### `member_id` в логах — печатаем открыто, и это решение (#525)

⚠ **Первая редакция этого раздела была неточной, и ошибка была в сторону «у нас всё стройно».**
Ревью проверило каждое утверждение и опровергло два. Оставляю разбор целиком, потому что аккуратная,
но ложная картина опаснее честной с дырами — по ней принимают решения.

| канал | что РЕАЛЬНО делает с `member_id` | экспозиция |
|---|---|---|
| OpenTelemetry-спаны | **хеширует** (`portal.hash`) | уезжает во внешний коллектор |
| экран `/queues` | **хеширует** (`portalHash`) | pull, за сессией оператора |
| Telegram-алерты | **не несёт вовсе** — только числа и название банка | push наружу, отозвать нельзя |
| логи воркера, `[fetch]`/`[op]`/`[recognize]`/`[resolve]`/`[allocate]`/`[crm-sync]`, а также `[trigger]` (`applyTriggerDep.ts`) и роут событий Б24 | **печатают открыто** | локальный `json-file` |
| логи воркера, ветка `[deletion]` | **хеширует** | тот же локальный канал |

⚠ Точного ЧИСЛА строк здесь намеренно нет. В первой редакции стояло «19», ревьюеры насчитали
18 и 20 разными способами подсчёта, а тестом такую цифру не закрепить — то есть она разъехалась бы
с кодом молча, ровно как то утверждение, которое этот раздел и исправляет. Перечислены маркеры.

⚠ Прежняя таблица утверждала, что Telegram «хеширует» — **неверно**. Он идентификатор портала не
несёт **вообще**, и это осознанно (`bankHealthAlert.ts`). Вывод отсюда обратный тому, что я
написал сначала: где канал точно внешний, проект предпочёл **не нести** значение, а не хешировать.
⚠ И «одно правило на канал» тоже неверно: внутри логов уже ДВА режима — `[deletion]` хеширует.

**Решение остаётся: печатаем открыто.** Довод не в стройности (её нет), а в цене: весь разбор в
`OPERATIONS.md` построен на том, что в строке видно, ЧЕЙ это портал, а `member_id` и так лежит
открытым первичным ключом в `portal_tokens`, `bank_tokens`, `import_result`, `metrics_counter`.

#### Остаточные риски — принятые, а не отсутствующие

Ревью нашло три пути, которых в первой редакции не было. Ни один не отменяет решение, но каждый
сужает его, и молчать о них нельзя:

1. ⚠ **Оператор копирует вывод в чат.** `make poll-check` показывает строки `[fetch]`/`[op]` на
   экране, и человек с мобильного терминала, увидев красное предупреждение, естественно
   пересылает это за помощью. Это не гипотетический сборщик логов, а штатный рабочий процесс —
   и его не закрывает ни тест, ни драйвер.
2. ⚠ **`[op]` создаёт пару, которой больше нигде нет.** Он печатает `member_id` **вместе со счётом
   КОНТРАГЕНТА**, а тот в системе не хранится вовсе: те же данные в очереди живут **час**
   (`STATEMENT_JOB_RETENTION`). Ротация логов — по РАЗМЕРУ (10 МБ × 5), не по времени, поэтому на
   тихом портале эта пара переживёт своего redis-близнеца на недели. Довод «хеш не скрыл бы
   ничего, что не лежит рядом» здесь **не работает**: рядом не лежит. Для `[fetch]` (наш
   собственный счёт, постоянно в `bank_tokens`) — работает.
3. ⚠ **Есть и четвёртый канал наружу.** `programFeedback.ts` кладёт `member_id` в тело issue
   приватного репо обратной связи — открытым, и это отдельно осознано в `docs/FEEDBACK.md` как
   non-PII. Здесь названо, чтобы «в трёх каналах» не читалось как исчерпывающий список.
4. ⚠ **`member_id` не полностью безразличен к атаке.** В #162 таргетированная подделка установки
   требует ЗНАТЬ `member_id` жертвы, а защита (`verifyInstallMember`) отключается отсутствием
   `B24_CLIENT_ID/SECRET` — это warning, не отказ старта.

Открытый вопрос — хешировать ли `member_id` именно в `[op]` (пара + путь в чат) — вынесен
отдельно, а не решён здесь на бегу: правка горячего пути логирования заслуживает своего разбора.

⚠ Решение привязано к свойству КАНАЛА. Подключение внешнего сборщика логов переводит логи в класс
«уезжает наружу», и тогда пересматривать надо вместе с ним.

⚠ Закреплено **тестом** (`tests/logChannelLocality.test.ts`): он падает, когда в `docker-compose*.yml`
появляется не-локальный драйвер или сервис-сборщик. Правило, которое надо помнить, — это дефект,
ждущий единственного раза, когда его забудут. ⚠ **Границы сторожа честные и заметно уже, чем
кажется**: агент через `daemon.json`/systemd он не видит, и — что важнее — **не видит
compose-сайдкар с незнакомым именем** (`registry.internal/acme-log-agent`, монтирующий
`/var/lib/docker/containers`), хотя это ровно тот путь, которым сборщик и добавляют. Он ловит
частый случай, а не все.

Счёт **контрагента** в `[op]` — не расширение объёма ради удобства, а единственный способ сделать
`unmatched` действием: это ровно то значение, которое `findCompany` ищет в реквизитах портала, и без
него сводка «117 обработано, 117 не опознано» не говорит, что чинить. Он того же класса, что наш
собственный счёт, который логируется с самого начала.

⚠ **Строка `[op]` печатается НЕ на каждую операцию (#498).** По умолчанию (`STATEMENT_OP_LOG=notable`)
она пишется только для операций, которые **ни во что не приземлились** — то есть номера счетов
приземлившихся платежей в лог не попадают вовсе. Заведено это ради объёма (221 байт × каждая
операция сжимали историю до четырёх часов), но по ретенции ПДн эффект тот же и в ту же сторону:
на здоровом портале в логе оседает **меньше** номеров счетов, чем раньше. ⚠ Обратное тоже верно и
важнее: на ненастроенном портале не приземляется ничто, значит объём равен прежнему — послаблением
ретенции этот режим считать нельзя. Итог прогона `[crm-sync]` номеров счетов не содержит вообще,
только счётчики. Режим `all` возвращает прежнее поведение (калибровка), `off` не пишет построчно
ничего.

**Назначение платежа — исключение, и оно за флагом.** Это самый широкий неконтролируемый текст,
который мы держим, поэтому по умолчанию его в логе нет. Раскрывает его `STATEMENT_DEBUG_LOG=1`
(воркер) — **осознанное временное послабление** на время калибровки «карты сопоставления»: маску
нельзя написать для нумерации, которую ни разу не видел. Порядок тот же, что с уровнем error-лога
крипто-шлюза (§выше): включили на прогон, выключили обратно. Флаг читается один раз при старте —
менять его значит перезапускать контейнер, и это намеренно: не рантайм-ручка.

**Крипто-шлюз (#460)** — отдельный источник того же класса данных: у Приорбанка номер счёта едет
**в пути URL** (`/open-banking/v1.0/accounts/<IBAN>/statements`), а шлюз этот путь проксирует.
⚠ Шлюз живёт в [отдельном репозитории](https://github.com/bx-shef/bee2-tls-gateway) — гарантия ниже держится ТАМ (конфигурация nginx и
проверки в его CI), а не в этом репозитории: здесь её больше нечем проверить. Обновляя образ,
сверяйтесь с его README. Его access-лог написан БЕЗ пути (`route=/method=/status=/bytes=/rt=`), а формат error-лога
nginx менять не умеет и на уровне `error` печатает строку запроса целиком — отсюда уровень `crit`
по умолчанию (`GW_ERROR_LOG_LEVEL`). Диагностика отказов при этом не теряется: они видны в
access-логе как `status=502`. На живой прогон уровень поднимают до `info` и возвращают обратно —
это осознанное временное послабление, а не рабочий режим.

## Телеметрия (OpenTelemetry, #78)

Спаны OpenTelemetry (см. [`OBSERVABILITY.md`](OBSERVABILITY.md); DEFAULT OFF) **не несут финансовых
ПДн** — тройная защита: (1) наши ручные спаны эмитят **только allowlist** безопасных ключей
(`server/utils/telemetryAttributes.ts` `pickSafeAttributes` — счёт/сумму/назначение/контрагента
прикрепить нельзя, значение-объект отбрасывается); (2) **redaction-SpanProcessor** в бутстрапе
срезает чувствительные атрибуты авто-инструментирования (`db.statement`/`url.*`/`*body*`/`*token*`/…)
до экспорта, а `pg` идёт с `enhancedDatabaseReporting:false` (значения SQL-параметров не собираются);
(3) member_id → необратимый `portal.hash` (SHA-256), `error_kind` — токен из `code`/`name`, **не** текст
ошибки (`recordException` не вызывается). ⚠ Инвариант: SQL остаётся **параметризованным** — имя pg-спана
это неотредактированный канал, и литерал в непараметризованном запросе попал бы в имя спана.

## Открытые пункты (follow-up)

- **TTL «спящих» агрегатов** (#245): `import_result`/`metrics_counter` живут до
  uninstall — для установленного, но давно неактивного портала можно ввести необязательный TTL/архивацию
  (сейчас не критично: без выписок, только id-ссылки/счётчики). `allocation_fact` полностью снят (§9.3 #6 —
  идемпотентность/аудит разнесения живут на dist-СП в портале, у нас таблицы нет).
- **Приватный feedback-репо** (#284): файл выписки, приложенный к отзыву для воспроизведения, —
  срок хранения/подчистка в приватном репо-приёмнике (по умолчанию PII в публичный issue **не** кладём —
  см. `FEEDBACK.md`).
- **Маскировка идентификаторов в логах**: суммы в логи не идут, но счёт + распознанные номера
  (заказ/оплата/счёт из назначения) — да; рассмотреть маскирование при разборе инцидентов на чужой стороне.
- **Отладка упавших импортов**: payload упавшего statement-джоба ограничен **и** возрастом (сутки),
  **и** капом (200) — что раньше; на объёмном портале старый упавший payload может уже уйти. Криминалистика
  по последнему прогону живёт в Postgres (`import_result.errors` + метрики), не в Redis — там и смотреть.
- ✅ **Гарантия по стенным часам** — сделано: периодический `queue.clean` для statement-очередей на
  крон-инстансе (`server/queue/statementSweep.ts`, `STATEMENT_SWEEP`/`STATEMENT_SWEEP_INTERVAL_MIN`).

## Исходящие каналы

| Канал | Куда | Что уходит |
|---|---|---|
| Оповещения оператору (#426) | `api.telegram.org` | **Только** имена очередей, счётчики и возраст задач. Финансовых данных нет **по построению**: правила видят лишь метаданные BullMQ (`QueueHealthInput` не несёт ни сумм, ни счетов, ни назначений), а текст собирается из имени очереди и чисел. Зафиксировано сквозным тестом в `tests/queueAlertDeliver.test.ts` |
| Обратная связь (#61/#198) | GitHub, **приватный** репо-приёмник | Комментарий сотрудника; по **явному согласию** — файл выписки (финансовые ПДн). Репо никогда не дефолтится на публичный |
