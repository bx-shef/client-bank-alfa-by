# Деплой на виртуальную машину Битрикс24 (третий таргет)

> Last reviewed: 2026-08-25

Развёртывание приложения **рядом с боевым порталом** на виртуальной машине Битрикс24
(bitrix-env): домен третьего уровня, nginx машины терминирует TLS и проксирует всё в
docker-стек на loopback, обновления сервер забирает сам опросом git.

> Два других таргета: [`DEPLOY.md`](DEPLOY.md) — основной (GHCR + Watchtower за общим
> nginx-proxy), [`DEPLOY_VIBECODE.md`](DEPLOY_VIBECODE.md) — Битрикс24 Вайбкод.
> Эксплуатация после запуска общая для всех — [`OPERATIONS.md`](OPERATIONS.md).

Артефакты таргета — в [`deploy/bitrixvm/`](../deploy/bitrixvm/).

## Когда этот таргет уместен

У клиента уже есть виртуальная машина с коробочным Битрикс24, там же живёт nginx с
рабочим механизмом выпуска сертификатов, и заводить отдельный сервер незачем. Взамен
приходится ужиться с чужим nginx и не сломать портал — этому посвящена половина
документа.

## Схема работы с клиентами

Приложение разворачивается из **клона** апстрима в отдельный клиентский репозиторий:
там живут правки под этого клиента, его CI собирает образы в его GHCR. Обновления
апстрима приходят merge'ем — то есть решение «принять новую версию» принимает человек,
а сервер лишь исполняет уже принятое.

Доступ к апстриму выдаётся **deploy key**: ключ привязан к одному репозиторию, отзывается
одним действием, и GitHub показывает дату последнего использования — это и есть аудит.
Образы тянутся отдельным токеном с правом `read:packages`, то есть доступ к исходникам и
доступ к сборкам разведены.

При прекращении отношений отзыв ключа **не трогает** ни развёрнутое приложение, ни код у
клиента: прекращается только поток обновлений.

⚠ У клона нет автоудаления, которое GitHub применяет к приватным **форкам** при отзыве
доступа. Если такой рычаг нужен, это осознанный выбор в пользу форка — и тогда апстрим
обязан быть приватным **до** создания форка: форк публичного репозитория остаётся
публичным навсегда и отцепляется в самостоятельный репозиторий, то есть ни рычага, ни
штатной синхронизации не будет.

## Что понадобится заранее

- домен третьего уровня и A-запись на этот сервер;
- дополнительный сайт, созданный **штатным меню** bitrix-env (даёт
  `/home/bitrix/ext_www/<домен>`, пару конфигов nginx и каталог для наших настроек);
- сертификат, выпущенный тем же меню (его же оно и продлевает);
- docker и compose-плагин;
- клиентский репозиторий с настроенным CI.

## Порядок

### 1. Сайт и сертификат — только через меню

Меню создаёт `bx_ext_<домен>.conf` и `bx_ext_ssl_<домен>.conf`, каталог
`/etc/nginx/bx/site_settings/<домен>/` и docroot. Дальше мы правим **только** каталог
`site_settings`; сгенерированные конфиги не трогаем вовсе.

### 2. Проксирование

```bash
install -m 644 -o root -g root deploy/bitrixvm/nginx/00-app-proxy.conf \
  /etc/nginx/bx/site_settings/<домен>/00-app-proxy.conf
nginx -t && systemctl reload nginx
```

Механика и её обоснование — в шапке самого файла. Коротко о трёх решениях, которые легко
принять неправильно:

⚠ **Свой `server`-блок не заводим.** Два блока с одним `server_name` дают
`conflicting server name`, и nginx берёт первый по порядку инклюда — а это блок BitrixVM.
Домен молча отдавал бы Apache, и выглядело бы это как «приложение не поднялось».

⚠ **Своего `location /` тоже нет** — дубликат `location` в одном блоке nginx не примет.
Он и не нужен: `bx/conf/bitrix.conf` проксирует в **переменную** `$proxyserver`, которую
мы переопределяем. Вместе с `location /` нам достаются `~ \.php$`, `~ /$` и `@fallback`.

⚠ **Статику приходится перехватывать руками.** В `bx/conf/bitrix_general.conf` есть
`location ~* \.(css|js|…)$` **без** `proxy_pass`: он отдаёт файл из docroot, а docroot у
нас — заглушка, и `error_page 404` там переопределён на страницу BitrixEnv. Без перехвата
весь `/_nuxt/*` вернул бы страницу ошибки: HTML пришёл, скрипты нет — снаружи это читается
как «открылось, но не работает».

### 3. Docroot

```bash
D=/home/bitrix/ext_www/<домен>
cp -a "$D/index.php" "$D/index.php.orig-$(date +%F)"
cp deploy/bitrixvm/docroot/index.php deploy/bitrixvm/docroot/.htaccess "$D/"
chown bitrix:bitrix "$D/index.php" "$D/.htaccess"
```

Каталоги `bitrix/`, `upload/`, `local/` не трогаем. `index.php` меню кладёт боевой,
битриксовый — заменяем заглушкой, отвечающей `503` (попадание туда означает сломанное
проксирование, и `200` соврал бы мониторингу). Из `.htaccess` убраны редирект на чужой
сайт и CORS чужого портала — оба приезжают в новый docroot копипастой и уводили бы
посетителей служебного домена на портал.

HTTP→HTTPS включается штатным для bitrix-env способом — файлом `.htsecure` в docroot:

```bash
touch "$D/.htsecure" && chown bitrix:bitrix "$D/.htsecure"
```

### 4. Стек

```bash
mkdir -p /home/bitrix/bank-import   # сюда: оба compose-файла и .env
cp docker-compose.prod.yml deploy/bitrixvm/docker-compose.bitrixvm.yml /home/bitrix/bank-import/
cp deploy/bitrixvm/.env.example /home/bitrix/bank-import/.env   # заполнить, chmod 600
cd /home/bitrix/bank-import && docker compose up -d
```

⚠ Сеть `proxy-net` базовый файл объявляет `external` — её надо создать пустой
(`docker network create proxy-net`). Убрать её оверлеем нельзя: списки сетей при слиянии
compose объединяются, а не замещаются. Без nginx-proxy она инертна, как и переменные
`VIRTUAL_HOST`/`LETSENCRYPT_*` и метки Watchtower.

⚠ `COMPOSE_FILE` с обоими файлами задан прямо в `.env`. Забытый оверлей — это молчаливый
откат к схеме с nginx-proxy: контейнер не опубликуется на loopback, и домен начнёт
отдавать 502 без единой ошибки в логе.

⚠ Порт публикуется **строго на 127.0.0.1**. Без явного адреса docker слушает `0.0.0.0` и
вписывает правило **в обход firewalld**: приложение оказывается доступно по IP сервера
мимо TLS и мимо ограничений nginx, при этом `firewall-cmd --list-all` выглядит прежним.

### 5. Переменные, специфичные для коробочного портала

Их две, и это **разные слои**, одно другого не заменяет:

| где | что | кто применяет |
|---|---|---|
| переменная клиентского репозитория `B24_PORTAL_ORIGINS` | домены портала в CSP (`frame-ancestors`, `connect-src`) | браузер |
| `.env` на сервере `B24_SELFHOSTED_HOSTS` | тот же список для SSRF-гейта | наш backend |

Забыть первую — приложение открывается снаружи, но внутри портала показывает пустой фрейм.
Забыть вторую — серверные вызовы в портал отвергаются нами же, ещё до сети.

`NUXT_PUBLIC_SITE_URL` задаётся переменной клиентского репозитория и **запекается в образ
при сборке**: из него `/install` строит абсолютный адрес обработчика событий Б24. Образы,
собранные под другой домен, дают нерабочую установку.

### 6. Автообновление

```bash
install -m 755 deploy/bitrixvm/git-poll-deploy.sh /usr/local/sbin/bank-app-deploy
mkdir -p /etc/bank-app-deploy && chmod 700 /etc/bank-app-deploy
cp deploy/bitrixvm/deploy.env.client.example /etc/bank-app-deploy/deploy.env  # заполнить
chmod 600 /etc/bank-app-deploy/deploy.env
cp deploy/bitrixvm/systemd/bank-app-deploy.* /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now bank-app-deploy.timer
```

Ключ и токен кладём файлами с правами `600`, а не в юнит: содержимое юнита видно любому
пользователю через `systemctl cat` и попадает в бэкап конфигурации.

Два варианта источника опроса — `deploy.env.client.example` (клиентский репозиторий,
штатный) и `deploy.env.upstream.example` (апстрим напрямую; годится для стенда, в бою нет —
домен запечён в образы апстрима под его домен).

⚠ Разворачивается образ **по тегу коммита** (`sha-<короткий>`), а не `:latest`: движущийся
тег между двумя `pull` может сдвинуться, и получится половина одной версии и половина
другой. Отсюда же проверяемость: «развёрнут коммит X» — утверждение, которое можно
проверить, а откат сводится к «развернуть предыдущий X».

⚠ Проверяются **два** адреса: `/api/health` остаётся зелёным при мёртвых Postgres и Redis,
то есть по нему одному успешным признавалось бы ровно то, что новая версия и ломает —
несовместимая миграция и отвалившаяся очередь. Не прошло — откат на прежние образы **по их
идентификаторам**, а не по тегу: тег к этому моменту уже переписан.

⚠ Состояние после отката **не** обновляется: следующий тик попробует тот же коммит снова.
Сломанную версию чинит новый коммит, и сервер подхватит его сам.

### 7. Оффлайн-копия

```bash
make offline-snapshot     # в cron раз в неделю
```

Зачем: источник образов может исчезнуть (доступ отозван, репозиторий удалён, реестр
недоступен). Уже запущенные контейнеры это переживают — docker не удаляет образ, на
котором работает контейнер, поэтому и `docker image prune -f` (он сносит только висячие,
не занятые) им не грозит. Копия закрывает другие случаи: пересоздание контейнера на
хосте, где образ уже вычищен, откат на предыдущую версию после того, как её тег
переписан, восстановление после потери диска.

Скрипт обновления образы не удаляет вовсе — ни висячие, ни какие-либо ещё; в основном
таргете `make prod-redeploy` шаг прунинга есть, здесь его нет намеренно.

## Операторские цели

Все — из `/home/bitrix/bank-import`, после `make self-update`:

| цель | что делает |
|---|---|
| `make bitrix-check` | доедет ли запрос с домена до приложения: конфиг, контейнер, **статика**, таймер. Работает и до появления домена — ходит по `Host` на 127.0.0.1 |
| `make deploy-status` | включён ли таймер, какой коммит развёрнут, последний прогон |
| `make deploy-now` | проверить обновления сейчас, не дожидаясь тика |
| `make deploy-pause` / `deploy-resume` | приостановить и вернуть автообновление (пауза переживает перезагрузку — «само включилось ночью» было бы худшим поведением) |
| `make offline-snapshot` | копия образов работающих контейнеров |

## После каждой операции в меню bitrix-env

Меню перегенерирует `bx_ext_*<домен>*.conf`. Наш файл лежит в `site_settings`, который
генератор помечает как переживающий обновления, — но проверять всё равно нужно, потому
что цена ошибки здесь «домен отдаёт портал вместо приложения»:

```bash
grep -r 'proxyserver' /etc/nginx/bx/site_settings/<домен>/ && nginx -t \
  && curl -sS -o /dev/null -w '%{http_code}\n' https://<домен>/api/health
```

## Диагностика

| симптом | что смотреть |
|---|---|
| страница открывается, но пустая; в консоли ошибки CSP | `B24_PORTAL_ORIGINS` при сборке образа |
| HTML отдаётся, скрипты `/_nuxt/*` — страница ошибки | не установлен или потерян `00-app-proxy.conf` |
| домен отдаёт портал/Apache | сгенерированный блок победил наш — проверить, не появился ли свой `server`-блок |
| 502 на домене | контейнер не слушает `127.0.0.1:8080` — забыт оверлей (`COMPOSE_FILE`) |
| 504 на подключении банка | таймаут внешнего nginx меньше 65 с |
| `/api/ready` = 503 | Postgres или Redis; `docker compose ps`, логи backend |
| обновления не приходят | `systemctl status bank-app-deploy.timer`, `journalctl -u bank-app-deploy` |
