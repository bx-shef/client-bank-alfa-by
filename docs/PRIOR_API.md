# Приорбанк — как работать с выпиской

> Last reviewed: 2026-08-13

С Приорбанком есть **два пути**, и оба реализованы: импорт текстовой выписки (раздел 1) и
живой Open Banking API по СПР (раздел 2 — движок опроса, connect-поток и включение в крон
готовы, A5b). Sandbox `:9344` работает обычным TLS. Для **прода** второму пути нужны **две
разные вещи**, и путать их нельзя:

1. **Инфраструктура** — BY-крипто TLS до `apibel.priorbank.by:9345` (СТБ 34.101.65),
   [#41](https://github.com/bx-shef/client-bank-alfa-by/issues/41). ✅ **Кодовая часть закрыта**:
   собран крипто-шлюз на открытой реализации bee2evp
   ([#460](https://github.com/bx-shef/client-bank-alfa-by/issues/460)), живой прогон против боевого
   банка прошёл; шлюз живёт в [bx-shef/bee2-tls-gateway](https://github.com/bx-shef/bee2-tls-gateway). Покупать СКЗИ у вендора не требуется. ⚠
   Остаётся **владельческий** вопрос: признаёт ли банк несертифицированную реализацию — это к банку,
   не к коду.
2. **Код** — прод-метод аутентификации `private_key_jwt`
   ([#444](https://github.com/bx-shef/client-bank-alfa-by/issues/444)), потому что
   `client_secret_basic` банк принимает **только в тестовой среде**. ✅ **Реализовано**
   (переключается `PRIOR_OAUTH_AUTH_METHOD`).

⛔ **Сегодня поток упирается НЕ в это.** Песочница отвергает создание согласия
(`403 BY.NBRB.Reauthenticate`) на запросе, дословно совпадающем с Postman-коллекцией банка —
подробности и таблица исключённых гипотез ниже, в разделе «Открытый блокер». Пока он не снят,
сквозной прогон Приора невозможен ни с каким методом аутентификации.


## Движок опроса: две вещи, на которых легко ошибиться

- **`accountId` Приора — НЕ наш IBAN.** Перед созданием запроса выписки нужно резолвить опаковый
  идентификатор счёта из нашего номера (`resolvePriorAccountId` → `GET /accounts`). Это разные
  идентификаторы, и подстановка IBAN напрямую даёт отказ, который легко принять за «нет данных».
- **429/5xx на поллинге ресурса — это «ещё не готово», а НЕ пустая выписка.** Трактовать их как
  пустой ответ нельзя: троттл тихо съел бы окно операций, и импорт «прошёл бы успешно» без единой
  строки. Нераспознанное тело ответа — тоже ошибка, а не «пусто».

## 1. Импорт текстовой выписки client-bank (работает сейчас)

Приорбанк (и ручная выгрузка) отдаёт выписку в **текстовом формате client-bank**
(`***** ^Type=…`, родственник `1CClientBankExchange`), кодировка **windows-1251 (CP1251)**.
Это *формат*, а не банковский клиент, поэтому он обслуживает оба провайдера —
`prior-by` и `manual` (см. `app/config/banks.ts`).

- **Парсер (формат):** `app/utils/clientBankText.ts` → `parseClientBankText(text)` возвращает
  секции `GENERAL` / `IN_PARAM` / `OUT_PARAM` (`header` / `items` / `footer` / `unrouted`).
  Вход — уже декодированная строка (CP1251 → utf-8 декодируем заранее). `DocID`/`Cod` (BIC)
  теперь пишутся по строкам. Остаточный рефактор (словари ключей, лимит размера) — **issue #19**.
- **Нормализация:** `app/utils/clientBankStatement.ts` → `normalizeClientBank(parsed, ctx)` →
  `StatementItem[]` (контракт `StatementNormalizer`): приход/расход (плюсовой дебет → расход),
  валюта (нац/инвалюта: маркеры `I3`/`I1`/`I2`, иначе `BY…`-счёт → `BYN`), контрагент (имя/УНП/счёт/BIC),
  `Nazn`+`Nazn2` → назначение, `account|docId`-дедуп. Для инвалюты сумма берётся в валюте счёта
  (поле `…Q`) — правило подтверждено на образце CNY, проверить на реальных инвалютных выписках (#19).
- **Образцы:** `tests/fixtures/client-bank/demo-prior-byn.txt` (рубли),
  `demo-prior-cny.txt` (валюта) — обезличенные, CP1251 (`.gitattributes` → `binary`).
- **Тесты:** `tests/clientBankText.test.ts` (парсер) + `tests/clientBankStatement.test.ts` (нормализация)
  против образцов.

### Скрипт просмотра: `pnpm parse:statement`

`scripts/parse-statement.ts` — читает CP1251-файл, декодирует, прогоняет через
**канонический** `parseClientBankText` (логика не дублируется) и печатает разбор:
`GENERAL` (тип, счёт — маскирован, заголовок), по секциям `IN_PARAM`/`OUT_PARAM` —
число операций, период, остатки, первые операции и счётчик `unrouted`-ключей.

```bash
pnpm parse:statement tests/fixtures/client-bank/demo-prior-byn.txt
pnpm parse:statement path/to/your-export.txt another.txt   # можно несколько
```

Запускается нативным TS-стриппингом Node (`--experimental-strip-types`, **нужен Node ≥ 22**,
что совпадает с `engines` и CI) — без сборки и без новых зависимостей. Кросс-платформенно
(Linux/Windows). Декод CP1251 требует **full-ICU** Node (по умолчанию в официальных сборках).

> ⚠️ Вывод содержит **данные контрагентов и назначения платежей (PII)**, номер счёта —
> маскируется. Не запускай на боевых выписках в логируемых/расшаренных средах. Образцы в
> `tests/fixtures/` обезличены.

(PDF, 21 стр.; СПР 6.01-2020 / 6.02-2022, стек **WSO2 API Manager**). Портал:

### Три API

| API | Назначение |
|---|---|
| **Open-banking-authorize** | Аутентификация/авторизация, токены (`/oauth2/token`, `/oauth2/authorize`, `/oauth2/revoke`) |
| **Open-banking-DCR** | Динамическая регистрация бизнес-приложения (`/register`, `/oidcdiscovery`) |
| **Open-banking** | Согласия и счета (`/accountConsents`, `/accounts/...`) |

### Хосты и среды

- **Sandbox:** `https://api.priorbank.by:9344` — **обычный TLS** (OpenSSL). СКЗИ не нужен.
  Тестовый конечный пользователь для авторизации согласия: ЮЛ `testspr_le` / `445_e58$a7e8`,
  ФЛ `testspr_pi` / `jghh6ZQX`.
- **Прод:** `https://apibel.priorbank.by:9345` — **TLS на белорусских криптоалгоритмах**
  (СТБ 34.101.65), требуется **СКЗИ** (см. ниже) и **Договор об использовании Платёжного API**
  с банком (стр. 5 инструкции). ✅ **Договор с банком заключён** (подтверждено владельцем,
  2026-08) — этот шаг закрыт, остаются СКЗИ
  ([#41](https://github.com/bx-shef/client-bank-alfa-by/issues/41)). Прод-метод аутентификации
  ([#444](https://github.com/bx-shef/client-bank-alfa-by/issues/444)) — **реализован**, см.
  «Способы аутентификации» ниже.
  ⚠ **Отдельного тестового хоста у прода нет** — эндпоинт тот же. В личном кабинете Магазина API
  создаются отдельные «тестовые» и «промышленные» ключи приложения (стр. 7, §1.3), но тип ключей
  **не влияет на транспорт**: любое обращение к `:9345` всё равно требует BY-крипто TLS, то есть
  без СКЗИ туда не достучаться никакими ключами.

### Поток подключения (4 шага)

1. **Тех-приложение (DCR).** В Магазине API создать технологическое приложение → подписать
   на **Open-banking-DCR** → создать ключи (`client_id`/`client_secret`).
   - Токен A: `POST /open-banking-authorize/v1.0/oauth2/token`,
     `grant_type=client_credentials`, `scope=apim:subscribe apim:app_manage`
     (креды тех-приложения — Basic-auth).
2. **Бизнес-приложение (DCR register).** `POST /open-banking-dcr/v1.0/register` с токеном A →
   создаётся бизнес-приложение (его `client_id`/`client_secret`). В теле:
   - `redirect_uri` — куда банк вернёт `code`;
   - `grant_types`: `client_credentials` (для согласия) + `authorization_code` (для счетов)
     + `refresh_token` (если нужен рефреш);
   - `token_endpoint_auth_method` (см. «Способы аутентификации»);
   - `jwks` (публичные ключи в формате JWK Set) — если метод `private_key_jwt` /
     `self_signed_tls_client_auth` или `grant_types` содержит `authorization_code`.
   - Конфиг сервера авторизации (в т.ч. `aud` для JWT) — `GET /open-banking-dcr/v1.0/oidcdiscovery`.
   - Затем подписать бизнес-приложение на **Open-banking API**.
3. **Согласие (consent).** Токен Б: `POST /oauth2/token`, `grant_type=client_credentials`,
   `scope=accounts` → `POST /open-banking/v1.0/accountConsents` с `permissions` (нужное нам:
   `ReadStatementsBasic`/`ReadStatementsDetail`, `ReadTransactionsBasic`/`Detail`/`Credits`/`Debits`,
   `ReadAccountsBasic`/`Detail`; ⚠ `ReadBalances` НЕ запрашиваем — остаток нигде не читается), `expirationDate`, `transactionFromDate/ToDate`
   → получаем `openbanking_intent_id`. Затем **авторизация согласия пользователем**:
   `GET|POST /oauth2/authorize`, `response_type=code`, `scope=openid accounts`, параметр
   `request` = **подписанный JWT** (с `openbanking_intent_id`) → пользователь вводит логин/пароль
   от интернет-банка **на странице Приорбанка** → `code` на `redirect_uri`.
4. **Выписка.** Обмен `code` → токен B: `POST /oauth2/token`, `grant_type=authorization_code`.
   Затем **асинхронно**: `POST /accounts/{accountId}/statements` (или `.../transactions`) → потом
   опрашивать `GET /accounts/{accountId}/statements/{statementId}` (пока не готово — ошибка
   `BY.NBRB.Resource.NotCreated`). Рефреш: `grant_type=refresh_token`; отзыв: `POST /oauth2/revoke`.

### Способы аутентификации приложения (`token_endpoint_auth_method`)

Перечень и границы применимости — стр. 9 §2.2 инструкции, детали каждого метода — §4.1.1–4.1.4.

- `client_secret_basic` / `client_secret_post` — **только тестовая среда** (client_id/secret в
  Basic-хедере или в теле). Формулировка инструкции категоричная: «используется только для тестовой
  среды», §4.1.1 вынесено в заголовок.
- `private_key_jwt` — тестовая **и промышленная**. Подпись JWT (`client_assertion` +
  `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`); публичный ключ
  регистрируется в `jwks`.
- `tls_client_auth` — тестовая и промышленная, mTLS с сертификатом X.509 от доверенного УЦ
  (в РБ — **ГосСУОК**). Дополнительно при регистрации нужен один из параметров
  `tls_client_auth_subject_dn` / `_san_dns` / `_san_uri` / `_san_ip` / `_san_email` (§4.1.3).
- `self_signed_tls_client_auth` — тестовая и промышленная, mTLS с **самоподписанным** сертификатом,
  опубликованным в `jwks` (§4.1.4). ГосСУОК не нужен, но взаимный TLS остаётся.

> **Что берём:** sandbox — `client_secret_basic` (проще всего). Прод — **`private_key_jwt`**: из трёх
> допустимых в проде методов он единственный без взаимного TLS и без клиентского сертификата, то есть
> и без ГосСУОК. Это **не предпочтение, а требование** — `client_secret_basic` в проде не примут.
>
> ✅ **`private_key_jwt` реализован** ([#444](https://github.com/bx-shef/client-bank-alfa-by/issues/444)).
> Метод выбирается переменной **`PRIOR_OAUTH_AUTH_METHOD`** (`client_secret_basic` по умолчанию —
> sandbox; `private_key_jwt` — прод). Неизвестное значение ⇒ откат к sandbox-методу: fail-safe,
> чтобы не вооружить прод-метод, под который приложение может быть не зарегистрировано.
>
> ⚠ **DCR регистрирует ОДИН метод на приложение**, поэтому переключать надо согласованно: env
> сервера **и** регистрацию приложения (`pnpm prior:test --auth-method private_key_jwt --dcr`).
> Рассогласование = 401 на том месте, которое забыли.
>
> Все места аутентификации идут через **единую точку** — чистый `priorTokenRequest`
> (`app/utils/priorOauth.ts`) поверх `resolvePriorTokenAuth` (`server/utils/priorTokenAuth.ts`):
>
> 1. **Регистрация приложения (DCR)** — `buildRegistrationMetadata` (`tokenEndpointAuthMethod`);
> 2. **Токен Б** (создание согласия, `client_credentials`) — `server/utils/priorConnectStart.ts`;
> 3. **Обмен `code` на токен** — `server/utils/bankConnectCallback.ts`;
> 4. **Рефреш токена** — `server/utils/ensureBankToken.ts` (`bankRefreshRequest`).
>
> ⚠ Пункт 2 легко пропустить (он в connect-преамбуле, а не в «токенных» модулях) — а именно он
> ломает прод **на первом же шаге** подключения, раньше остальных. Есть отдельный тест ровно на это.
> В скрипте разведки то же самое касается и `/oauth2/revoke` (в backend такой ветки нет).
>
> **Что осталось:** живой прогон на sandbox (`pnpm prior:test --auth-method private_key_jwt`).
> ⚠ Он **заблокирован** отказом банка на создании согласия (см. «Открытый блокер»), а не
> транспортом: до `:9345` мы уже достучались через крипто-шлюз (#460), и `private_key_jwt`
> подтверждён на обеих регистрациях — токен выдаётся.
>
> Способ аутентификации приложения — **отдельный слой** от транспортного TLS: на проде BY-крипто TLS
> (СКЗИ) обязателен при любом из этих методов.

### Скрипт живой проверки sandbox: `pnpm prior:test`

`scripts/prior-oauth-test.mjs` — самодостаточный (без npm-зависимостей, ESM, как
`alfa-oauth-test.mjs`) прогон **sandbox** по контракту выше. Конфиг — `.env.priorbank`
(шаблон `.env.priorbank.example`); токены/счета маскируются, вывод — в `prior-demo-output.json`
(gitignored). Режимы:

```bash
pnpm prior:test --gen-key      # RSA-пара + jwks для регистрации приложения (kid ← PRIOR_KID)
pnpm prior:test --oidc         # token A → /oidcdiscovery (issuer, token endpoint = aud)
pnpm prior:test --dcr          # token A (тех-приложение) → POST /register → бизнес-app client_id/secret
pnpm prior:test                # consent → authorize (подписанный request-JWT) → code → выписка
pnpm prior:test --url-only     # только собрать и показать authorize-URL (без сети)
pnpm prior:test --revoke <t>   # отзыв токена
```

Поток по умолчанию: token Б (`scope=accounts`) → `POST /accountConsents` → печатает
authorize-URL (подписывает `request`-JWT ключом `PRIOR_PRIVATE_KEY`) → входишь тестовым
пользователем (`testspr_le`/`testspr_pi`) → вставляешь redirect с `code` → обмен на токен B →
`GET /accounts` → асинхронные `POST`/`GET /accounts/{id}/statements`. Живой запуск — на деплой-сервере
с кредами `.env.priorbank` (sandbox `:9344`). Флаги для итераций:
`--access-token <tokenB>` (пропустить браузер), `--account <id>`, `--all`, `--from/--to`,
`--expires`, `--verbose`.

**Прод-метод аутентификации (#444):** `--auth-method private_key_jwt` переключает клиентскую
аутентификацию на подписанный `client_assertion`. Флаг влияет и на `--dcr`, потому что
зарегистрированный метод обязан совпадать с тем, которым потом ходим:

```bash
pnpm prior:test --auth-method private_key_jwt --dcr   # НОВАЯ регистрация под прод-метод
pnpm prior:test --auth-method private_key_jwt         # тот же поток тем же методом
```

Токен A (тех-приложение) остаётся на Basic всегда — это не DCR-клиент, у него нет `jwks`.
Против среды, отличной от sandbox, задавай ещё и `--audience` (значение читается через `--oidc`):
дефолт — sandbox-issuer и за `--base` он не следует.

### ⚠ Переключение РЕАЛЬНОГО деплоя на `private_key_jwt`

Это не «поменять одну переменную». У существующего приложения метод не переключается — нужна
**новая DCR-регистрация**, а значит новый `client_id`/`client_secret`. Отсюда следствие, которое
легко проглядеть:

> **Смена `client_id` осиротит все уже подключённые счета Приора.** Их `refresh_token` выдан
> старому клиенту, поэтому при следующем обновлении они начнут падать, пока админ не переподключит
> банк заново из настроек портала. Пер-портальные отказы `bank-fetch-prior` намеренно исключены из
> алертинга (#426), так что первым сигналом станет молча остановившийся импорт.

Порядок:

1. Зарегистрировать новое приложение под метод (`--dcr --auth-method private_key_jwt`), сохранить
   выданные `client_id`/`client_secret`.
2. Обновить в env бэкенда: `PRIOR_OAUTH_CLIENT_ID`, `PRIOR_OAUTH_CLIENT_SECRET`,
   **`PRIOR_OAUTH_AUTH_METHOD=private_key_jwt`**, и убедиться, что `PRIOR_OAUTH_PRIVATE_KEY` /
   `_KID` / `_AUDIENCE` заданы **на всех** процессах, включая воркер и крон (рефреш живёт там,
   а не в API-контейнере). При старте `envCheck` предупредит, если чего-то не хватает.
3. Предупредить клиентов и **переподключить счета** через настройки портала.
4. Откат: вернуть прежние `client_id`/`client_secret` и снять `PRIOR_OAUTH_AUTH_METHOD` —
   код целиком вернётся к прежнему поведению. Счета придётся переподключить снова.

Общее правило про ротацию банковских кредов — [`OPERATIONS.md`](OPERATIONS.md).

### Подтверждено на живом прогоне sandbox (2026-07-01)

Весь поток пройден end-to-end по свагерам DCR и Open-banking. Нюансы, которые дал живой прогон
(учтены в скрипте):

- **DCR `POST /register`** (`application/json`): `jwks` передаётся **строкой** (сериализованный JWK
  Set), `token_endpoint_auth_method` — **массив**; обязателен только `redirect_uris`. Имя приложения
  (`client_name`) обязано быть **уникальным** (дубль → `409`). Обновления
  имени по API нет (только `GET /register/{clientId}`) — смена имени = перерегистрация.
  ⚠ **Про имя здесь раньше стояло «кириллица/пробелы ок» — это неверный вывод из `201`.** Приняли —
  не значит «работает»: банк на WSO2, где `client_name` становится именем **приложения в Магазине
  API**, а витрина валидирует его по `^[a-zA-Z0-9 ._-]*$`. Имя вне этого набора регистрируется на
  уровне identity (токены выдаются штатно), а объект в витрине остаётся кривым — и снаружи это
  неотличимо от отказа по правам. Живая регистрация, прочитанная 2026-08-13, несла ровно такое имя:
  `Импорт выписки Bitrix24 basic 0812-162429`. Теперь имя строит `buildPriorClientName`
  (латиница/цифры/`. _ -`, без пробелов), а `buildRegistrationMetadata` **бросает** на небезопасном —
  проверять после отправки поздно, рабочего `PUT /register` нет.
- **`default_max_age` банк проставляет САМ — `900`** (прочитано с живой регистрации 2026-08-13; мы
  это поле не слали). Стоит держать под контролем: `max_age` в OIDC означает «переаутентифицировать
  пользователя, если `auth_time` старше», а у токена `client_credentials` никакого `auth_time` нет
  вообще — сервер, применяющий это правило к нему, может ответить только «требуется повторная
  аутентификация». Совпадение с текстом нашего 403 (`client re-authentication is required`) —
  причина, по которой скрипт теперь шлёт `default_max_age` явно (по умолчанию `0`, флаг `--max-age`).
  ⚠ Это **гипотеза, не установленный факт**: пока не проверена перерегистрацией.
- **`PUT /register/{clientId}` НЕ РАБОТАЕТ — проверено 2026-08-12.** Обе формы тела дают
  `500 Internal Server Error`: и `application/json`, и подписанный RS256 JWT (`application/jwt`) с
  теми же claim'ами, что принимает `POST /register`. Не `404` и не `405` — то есть маршрут
  существует, но обновление метаданных через него недоступно. Практический вывод: **любая правка
  регистрации (метод аутентификации, `jwks`, `redirect_uris`, имя) = ПЕРЕРЕГИСТРАЦИЯ**, а значит
  новый `client_id`, а значит переподключение всех уже подключённых счетов Приора. Отсюда правило:
  всё, что задаётся при регистрации, доводить до правильного вида ДО того, как подключён первый
  боевой счёт — пока перерегистрация ничего не стоит.
- **`GET /register/{clientId}` (токен A) — рабочий и очень полезный.** Одним запросом отдаёт
  `token_endpoint_auth_method`, `jwks` (с `kid`), `redirect_uris`, `grant_types`, `client_name`,
  то есть проверяет пригодность существующей регистрации без гаданий по UI кабинета.
- **`aud` в `client_assertion` — ТОЛЬКО `issuer` (:9544), проверено перебором 2026-08-12.**
  Это отдельное измерение от `aud` в `request`-JWT выше, и оно того стоило: банк различает два
  случая РАЗНЫМИ ошибками, и они читаются как диагноз.

  | `aud` | Ответ |
  |---|---|
  | `https://api.priorbank.by:9544/oauth2/token` (issuer) | принят; дальше проверяется подпись |
  | `…:9344/open-banking-authorize/v1.0/oauth2/token` (token_endpoint) | `400 invalid_request` «Failed to match audience values» |

  Массив против строки — **безразлично**, оба варианта приняты. Практический вывод: `400
  invalid_request` про audience = неверный `aud`; `401 invalid_client` = `aud` верный, но не
  сошлась подпись (не тот ключ / `kid`). Раньше эти два случая были неразличимы.
- **Подписки на API нужны КАЖДОЙ регистрации отдельно и различаются по симптому.** DCR создаёт
  приложение без подписок; предыдущая регистрация их не передаёт. Поскольку токен и ресурсы живут
  за РАЗНЫМИ API, отсутствие каждой подписки проявляется на своём шаге:

  | Не подписано | Где падает |
  |---|---|
  | `Open-banking v1.0` | любой вызов ресурсного API → 403 `900908` |

  ⚠ **Отказ по подписке отличим от отказа по правам — по ОТПРАВИТЕЛЮ и коду** (замерено 2026-08-12
  на свежей DCR-регистрации без единой ручной подписки):

  ```
  нет подписки : 403 {"code":"403 Resource forbidden","errors":[{"errorCode":"BY.PRIORBANK.Unauthorized",
                      "message":"Access failure for API: /open-banking/v1.0 … (900908) - Resource forbidden"}]}
  подписка есть: 403 {"code": "403 Forbidden","errors":[{"errorCode":"BY.NBRB.Reauthenticate", …}]}
  ```

  Первое — шлюз WSO2 (`900908`), второе — бэкенд СПР. Путать их дорого: они требуют
  ПРОТИВОПОЛОЖНЫХ действий (подписать приложение vs разбираться с правами регистрации), а
  различаются только текстом внутри одинакового HTTP-кода.

  **Подписки управляются по REST — DevPortal API на порту 443** (найдено 2026-08-13). Инструкция
  описывает подписку как ручной шаг в кабинете, и именно поэтому она терялась при каждой
  перерегистрации. На деле у витрины есть полноценный API WSO2 APIM v3:
  `https://api.priorbank.by/api/am/devportal/v3/` — **не** на `:9344` (там шлюз, отдаёт `404`) и
  **не** на `:9443` (снаружи закрыт). Именно к нему относятся скоупы `apim:subscribe` /
  `apim:app_manage`, которые мы запрашиваем в токене A и до сих пор нигде не использовали.

  Часть эндпоинтов открыта вообще без авторизации (`IsAnonymousModeEnabled: true`), поэтому ID
  можно прочитать заранее и не гадать:

  | API | `apiId` | тариф |
  |---|---|---|
  | `Open-banking` v1.0 | `f0e0e91d-ace5-4f59-a608-54af4775696a` | `Standard` |
  | `Open-banking-authorize` v1.0 | `a24d3551-794a-4971-b18b-0dbc8578efa5` | `Standard` |

  | `Open-banking-info` v1.0 | `c65237ac-bad9-4007-afee-66e3ac5df6cd` | `Standard` |

  Подписка — `POST /subscriptions` с `{applicationId, apiId, throttlingPolicy:"Standard"}`. ⚠
  `applicationId` — это **UUID витрины**, не `client_id`; связать их можно через
  `GET /applications/{id}/oauth-keys` (там лежит `consumerKey` = наш `client_id` и, что важнее,

  **Что этот API показал про наш блокер (2026-08-13) — три гипотезы закрыты за один прогон:**

  - **Приложение в витрине ЕСТЬ**, с тем самым кириллическим именем, статус `APPROVED`. То есть
    `client_name` вне `^[a-zA-Z0-9 ._-]*$` **не помешал** создать объект в Магазине API — гипотеза
    «DCR создал клиента только на уровне identity» **опровергнута**. (Латиницу в коде оставили: она
    всё равно правильнее, но причина 403 не в ней.)
  - **Тип ключей — `SANDBOX`**, единственный набор у этого приложения. Для песочницы верно.
  - **Подписки были и до правки** (`Open-banking`, `Open-banking-authorize`, обе `UNBLOCKED`), а
    после добора до полного набора из пяти API — тех же, что у рабочего ручного тех-приложения —
    **403 не изменился**. Подписки как причина исчерпаны окончательно.
  - **Владелец у всех приложений кабинета один и тот же**, все `APPROVED`. Значит «тип учётной
    записи» (версия банка) может объяснять только весь кабинет целиком, а не различие между
    приложениями.
  - ⚠ **Побочный дефект на стороне банка:** ручное тех-приложение, подписанное на `Open-banking`,
    на запрос токена со `scope=accounts` отвечает **`500 server_error`** (при этом со
    `scope=apim:*` токен выдаёт штатно, и наш DCR-клиент `accounts` получает без проблем). Из-за
    этого не удалось довести до конца контролируемое сравнение «ручной клиент vs DCR-клиент» — это
    отдельный вопрос к банку.

  ⚠ **Токен Б выдаётся и БЕЗ ручных подписок** — свежерегистрированное DCR-приложение получило
  токен по `client_secret_basic` сразу, при 403/900908 на обоих ресурсных вызовах. Прежняя запись
  здесь утверждала обратное («нет подписки на `Open-banking-authorize` ⇒ 403 на токене») — это
  наблюдение было ошибочно обобщено с одного случая. Значит **успешный токен ничего не говорит о
  подписках**, и проверять их надо ресурсным вызовом.
- **`client_name` уникален с точностью до символа, повтор → `409 Resource Already Exists`.**
  Автоматической генерации имени с точностью до минуты недостаточно: два запуска подряд в одну
  минуту дают коллизию. ⚠ Скрипт при этом обязан выходить ДО правки `.env` — иначе повторный
  запуск затрёт рабочий `client_id` пустым значением.
- **`aud` в `request`-JWT** = `issuer` из `/oidcdiscovery` = `https://api.priorbank.by:9544/oauth2/token`
  (порт **9544**, не 9344).
- **Согласие `POST /accountConsents`**: `data.expirationDate` — **срок действия согласия, в будущем**
  (не окно выписки); окно — `transactionFromDate/ToDate` (может быть в прошлом).
- **Ресурсный API требует ДВА заголовка, и проверяет их ДО тела** (замерено 2026-08-12): помимо
  `x-fapi-interaction-id` каждая ЗАПИСЬ несёт **`x-idempotency-key`**, иначе
  `400 BY.NBRB.Header.Missing`. Проверено четырьмя разными телами согласия — ответ во всех случаях
  одинаковый, то есть по нему о теле судить нельзя вообще. Обратная сторона того же: как только
  заголовки на месте, ошибка по телу становится точной — полный ISO в `expirationDate` даёт
  `BY.NBRB.Field.Invalid: must match yyyy-MM-dd` с указанием `path`. В коде заголовки записи —
  отдельная функция `priorWriteHeaders` (запись без ключа идемпотентности не собирается по типам).
- **Диагностика по отправителю ошибки.** Компактный JSON (`{"code":"400 Bad Request",…`) отдаёт
  ШЛЮЗ (валидация запроса), JSON с пробелами после двоеточий (`{"code": "403 Forbidden", …`) —
  БЭКЕНД СПР. Это даёт бесплатный признак: долетел ли запрос до банковской логики или отсечён
  раньше. Так, `GET /accounts` без согласия отвечает `BY.PRIORBANK.Request.Invalid` («нет
  `x-accountConsentId`») — ответ бэкенда, то есть подписка на `Open-banking v1.0` в порядке, и
  403 на соседнем `POST /accountConsents` того же API искать надо не в подписках.
- **`scope` токена Б**: запрошенный `accounts` выдаётся как `accounts` (плюс WSO2-шный `default`),
  `accounts consents` — принимается, а `consents`/`openid`/пустой → `invalid_scope`. То есть перебор
  scope как объяснение отказа на согласии исчерпан. Свагер `Open-banking-authorize` это
  подтверждает: для `client_credentials` допустимы ровно `accounts` / `payments` / `apim:*`.
- ⚠ **`BY.NBRB.Reauthenticate` НЕ несёт диагностики.** По свагеру `Open-banking v1.0` это
  **пример** кода в схеме `Error403` — то есть штатный код ЛЮБОГО отказа авторизации на
  `POST /accountConsents`, а не сигнал «согласие требует повторной аутентификации». Читать его как
  указание на состояние согласия — ошибка (я её сделал): текст сообщения банк подставляет свой, а
  сам код одинаков для всех причин отказа.
- **Свагер `Open-banking v1.0` подтверждает наш запрос согласия целиком** (сверено 2026-08-12):
  обязательны ровно два заголовка (`x-fapi-interaction-id`, `x-idempotency-key`; `x-fapi-auth-date`,
  `x-fapi-customer-ipaddress`, `x-customer-useragent`, `x-api-key` — необязательные), `security` =
  scope `accounts`, тело — `{data:{permissions[]}}`, где обязателен только `permissions`, и все
  восемь запрашиваемых нами значений входят в enum (там же `ReadBalances`, который мы намеренно не
  просим). Даты — `yyyy-MM-dd`. Значит при 403 на этом шаге искать дефект в запросе бессмысленно:
  отказ — решение банка о правах регистрации, и разговор с банком нужно начинать сразу.
- **⛔ Открытый блокер (2026-08-12): `POST /accountConsents` → `403 BY.NBRB.Reauthenticate`**
  («client re-authentication is required to process the request»). Со стороны приложения проверено и
  ИСКЛЮЧЕНО всё, что можно проверить снаружи — список ниже, чтобы не проходить его заново:

  | Гипотеза | Чем исключена |

  | нет подписки на `Open-banking` | `GET /accounts` тем же токеном доходит до бэкенда (`BY.PRIORBANK.Request.Invalid`); отказ по подписке выглядит иначе — `900908` от шлюза |
  | не тот `scope` | перебран до конца, см. таблицу ниже — с `accounts` в любом сочетании отвечает БЭКЕНД, без него отказывает ШЛЮЗ |
  | неверное тело | свагер: обязателен только `permissions`, все восемь наших значений в enum; полный ISO в дате даёт точечный `BY.NBRB.Field.Invalid`, значит тело разбирается |
  | не хватает заголовков | оба обязательных шлём; добавление `x-fapi-auth-date`, `x-fapi-customer-ipaddress`, `x-customer-useragent` ничего не меняет |
  | метод аутентификации | воспроизведено на `private_key_jwt` и на `client_secret_basic` — двух независимых регистрациях |

  **Перебор `scope` на самом `POST /accountConsents` (2026-08-13) — закрывает последнюю
  client-side переменную и попутно доказывает, что ШЛЮЗ удовлетворён полностью:**

  | `scope` токена | Ответ | Кто ответил |
  |---|---|---|
  | `accounts` | `403 BY.NBRB.Reauthenticate` | бэкенд СПР |
  | `accounts consents` | `403 BY.NBRB.Reauthenticate` | бэкенд СПР |
  | `accounts payments` | `403 BY.NBRB.Reauthenticate` | бэкенд СПР |
  | `payments` | `403 The access token does not allow you to access the requested resource` | **шлюз WSO2** |

  Читается так: без `accounts` запрос отсекает шлюз, с `accounts` — в любом сочетании — шлюз
  пропускает, и отказ выносит бэкенд. ⚠ Заодно это **опровергает свагер**: у `POST /accountConsents`
  он объявляет `security: [{"default": []}]`, то есть scope формально не требуется, а на деле шлюз
  требует `accounts`. Полагаться на пустой `security` в этом свагере нельзя.

  **Контроль на токен — три РАЗНЫХ ответа, и это решающий довод:**

  | запрос | ответ |
  |---|---|
  | без заголовка `Authorization` | `401 Missing Credentials` |
  | с заведомо неверным токеном | `401 Invalid Credentials` |
  | с нашим токеном | `403 BY.NBRB.Reauthenticate` |

  Раз отсутствующий и неверный токен дают СВОЙ код, а наш — другой, значит наш токен принят и
  аутентификация пройдена: 403 выносится уже ПОСЛЕ неё. Это отказ по правам. ⚠ Такой контроль стоит
  делать первым при любом «странном 403»: он одним замером отделяет «нас не пускают» от «мы что-то
  не так шлём», а стоит три запроса.

  **Решающий замер: дословное тело из официальной Postman-коллекции банка тоже даёт 403.**
  Прогнаны три варианта — коллекционный (9 прав, включая `ReadBalances`, плюс окно
  `transactionFromDate`/`ToDate`), наш набор с окном и коллекционный без окна: ответ во всех трёх
  одинаковый. Запрос как причина исключён окончательно, вместе с двумя последними отличиями нашего

  **Версия банка (2026-08-12): дело в ТИПЕ УЧЁТНОЙ ЗАПИСИ разработчика.** При регистрации в
  devportal выбирается «Тип пользователя» — **«Пользователь API»** или **«Разработчик»**, и внутри
  первого ещё «пользователь API **1-го** / **2-го** типа». Банк: «чтобы согласие создавалось в
  тестовой среде — предположу, вам нужна уч. запись **разработчика**».

  ⚠ Это ровно тот параметр, который **не виден изнутри запроса**: он не в теле, не в заголовках, не
  в токене и не в регистрации приложения — он у ВЛАДЕЛЬЦА кабинета, под которым приложение создано.
  Поэтому перебор запроса и не мог его найти, сколько бы гипотез мы ни закрыли.

  Косвенное подтверждение было у нас в свагере с самого начала, и мы прошли мимо: заголовок
  `x-api-key` описан там как «идентификатор Apikey для запросов пользователя API **первого** типа»,
  а `x-fapi-auth-date` — как «дата последней авторизации пользователя API **второго** типа». То есть
  один метод ожидает разные наборы заголовков в зависимости от типа учётки — API типозависим, и
  отказ мог зависеть от типа. **Урок:** если в описании метода параметры расходятся по «типам
  пользователя», тип — такая же переменная конфигурации, как scope, и проверять её надо наравне с
  остальным, а не считать анкетной формальностью.

  ⚠ Тип для разработки и тип для прода, вероятно, РАЗНЫЕ: в проде мы — поставщик услуги, который
  запрашивает данные по поручению клиента (по СПР это «пользователь API 2-го типа»), тогда как для
  песочницы банк называет «разработчика». Смена типа может потребовать пересоздания приложений и
  ключей ⇒ новый `client_id` ⇒ переподключение счетов. Это надо выяснить ДО прод-регистрации.
- **Промышленный контур: два РАЗНЫХ хоста, и это не косметика** (ответ банка, 2026-08-12).
  Серверные вызовы идут на `apibel.priorbank.by:9345` по BY-крипто TLS — там наш шлюз (живой прогон
  подтверждён). **Страница авторизации согласия отдаётся с
  ОБЫЧНЫМ сертификатом**, поэтому браузеру администратора СКЗИ не нужно, и продукт работает у
  клиента без установки чего-либо на рабочее место — это снимает последний продуктовый блокер
  промышленного Приорбанка.

  ⚠ Отсюда следует, почему `PRIOR_OAUTH_AUTHORIZE_BASE` — **отдельная переменная, а не «публичная
  форма» `API_BASE`** ([#455](https://github.com/bx-shef/client-bank-alfa-by/issues/455)): TLS
  выбирается на СОЕДИНЕНИЕ, а не на путь, поэтому хост, говорящий только по СТБ 34.101.65,
  физически не может отдать ту же страницу с обычным сертификатом. Это разные адреса по
  устройству, а не по договорённости. ⚠ Проксировать страницу входа в интернет-банк через свой
  домен нельзя ни при каких условиях: пользователь вводил бы банковские креды на чужом сайте.

  **Осталось уточнить у банка ТОЧНЫЙ адрес** промышленного `GET /oauth2/authorize` (какой хост/порт
  ставить в `PRIOR_OAUTH_AUTHORIZE_BASE`) и хост промышленного DCR — если регистрация живёт на
  `:9345`, понадобится [#473](https://github.com/bx-shef/client-bank-alfa-by/issues/473)
  (`/open-banking-dcr/` в allowlist шлюза), если на обычном TLS — не понадобится.
- **Метод аутентификации на отказ по согласию НЕ влияет** (замерено 2026-08-12): отказ
  воспроизведён на ДВУХ независимых регистрациях — `private_key_jwt` и `client_secret_basic`, обе
  подписаны, у обеих `GET /accounts` доходит до бэкенда. Значит `PRIOR_OAUTH_AUTH_METHOD` в этой
  диагностике можно не трогать вовсе.
- **Списка согласий нет:** `GET /accountConsents` → **405** (в свагере у пути только `POST`);
  прочитать можно лишь конкретное — `GET /accountConsents/{accountConsentId}`. Проверить «нет ли уже
  висящего неавторизованного согласия» снаружи, не зная его id, **невозможно**.
- **Выписка `POST /accounts/{id}/statements`**: тело `{ data: { statement: { fromBookingDate,
  toBookingDate } } }`, даты в формате **`yyyy-MM-dd`** (без времени), окно **≤ 3 месяцев** (иначе
  `BY.NBRB.Field.InvalidDate`). Ответ `201` → `data.statement.statementId` → опрос
  `GET …/statements/{statementId}` (200 = готова). Sandbox **жёстко троттлит** (`429`) — по одному счёту.
- **Ответ выписки**: `data.statement` c `openingAvailableBalance`/`closingAvailableBalance`
  (`creditDebitIndicator`, `currency`, `amount`) + `transaction[]` + `links`/`meta` (пагинация).
  Элемент транзакции (`StatementInfoTransaction`): `creditDebitIndicator` (Credit=приход/Debit=расход),
  `amount`/`currency`/`equivalentAmount`, `transactionDetails` (назначение), `transactionId`, `number`,
  `bookingDateTime`/`valueDate`, `debtor`/`creditor` (`name`), `debtorAccount`/`creditorAccount.identification`
  (IBAN), `debtorAgent`/`creditorAgent.identification` (BIC) — прямой маппинг в наш `StatementItem`.

Требование СПР 6.02: TLS с сервером авторизации Приорбанка на проде должен идти на **белорусских
криптоалгоритмах** (СТБ 34.101.65). Инструкция (стр. 4) говорит дословно:

> «разработчику обязательно требуется приобрести СКЗИ … для взаимодействия с нашим сервером
> авторизации, который использует программный комплекс "Сервер TLS АВЕСТ" (AvTLSSrv). На стороне
> клиента должны быть установлены СКЗИ, обеспечивающие клиентскую часть TLS-соединения, согласно
> требованиям СТБ 34.101.65 **с возможностью аутентификации сервера авторизации или двусторонней
> аутентификации**. Такими СКЗИ **могут быть, в том числе**, AvAuthGate (ЗАО «АВЕСТ») или компоненты
> комплекта абонента АВЕСТ (AvUCK). СКЗИ настраиваются в соответствии с рекомендациями разработчика.»

Что отсюда следует буквально — и что **не** следует:

- **AvTLSSrv — это то, что стоит у банка.** Для нашей стороны инструкция продукт не предписывает
  вообще: список открытый («могут быть, **в том числе**»), названы **AvAuthGate** и **AvUCK**.
  ЗАО «АВЕСТ» на прямой запрос рекомендует **AvTLSSrv с настройками клиентской части** (2026-08) —
  это рекомендация вендора, а не требование банка. Банк на вопрос о совместимых версиях ответил:
  «перечня совместимых версий не имеем, выбор решения лежит на разработчике».
- **Достаточно односторонней аутентификации** (только сервера авторизации) — двусторонняя названа
  как альтернатива, не как обязанность. Подтверждено ответом банка (2026-08): «достаточно серверной
  аутентификации».
- **Сертификат ГосСУОК для нашего сценария НЕ нужен.** В разделе про СКЗИ он не упомянут ни разу;
  единственное место в инструкции — §4.1.3, в описании `tls_client_auth` (mTLS). Мы этот метод не
  используем, см. «Способы аутентификации» выше и [#444](https://github.com/bx-shef/client-bank-alfa-by/issues/444).
  *(Ранее в этом документе ГосСУОК ошибочно значился как обязательный для прода — два разных
  требования были склеены в одно.)*
- **Про носители ключей (НКИ) в инструкции нет ничего** — это свойство конкретного продукта СКЗИ,
  а не требование банка. Вопрос принципиальный для облачного сервера (аппаратный токен туда не
  вставить) и адресуется вендору, см. [#41](https://github.com/bx-shef/client-bank-alfa-by/issues/41).

Ниже — **наша трактовка деплоя** (в PDF деталей про шлюз/Docker нет):

- **Где стоит:** на **нашем сервере (backend)**, а не у конечного пользователя. Практично
  развернуть как локальный **TLS-шлюз**: наш код ходит в него обычным HTTP(S), а он поднимает
  BY-крипто TLS до `apibel.priorbank.by:9345`; base URL Приора на проде указывает на шлюз.
- **Конечному пользователю ничего не нужно** — он лишь вводит логин/пароль интернет-банка на
  странице банка (обычный браузер/HTTPS); его пароль наше приложение не видит. *(Это уже из
  инструкции: авторизация согласия — на странице Приорбанка.)*
- **Sandbox работает без СКЗИ** — весь флоу разрабатываем и тестируем на `:9344` обычным TLS,
  СКЗИ подключаем последним шагом перед продом. *(Из инструкции: BY-крипто требуется для
  взаимодействия с сервером авторизации по `:9345`.)*
- **Docker (наша интерпретация):** СКЗИ — **не библиотека в образ**, а отдельный крипто-шлюз
  (продукт АВЕСТ). Разумно развернуть **отдельным сервисом** рядом с backend
  (сайдкар/на хосте) — **поддержку Linux/контейнера, требование к носителю ключей и лицензирование
  обязательно уточнить у АВЕСТ**. Прод-схема (шлюз + маршрут backend→шлюз→банк) — отдельный долг.
- **Адреса расщеплены — код к шлюзу готов** (#455). ⚠ Написано под **шлюзовую** модель; для
  диспетчерного AvTunProxy эта подмена адреса, скорее всего, не используется вовсе — см. ниже
  «Следствие для интеграции». У `PRIOR_OAUTH_API_BASE` было **две роли**, и
  они требуют разных адресов:
  | Переменная | Кто ходит | Куда при шлюзе |
  |---|---|---|
  | `PRIOR_OAUTH_API_BASE` | backend: токен, согласие, счета, выписка | **на шлюз** (можно `http://` — внутренний адрес) |
  | `PRIOR_OAUTH_AUTHORIZE_BASE` | **браузер администратора**, top-level | **на публичный хост банка** (только `https://`) |

  `PRIOR_OAUTH_AUTHORIZE_BASE` не задан ⇒ берётся `PRIOR_OAUTH_API_BASE` — верно, пока шлюза нет.
  Правила адресов — чистый `app/utils/bankGatewayUrl.ts` (под тестами): `http://` разрешён **только**
  на внутренний хост (loopback / имя docker-сервиса / приватная сеть), потому что именно так работает
  шлюз; `http://` на публичный хост отвергается — это отправило бы токен открытым текстом. Внутренний
  адрес в authorize-origin отвергается тоже: это ровно та ошибка, которая убивает подключение молча.
  Заданное, но негодное значение **не подменяется** молча на API-base — конфиг просто не собирается.

  Где правило реально применяется (а где нет — чтобы не считать проверку тотальной):
  | Читатель env | Переменная | Проверка |
  |---|---|---|
  | `priorConnectStart.ts` (`priorConnectConfigFromEnv`) | `PRIOR_OAUTH_API_BASE` / `_AUTHORIZE_BASE` | обе, fail-closed → 400 |
  | `priorFetch.ts` (`priorApiBaseFromEnv`) | `PRIOR_OAUTH_API_BASE` | да |
  | `bankFetch.ts` (`bankApiConfig`) | `PRIOR_OAUTH_API_BASE`, `ALFA_OAUTH_API_BASE` | да (оба банка) |
  | `ensureBankToken.ts` (`bankCredsFromEnv`) | `{PRIOR,ALFA}_OAUTH_TOKEN_URL` | да |
  | `envCheck.ts` | всё вышеперечисленное | предупреждения на старте |

  Вне охвата **сознательно**: `PRIOR_OAUTH_AUDIENCE` (это claim в JWT, а не сетевой адрес),
  `ALFA_OAUTH_REDIRECT_URI`/`PRIOR_OAUTH_REDIRECT_URI` (их байт-в-байт сверяет банк — наша
  нормализация сломала бы сверку) и authorize-хост Альфы (выводится из её `TOKEN_URL`, который уже
  проверен).
- ⚠ **`PRIOR_OAUTH_AUDIENCE` трогать нельзя** — это claim `aud` внутри подписанного `request`-JWT,
  который проверяет банк, а не сетевой адрес. Переставить его «за компанию» на шлюз = банк начнёт
  отвергать JWT, а симптом будет выглядеть как ошибка авторизации, не как ошибка конфигурации.
- ⚠ **`PRIOR_OAUTH_API_BASE` и `PRIOR_OAUTH_TOKEN_URL` — независимые переменные**, код нигде не
  проверяет, что они смотрят на один адрес. Обновят одну, забудут вторую — рефреш токена тихо
  продолжит стучаться на старый хост. Проверять обе вместе.

#### Разведка AvTunProxy: что проверено запуском (2026-08-11)

Кандидат на роль клиентского СКЗИ — **AvTunProxy** (ЗАО «АВЕСТ», [avtunproxy.by](https://avtunproxy.by/)):
HTTP-прокси, шифрующий трафик по СТБ 34.101.65. Дистрибутив скачан и **запущен**, поэтому ниже —
наблюдения, а не пересказ рекламы. Версия **5.10.12** (сборка 30.01.2022, Go), внутри архива три
файла: бинарник + `libavc.so` + `libavcryptokibign.so`.

| Проверка | Результат |
|---|---|
| Самотест криптоядра | `avc self-test result: OK` |
| Запуск без графики | **Нет.** Слинкован с GTK-3/`libappindicator`, использует systray → `Gtk-WARNING: cannot open display` и выход |
| Запуск под `xvfb-run` | **Да:** `[APP] binding to 127.0.0.1:10224` → `binded OK` |
| Нужен ключ/носитель, чтобы стартовать и принять запрос | **Нет.** Ни токена, ни сертификата, ни контейнера — прокси поднялся и обработал `CONNECT` |
| Настройка без GUI | **Да:** флаг `-c <config.yml>`; ключи YAML — `net.port`, `net.proxy.{addr,auth_data,bypass}` (внешний прокси), `trust`, `refresh_config` |

Сетевые зависимости при старте (важно для закрытого контура): `config.avtunproxy.by`,
`rand.avtunproxy.by` (**источник случайности** — тянется у вендора), плюс корни и CRL с `nces.by`,
`avest.by`, `cdn.belpost.by`, `portal.nalog.gov.by`, `skko.by`.

#### Живой прогон с деплой-сервера (Debian 11, 2026-08-12)

Тот же дистрибутив запущен **владельцем на прод-сервере**, у которого есть сеть до банка.
Дистрибутив — с сайта вендора (<https://avtunproxy.by/linux/>), проверенная сборка **5.10.12**
(`avtunproxy/version`, дата файлов 30.01.2022); регистрация для скачивания не требуется.

Повторный разворот на чистом Debian 11:

```bash
sudo apt-get install -y xvfb xauth libgtk-3-0 libglib2.0-0 \
                        libappindicator3-1 libpcsclite1 libusb-1.0-0
tar xzf avtunproxy-latest.linux64.tar.gz && cd avtunproxy
ldd ./avtunproxy | grep "not found"        # ПУСТО = зависимости закрыты
setsid xvfb-run -a ./avtunproxy -l dbg > avtp.log 2>&1 < /dev/null &
sleep 20
grep -E "self-test|binded" avtp.log        # ждём: self-test OK + binded OK
curl -s -o /dev/null -w "PAC=%{http_code}\n" http://127.0.0.1:10224/proxy.pac   # ждём 200
```

⚠ `libpcsclite1` обязателен, хотя смарт-карт у нас нет — это жёсткая ELF-зависимость (`NEEDED`),
без неё процесс не стартует вовсе (`error while loading shared libraries`). ⚠
`libayatana-appindicator3-1` **не подходит**: SONAME другой (`libayatana-appindicator3.so.1`),
нужен именно `libappindicator3-1` — иначе симлинк + `ldconfig`. ⚠ `xauth` нужен самому `xvfb-run`
и на минимальном образе отсутствует. Уборка: `pkill -f avtunproxy` (процесс ничего не оставляет
за пределами `~/.config/avtunproxy/config.yml`).

| Проверка | Результат |
|---|---|
| Старт | `avc self-test result: OK`, `[APP] binded OK` |
| Лицензия подписанта обновлений (админ-страница `/`) | **valid until 2030-01-01** — но это НЕ ответ про серверное использование, см. ниже |
| PAC | `200` |
| `apibel.priorbank.by` в PAC | **отсутствует** (0 совпадений) |
| Другие банки в PAC | `openapi.mtbank.by`, `openapi.paritetbank.by`, `test-openapi.paritetbank.by`, `ibapi.rrb.by` |
| Туннель до банка | `[PROXY] CONNECT apibel.priorbank.by:9345 -- 200 -- 73.5 ms` — соединение установлено |
| Запрос | `curl: (35) SSL routines:set_client_ciphersuite:unknown cipher returned` |

**Как это читать.** Ошибка пришла из OpenSSL **внутри curl**, а не от прокси: сервер прислал в
ServerHello шифронабор, которого клиент не знает — то есть **банк ответил белорусским шифром**, он
жив и говорит по СТБ 34.101.65. Но раз хендшейк вёл curl, значит для этого хоста прокси сработал
**сквозным туннелем** и криптографию не применил.

**Вывод ДОКАЗАН сравнением двух банков** (тот же прокси, тот же прогон, соседние запросы):

```
[rid=3dbbeb28…] [PROXY] stb handshake ok; ciphersuite: 65303
[rid=3dbbeb28…] [PROXY] CONNECT openapi.mtbank.by:443     -- 200 -- 256.6 ms   → MTBANK=303
[rid=d4b5d352…] [PROXY] CONNECT apibel.priorbank.by:9345  -- 200 -- 1076.6 ms  → PRIOR=000
```

Для **mtbank** (есть в списке) прокси сам провёл **СТБ-рукопожатие** — строка `stb handshake ok`
с тем же `rid`, что и запрос, — и вернул настоящий HTTP-ответ `303`. Для **Приорбанка** (нет в
списке) строки `stb handshake ok` **не появилось вообще**: туннель открылся, криптография не
применилась, и рукопожатие пытался вести сам curl → `unknown cipher`.

То есть AvTunProxy применяет BY-крипто **только к хостам из своего списка** (`proxy.pac`, приезжает
с `config.avtunproxy.by`).

⚠ **Оговорка о чистоте этого сравнения.** В нём различаются **две** переменные сразу: и хост
(в списке / нет), и порт (443 / 9345). Само по себе оно не отличает «дело в списке» от «крипто
применяется только на 443». Порт исключён **следующим** экспериментом: там взят хост **из списка**,
но на порту **7443**, и СТБ-обработка началась (прокси дошёл до разбора сертификата). Различие,
таким образом, действительно по списку, а не по порту.

⚠ Второе, чего этот прогон не доказывает: что Приорбанка нет в списке **прямо сейчас на стороне
вендора**. Список кешируется локально (`refresh_config`), и мы не форсировали обновление перед
замером. Для причинного вывода это неважно, а для формулировки заявки — проверяется одним
перечитыванием `proxy.pac` после перезапуска.

**Схема работает целиком** — на headless-сервере, без единого ключа, носителя и сертификата, с
лицензией до 2030. **Технически остался один шаг:** попросить АВЕСТ добавить
`apibel.priorbank.by:9345` (прод) и `api.priorbank.by:9344` (тест) в список. Вопрос предметный — для
трёх других банков РБ это уже сделано. ⚠ Но «один шаг» — только про **крипто-канал**: отдельно и
независимо остаются открытыми лицензирование продукта для **серверного** использования и вопрос,
поддерживает ли вендор такой сценарий вообще (см. предупреждение в конце раздела).

⚠ **Одна деталь к проверке при интеграции:** curl получил `303` от mtbank **без** ошибок
сертификата, хотя клиентскую сторону TLS терминировал прокси. Чем именно он при этом
представляется, из лога не видно. Когда Приорбанк добавят в список — проверить, доверяет ли наш
backend предъявленному сертификату (и не потребуется ли положить CA прокси в доверенные).

#### Совместимость крипто с сервером Приорбанка — ДОКАЗАНА

> ⛔ **Приём, которым это проверено, повторять нельзя** — ни в проде, ни «ещё раз посмотреть».
> Он состоял в локальной подмене имени так, чтобы СКЗИ применило криптографию к адресу вне своего
> списка ресурсов. Это использование сертифицированного средства вне заявленной вендором области
> применения, и оно бьёт ровно по тому, что нам нужно: по доброй воле АВЕСТ (у которых лежит наша
> заявка) и по доверию банка (с которым подписан договор). Разовый замер сделан, результат ниже —
> **этого достаточно, воспроизводить нечего**. Пошаговый протокол намеренно не публикуем.
> Легальный путь один: регистрация хостов банка в списке ресурсов.

Открытым оставался главный технический риск: договорятся ли реализация СТБ у АВЕСТ и сервер
Приорбанка. Замер выполнен на изолированном стенде (разобран сразу после), внутри нашего сервера,
без обращения к чужим системам под чужим именем: TCP-соединение уходило **на адрес банка**, с
которым у владельца заключён договор.

Показательная строка из журнала прокси:

```
[ERR] [PROXY] HTTP 503 - x509: certificate is valid for apibel.priorbank.by, not <локальное имя>
```

**Как читать.** Чтобы выдать такую ошибку, прокси обязан был: провести СТБ-рукопожатие с сервером
банка → **получить его сертификат** (сообщение `Certificate` идёт **после** `ServerHello`: клиент,
который не понял выбранный сервером шифронабор, обрывается прямо на `ServerHello` и до сертификата
не доходит — именно это и делает обычный OpenSSL) → разобрать
его и прочитать имя. Отказ произошёл **только** на сверке имени. Напомним, что обычный OpenSSL с
этим сервером не согласовывает даже шифр — а крипто АВЕСТ дошло до разбора сертификата. Значит
**реализации совместимы**, и единственное недостающее звено — запись в списке ресурсов.

Попутно видно, каким корням доверяет прокси: `Корневой удостоверяющий центр ГосСУОК`,
`BY Root CA NCES 2` (НЦЭУ) и корни АВЕСТ — то есть сертификат банка проверяется против штатной
белорусской иерархии, отдельный CA докладывать не придётся.

⚠ **Следствие для интеграции.** AvTunProxy — **прокси**, а не reverse-шлюз, поэтому подключается,
скорее всего, НЕ подменой базового адреса (`PRIOR_OAUTH_API_BASE=http://crypto-gw:…`, как заложено
в #455), а прокси-диспетчером (undici `ProxyAgent`), при котором URL остаётся публичным адресом
банка. ⚠ Это **не** снимает вопрос доверия к сертификату, отмеченный абзацем выше: при схеме
`https://` через `CONNECT` наш Node всё равно проводит собственное рукопожатие внутри туннеля и
что-то валидирует. Вопрос закрыт будет только замером после регистрации хостов. Механизм #455 не
пропадает — он нужен шлюзовым продуктам (AvAuthGate/AvTLSSrv). Проектировать до ответа АВЕСТ рано.

⚠ **Про ключевые носители — самая дорогая путаница в этой теме.** Разделять надо ДВЕ вещи:
шифрование канала (нужна BY-криптография; при **односторонней** аутентификации личный ключ не
участвует — банк подтвердил, что серверной достаточно) и аутентификацию клиента (у нас это
`private_key_jwt` — **свой** RSA-ключ, обычный файл, #444). Сертификат ГосСУОК нужен только методу
`tls_client_auth`, которым мы не пользуемся. Поэтому по нашей схеме ключ на носителе, вероятно, не
нужен вовсе — и это первое, что проверяет команда выше.

Если же он всё-таки потребуется: [KB/3](https://avtunproxy.by/support/kb/3/) описывает **только
физические носители** (AvToken/AvPass через `udev`-правило `idVendor=="c1a5"`, AvBign и ID-карта
через `pcscd` + правка `ifd-ccid.bundle/Contents/Info.plist`). Файлового/программного контейнера для
Linux в документации нет — «выгрузить ключ в файл и увезти на облачный сервер» **не описано ни одним
источником**, передаётся только сам носитель.

> ⛔ **Рабочий ключ бухгалтера (ГосСУОК) нельзя использовать ни для тестов, ни для интеграции.**
> Им подписывают бухгалтерскую и банковскую отчётность: всё подписанное этим ключом юридически
> совершено его владельцем. Экспорт в программный контейнер снимает аппаратную защиту и делает
> возможной подпись от чужого имени — а копию с сервера уже не отозвать. Если ключ вообще
> понадобится (по нашей схеме — **скорее всего нет**, см. абзац выше), выпускается **отдельный**,
> под это приложение. Это единственное место в документе, где цена ошибки — не «интеграция не
> заработала», а компрометация юридически значимой подписи.

⚠ **AvTunProxy — не прод-решение по умолчанию.** Это пользовательский продукт для браузера на
рабочем месте: требует виртуальный дисплей, ходит за случайностью на сервер вендора, сборке 4,5 года.
Как проверка гипотезы — годится; **лицензирование для серверного использования и поддержку надо
уточнить у АВЕСТ** — в дистрибутиве видна действующая до 2030 лицензия подписанта обновлений, но это
**не** ответ на вопрос, разрешено ли применять продукт как серверный компонент (#41; вопрос включён в
заявку вендору). Вендор на прямой запрос рекомендовал AvTLSSrv с клиентскими настройками — но
AvTLSSrv по инструкции банка стоит **у самого банка**, см. цитату выше.

**Альтернатива без вендорской зависимости:** открытая реализация BY-криптографии
[bee2evp](https://github.com/bcrypto/bee2evp) (патч BTLS к OpenSSL) реализует **тот же** шифронабор
`0xFF17`, на котором работает банковская инфраструктура РБ. Проверяется в
[#457](https://github.com/bx-shef/client-bank-alfa-by/issues/457) скриптом
`scripts/bee2evp-probe.sh`; не блокер (Приор уже обслуживается ручной загрузкой файла). ⚠ Отдельный
вопрос — **юридический**: годится ли несертифицированное средство под СПР 6.02; задан банку письменно.

> **Чего не хватает для подключения** (issue [#27](https://github.com/bx-shef/client-bank-alfa-by/issues/27),
> [#20](https://github.com/bx-shef/client-bank-alfa-by/issues/20)): тестовые `client_id/secret`
> тех-приложения, `redirect_uri` (наш публичный HTTPS); **для прода — СКЗИ на `:9345`**
> ([#41](https://github.com/bx-shef/client-bank-alfa-by/issues/41)). Прод-метод аутентификации
> ([#444](https://github.com/bx-shef/client-bank-alfa-by/issues/444)) — **реализован**, остался
> live-прогон на sandbox. Крипто — требование РБ, не
> сетевое ограничение: sandbox `:9344` достижим с деплой-сервера.
> Чистое ядро провайдера (сборка запросов, парсинг, нормализация) пишется и тестируется на моках
> без доступов — как сделано для Альфы.

## Связь с архитектурой

`prior-by` и `manual` — провайдеры из абстракции `BankProvider` (`app/config/banks.ts`).
Единый контракт разбора — `StatementNormalizer` (raw → `StatementItem[]`, см.
[`REFACTOR_PLAN.md`](REFACTOR_PLAN.md) «Единый интерфейс выписки»):

- **`prior-by` (путь №2)** — нормализация **сделана**: `normalizePrior` в `app/utils/priorStatement.ts`
  (операция Open Banking → `StatementItem`), покрыта тестами по живому sandbox-образцу. OAuth/DCR/consent-ядро
  **вынесено** в чистый `app/utils/priorOauth.ts` (URL/тела/claims + парсеры, без `node:crypto`; аналог
  `alfaOauth.ts`) под `tests/priorOauth.test.ts`; `scripts/prior-oauth-test.mjs` — тонкий потребитель.
  **Серверный движок опроса — собран (A5b, слайс 1):** `server/utils/priorFetch.ts` (`fetchPriorStatement`) —
  async `POST /accounts/{id}/transactions` → поллинг `GET …/{id}` (пока `BY.NBRB.Resource.NotCreated` → ждём и
  повторяем, бюджет `PRIOR_POLL_MAX_ATTEMPTS`) → `normalizePrior`; чистые билдеры путей/классификатор статуса
  (`buildPriorResourceCreatePath`/`PollPath`/`classifyPriorPoll`) в `priorOauth.ts`, DI-транспорт, юнит-тесты
  (`tests/priorFetch.test.ts`). Проведён в `fetchBankStatement` (делегат `deps.fetchPrior`).
  **Connect-поток — собран (A5b, слайсы 2a-2d):** подписчик `server/utils/priorJwt.ts` (`signPriorJwt` — RS256
  через `node:crypto`, зеркалит `signJwt` recon-скрипта) + оркестрация `server/utils/priorConnectStart.ts`
  (`buildPriorConnectUrl`: токен Б → `POST /accountConsents` → подписанный `request`-JWT → authorize-URL;
  `priorConnectConfigFromEnv` fail-closed) + диспетчер по провайдеру в `bankConnectStart`/`bankConnectCallback`
  (гейты и подписанный state — общие с Альфой; обмен кода у Приора идёт **по настроенному методу**
  — Basic-заголовок или подписанный `client_assertion`, см. «Способы аутентификации»; отсутствующий
  `refresh_token` допускается) + пикер банка в `BankConnectCard.vue`. Env —
  `PRIOR_OAUTH_{CLIENT_ID,CLIENT_SECRET,REDIRECT_URI,AUDIENCE,PRIVATE_KEY,KID,API_BASE,AUTHORIZE_BASE,AUTH_METHOD}`
  (`AUTHORIZE_BASE` — только при крипто-шлюзе, см. «СКЗИ» ниже; `CLIENT_SECRET` — только при
  `client_secret_basic`).
  **Автоопрос ВКЛЮЧЁН в коде:** `prior-by` в `POLLABLE_PROVIDERS` (`server/queue/cron.ts`). Обе
  причины, по которым он раньше был выключен, закрыты:
  (1) лимитер A8 считал ЗАДАЧИ из расчёта «1 задача ≈ 1 запрос» (верно для Альфы), а задача Приора —
  до 10 HTTP → у Приора теперь свой бюджет **в запросах** (`providerJobRate`); (2) задача Приора
  держала слот `bank-fetch` весь цикл create+poll, блокируя выборки Альфы → у него отдельная очередь
  `bank-fetch-prior` со своими слотами (`QUEUE_PRIOR_CONCURRENCY`).
  ⚠ «Включён» ≠ «работает»: таймер опроса живёт за `CRON_REAL_POLL` (по умолчанию **выключен**), а без
  банк-кредов владельца и подключённого счёта опрашивать нечего. Подключение **без выбранного номера
  счёта** (#407) не опрашивается сознательно — у банка нет такого номера, задача падала бы вечно.
  **Осталось:** живой sandbox-прогон на кредах владельца (в т.ч. `--auth-method private_key_jwt`)
  и **прод-СКЗИ** (issue #41 — без BY-крипто TLS-шлюза прод-хост `:9345` недостижим;
  инфраструктура, кодом не решается). Прод-метод аутентификации (#444) — **сделан**. Sandbox
  `:9344` работает обычным TLS и не требует ни того, ни другого.
- **`manual` (путь №1)** — нормализация **сделана** для **двух форматов** (диспетчер
  `app/utils/manualImport.ts` → `detectManualFormat`/`normalizeManualStatement`):
  1. **`***** ^Type=`** (Приор/Альфа-выгрузка) — `normalizeClientBank` (`clientBankStatement.ts`).
     Проверено и на реальных `Type=4`-файлах: BYN-дефолт для старых 13-значных BY-счетов и фолбэк
     ключа дедупа `Num|DocDate`, когда в выгрузке нет `DocID` (**#19**).
  2. **`1CClientBankExchange`** (обмен 1С «Клиент-банк», версии 1.01–1.03) — `normalizeOneC`
     (`oneCExchange.ts` парсер + `oneCStatement.ts` нормализатор): направление по «наш счёт =
     плательщик/получатель», валюта из кода счёта (RU 20-знач `810`→RUB и т.п. / BY→BYN), дедуп
     `Номер|Дата`. Универсальный бухгалтерский формат 1С (РФ+РБ) — **#21**. Обезличенный образец —
     `tests/fixtures/1c-exchange/demo-1c.txt`.
  Осталось — UI-загрузка файла и остаточный рефактор парсера `***** ^Type=` (**#19**).

> **Дедуп/идемпотентность:** ключ операции — `account|docId`, где для Приорбанка `docId = transactionId`.
> Дедуп корректен, пока Приорбанк отдаёт **стабильный и уникальный** `transactionId` в разрезе счёта
> (подтвердить на проде; при переиздании id банком возможны дубли/потери). Для Альфы `docId` — учётный
> номер документа. При отсутствии `transactionId` ключ **не** схлопывается в `account|` (#430 C1):
> `dedupKey` падает на контент-сигнатуру (хеш суммы/валюты/даты/направления/назначения/счёта
> контрагента) — операции без id остаются различимы.
