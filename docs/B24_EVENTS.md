# События и авторизация Bitrix24 (установка, удаление, брокер событий)

> Last reviewed: 2026-09-30

Как приложение учитывает авторизацию портала, обрабатывает установку/удаление и
проверяет подлинность входящих событий Bitrix24. Здесь — **доменное ядро**
(чистые функции `app/utils/b24Events.ts` + типы `app/types/b24Events.ts`,
покрыты тестами `tests/b24Events.test.ts`) и контракт для будущего **backend**,
который владеет HTTP-транспортом и хранилищем токенов.

> Эталон — соседний backend `bx-synapse` (рабочая интеграция с Б24): тот же
> подход (`tokenStore`/`b24Install`/`b24EventAuth`/`b24Form`). Мы переносим
> **проверенную модель**: чистую логику держим во `frontend` (переносима в
> backend без переписывания — конвенция `CLAUDE.md`), транспорт реализует backend.

## Зачем это нужно

Тиражное приложение Б24 получает события **исходящими вебхуками** на свой URL:

- `ONAPPINSTALL` — сразу после успешной установки на портал. В нём приходят
  OAuth-данные (`access_token`/`refresh_token`) **и** `application_token` — общий
  секрет, которым подписаны все последующие события. Его нужно **сохранить**.
- `ONAPPUNINSTALL` — при удалении приложения. OAuth-данных в нём уже нет (права
  отозваны), поэтому **единственный** способ убедиться, что вебхук пришёл от Б24,
  а не от злоумышленника, — сверить `application_token` с сохранённым.
- **CRM-события удаления** (`ONCRMDEALDELETE`/`ONCRMCOMPANYDELETE`/`ONCRMDYNAMICITEMDELETE`,
  `B24_DELETION_EVENTS`, scope `crm`) — для сверки СП-леджера распределений (#109, §9.2
  `PROCESSING.md`). Биндятся `/install` тем же батчем, что и lifecycle-события
  (`B24_ALL_BOUND_EVENTS`), **безусловно** (робастно к пони/повышению тарифа: на тарифе без
  смарт-процессов `ONCRMDYNAMICITEMDELETE` просто не фаерится). Эндпоинт **верифицирует
  `application_token`** (fail-closed, как uninstall — OAuth в пакете нет) и кладёт `DeletionJob`
  в отдельную очередь **`b24-deletions`** (без синхронного фолбэка — пропущенное восстанавливается
  ручной кнопкой «пересчитать»). Классификация вида (наш СП vs инвойс vs other) — в консьюмере, где
  доступен SP-конфиг портала. Само `reconcile` — за транспортом леджера (сейчас логирует).
- `ONAPPUSERREADY` — портал создал (или снова включил) **служебного пользователя приложения**:
  техническую учётную запись с именем приложения, которой нет в списке сотрудников и которую не
  отдаёт `user.get`. Узнать её id можно **только** из этого события (отдельного метода нет).
  На неё ставятся новые элементы смарт-процессов «Платежи» и «Распределения» (решение владельца
  2026-09-29); где события нет — на установившего. Разбор — раздел «Служебный пользователь» ниже.

Подробности контракта — официальная дока:
[OnAppInstall](https://apidocs.bitrix24.ru/api-reference/common/events/on-app-install.html),
[onAppUninstall](https://apidocs.bitrix24.ru/api-reference/common/events/on-app-uninstall.html),
[ONAPPUSERREADY](https://apidocs.bitrix24.ru/api-reference/common/events/on-app-user-ready.html),
[Системный пользователь](https://apidocs.bitrix24.ru/settings/system-user.html),
[Безопасность в обработчиках](https://apidocs.bitrix24.ru/api-reference/events/safe-event-handlers.html).

## Учёт авторизации (per-portal)

Backend хранит по каждому порталу запись `PortalCredentials`
(`app/types/b24Events.ts`), ключ — `memberId` (стабильный id портала):

| Поле | Назначение |
|---|---|
| `memberId` | Первичный ключ портала |
| `domain` | Хост портала (`*.bitrix24.*`) |
| `applicationToken` | **Подпись событий.** Хранить открытым, **write-once** |
| `accessToken` | Короткоживущий токен REST (~1 ч) |
| `refreshToken` | Продление доступа. Хранить **зашифрованно** (не plaintext) |
| `expiresIn` | TTL access-токена (Б24: 3600 с) |
| `clientEndpoint`/`serverEndpoint` | База REST портала / сервер обновления токена |

Правила (как в `bx-synapse`, реализация backend — issue #35):

- **`refresh_token` — зашифрованно** (AES-256-GCM на backend), не как в legacy
  (plaintext на ФС). Тем же ключом он шифруется **и в пакете очереди** (`register`-джоба
  несёт `refreshTokenEnc`, не clear) — через Redis в открытом виде не ходит; консьюмер
  расшифровывает и пишет `saveToken`. `application_token` хранится открытым — он не даёт
  доступа к API, только подтверждает подлинность вебхука.
- **Удаление приложения → полная очистка (политика).** Любой легитимный `ONAPPUNINSTALL`
  стирает всё, что связано с порталом (строка `portal_tokens`, **банковские токены `bank_tokens`**,
  `portal_app_rating` **и** служебные сторы
  `import_result`/`import_batch`/`metrics_counter` по `member_id`; дедуп дел и разнесение живут в B24,
  локального стора нет — #259); флаг `CLEAN` не смотрим — удалили приложение, значит не
  храним по нему ничего. ⚠ Банковские креды здесь не формальность: удаление сносит их тем же
  нелокируемым `DELETE`, что и кнопка «Отключить», и обновление токена, вернувшееся из банка уже
  после этого, **не воссоздаёт строку** — обновление UPDATE-only, создавать подключение вправе
  только OAuth-колбэк (#505). Иначе портал, удаливший приложение, оставил бы нам живые креды к
  своему банку. Очистку делают **обе** ветки `deletePortal` (консьюмер очереди и
  синхронный фолбэк роута `/api/b24/events`) — онлайн-события Б24 не ретраятся, второго шанса нет.
- **`application_token` — write-once:** первый легитимный `ONAPPINSTALL` его
  вписывает, повторные события **не затирают** (в БД — `COALESCE(NULLIF(...))`).
  Write-once должен быть **атомарным** на уровне БД (idempotent к конкурентным
  install-событиям) — иначе повторный `ONAPPINSTALL` с другим токеном перехватит
  портал. Подлинность самой установки держит привязка к OAuth-гранту (#162, ниже).
  ⚠ Удаление, пришедшее раньше, чем установка успела записаться (регистрация ещё в очереди),
  проверить не по чему — сохранённого токена нет, — и оно получает 503; Битрикс24 его не повторяет.
  Так было и до #757 на порталах без env-токена (весь Маркет), теперь — везде. Окно — время
  разбора очереди `b24-events`, то есть секунды.
- **`expires_in` на wire — строка** (form-encoding не несёт типов): `parseBracketForm`
  отдаёт `"3600"`, приведение к числу — на стороне backend при сохранении.
- **Refresh access-токена** — по `isAccessTokenExpired` (`app/utils/alfaOauth.ts`,
  тот же приём с запасом 60 с): `POST {server_endpoint}/oauth/token`,
  `grant_type=refresh_token`, креды **в теле** запроса (не в URL — защита от логов).
- `issuedAtMs` ставит backend в момент получения токена (`Date.now()`), не при
  разборе — иначе проверка истечения бессмысленна.

`extractPortalCredentials(installEvent)` собирает `PortalCredentials` из auth-блока
события (без `issuedAtMs` — его ставит транспорт).

## Брокер событий (диспетчеризация + проверка подлинности)

Backend принимает все вебхуки одной точкой входа (`POST /api/b24/events`) и
прогоняет их через чистое ядро:

1. **Разбор wire-формата.** Б24 шлёт тело как `application/x-www-form-urlencoded`
   с PHP-скобками (`auth[member_id]=…`, `data[VERSION]=…`), а **не** JSON из доков.
   `parseBracketForm(rawBody)` восстанавливает вложенный объект той же формы, что
   разбирают `parse*Event`.
2. **Проверка подлинности (fail-closed).** `appTokenVerdict({ isInstall, incoming,
   storedToken })` → `accept` | `forbidden` | `unconfigured`:
   - на установке **первый** непустой токен бутстрапит доверие (пустой → `forbidden`,
     отсекаем зонды); подлинность самой установки держит привязка к OAuth-гранту (#162, ниже);
   - на прочих событиях ожидаемый токен — сохранённый в БД; его нет → `unconfigured`
     (портал неизвестен → отказ);
   - сверка — **constant-time** (`safeEqual`), без утечки по таймингу.

   ⚠ Переменной окружения `B24_APPLICATION_TOKEN` **больше нет** (#757, решение владельца
   2026-09-27). Она дублировала привязку к гранту, а документы называли её обязательной для
   одного портала — довод «знающий URL вебхука установит произвольный `member_id`» закрыт
   привязкой: поддельной установке нужен действующий refresh-токен нашего `client_id`.

   Backend отдаёт коды: `accept` → обработать, `forbidden` → **403**,
   `unconfigured` → **503**.

   **Привязка `member_id` к OAuth-гранту (#162).** `application_token` — секрет **уровня приложения**
   (его получает каждая установка этого приложения), поэтому даже при верном токене `member_id` остаётся
   **клиентским**: владелец чужого портала может прислать установку с `member_id` жертвы + своим OAuth-грантом
   и отравить `member_id` жертвы. Перед записью `register` `handleEventRequest` зовёт инъектированный
   `bindInstallMember` (обёртка над `verifyInstallMember`):
   **рефрешит присланный `refresh_token`** на фиксированном `oauth.bitrix.info/oauth/token/` и сверяет
   **authoritative** `member_id` из ответа с заявленным. Не совпал / поддельный грант (`invalid_grant`/
   `invalid_token`/`expired_token`) → **403**; сеть / `wrong_client` / нет `member_id` в ответе → **503**
   (fail-closed — установка **не** пишется; B24 online-события не ретраит → восстановление = переустановка).
   Рефреш **ротирует** токен ⇒ храним **возвращённый** грант, а не присланный. Гейт на `B24_CLIENT_ID/SECRET`:
   без них рефреш невозможен в принципе ⇒ установка **отклоняется (503)** — после #757 привязка
   единственная проверка установки, и без неё принимать её нельзя. Это
   **осознанное исключение** из «весь B24 через jssdk»: SDK-рефреш выбрасывает `member_id` из ответа, а
   привязка его требует — потому один сырой POST (хост фиксирован → нет SSRF, секреты в теле, таймаут).
3. **Решение → очередь → консьюмер (эндпоинт в БД не пишет).** `processB24Event`
   только **верифицирует** (шаг 2, чтение сохранённого токена для uninstall) и
   возвращает `B24EventResult` с `action`:
   - `register` (ONAPPINSTALL) — `action.credentials` для сохранения;
   - `unregister` (ONAPPUNINSTALL) — стереть портал **всегда** (флаг `CLEAN` не смотрим —
     удалили приложение, значит не храним по нему ничего);
   - `system-user` (ONAPPUSERREADY) — записать id служебного пользователя (см. раздел ниже);
   - нет `action` — событие не наше / отказ (200/403/503 по вердикту).

   `handleEventRequest` **кладёт `action` пакетом в очередь `b24-events`** (`refresh_token`
   шифруется перед Redis — в открытом виде через брокер не ходит), а **консьюмер**
   (`handleEventJob`) — единственный писатель: регистрирует портал (`saveToken`, write-once
   `application_token`) или удаляет (`deleteToken`). В норме приём быстрый, запись асинхронная и
   ретраится BullMQ (attempts+backoff; исчерпание → failed-set, восстанавливается вручную).

   **Гард порядка (#77).** Записи применяются идемпотентно, но без гарантии порядка, поэтому «зависший»
   `register` (ретрай install после более свежего uninstall) мог бы воскресить удалённый портал. Защита —
   **монотонная метка `eventTs`** (время события B24) + таблица-тумбстоун `portal_tombstone`: `deleteToken`
   пишет `(member_id, deleted_ts)`, а `saveToken` не пишет поверх равного-или-новее тумбстоуна. Настоящий
   reinstall (ts новее) проходит и чистит тумбстоун. Тот же гард — на синхронном фолбэке приёма.

   ⚠ **Тумбстоун защищает только путь УСТАНОВКИ (#510).** Рефреш токена — второй писатель в ту же
   строку, и раньше он ходил тем же `saveToken`, поэтому мог воскресить портал, который нас удалил.
   Окон было два: рефреш, прочитавший тумбстоун до деинсталляции, и рефреш, стартовавший ВНУТРИ неё
   (тумбстоун писался после удаления строки — теперь до). Закрыто не тумбстоуном, а разделением
   прав: рефреш зовёт **UPDATE-only** `updatePortalTokenSecrets`, который после `DELETE` просто не
   находит, что обновлять. ⚠ Перечит под advisory-локом окно сужал, но не закрывал — между ним и
   записью стоит сетевой POST на OAuth-сервер с потолком 15 с.

   **Онлайн-события Б24 не ретраятся** (`event.bind` — «никакого второго шанса», см. доку
   [«Концепция обработки событий»](https://apidocs.bitrix24.ru/api-reference/events/index.html);
   повторная доставка есть только у офлайн-событий `event.offline.*`, которые мы не используем).
   Поэтому если очередь недоступна (Redis нет/упал), `handleEventRequest` **синхронно пишет в БД
   тем же токен-стором** (фолбэк) — иначе установка потерялась бы безвозвратно. Нормальный путь —
   очередь; фолбэк — только когда брокер недоступен (взаимоисключающи, двойной записи нет).
   Redis желателен (async-пайплайн: воркеры/крон), но при его отсутствии приём событий не падает.

### Служебный пользователь приложения (`ONAPPUSERREADY`)

Решение владельца 2026-09-29: новые элементы смарт-процессов ставятся на служебного пользователя
приложения, а где его нет — «везде человек, который всё установил», то есть владелец сохранённого
токена. Термин: документация Битрикс24 называет его **системным** пользователем приложения, у нас
он «служебный» — это одно и то же. Новых прав приложение не просит: событие из базового набора
(scope «базовый» в документации события). Как это устроено и где держит:

- **Подписка — сами, на установке, и best-effort.** Документация обещает, что обработчик
  «регистрируется автоматически для любого приложения с URL установки», но куда он идёт, не говорит.
  Вариантов два, и какой из них настоящий — **не замерено**: адрес УСТАНОВКИ — у нас это
  пререндеренная страница `/install`, которой nginx на POST отвечает тем же HTML с кодом 200
  (`error_page 405 =200`, это в `nginx.conf`), то есть событие было бы «доставлено» без следа; либо
  адрес обработчика событий из формы регистрации приложения — `…/api/b24/events` (`DEPLOY.md`).
  Поэтому `/install` отдельным вызовом делает `event.bind ONAPPUSERREADY` на `/api/b24/events` —
  **до** `installFinish` (событие приходит по завершении установки). ⚠ Чужой обработчик этого
  события установка **не снимает**, в отличие от `ONAPPINSTALL`/`ONAPPUNINSTALL` (находка ревью #783):
  им может оказаться тот самый автоматический, который документация обещает переносить вместе с
  конфигурацией приложения, а лишняя доставка безвредна — задача с тем же id второй раз не ставится,
  запись повторяет то же значение. Наш уже стоит — исход «уже подписано». Отдельным вызовом, а не в
  общем батче: там отказ роняет установку, а здесь он ожидаем — незнакомое порталу событие по
  документации `event.bind` даёт `ERROR_EVENT_NOT_FOUND` (на живом портале не замерено). Исход —
  строка «Событие о служебном пользователе» в диагностике: «ok», «уже подписано», «недоступно на
  этом портале» (только на этот код) или «подписаться не удалось» (любой другой отказ ничего не
  говорит о самом портале). ⚠ Строка показывает **подписку**, а не доставку: событие придёт после
  `installFinish`, и дошло ли оно — видно только в логе `backend` (см. «Как проверить» ниже).
- **Проверка — сохранённым токеном приложения**, как у всех событий, кроме установки. Тонкость в
  порядке: по документации оба события вызываются при завершении установки, а установка
  записывается только после сетевого похода роута на сервер авторизации (#162), — так что событие
  **может прийти раньше**, чем есть с чем сверять. Порядок доставки двух событий не документирован и
  не замерен. Отказать нельзя (онлайн-события не повторяются), ждать в роуте тоже нельзя
  (если портал шлёт события по одному, он ждал бы нашего ответа, а мы — его следующего события).
  Поэтому в очередь едет **sha256-отпечаток** токена (сам токен в Redis не едет), а консьюмер сверяет
  его с токеном, который лежит в базе **в момент записи**, — ВСЕГДА, даже если роут уже сверил: между
  ними могут уложиться удаление и мгновенная переустановка (находка ревью). Первый взгляд — через
  3 с (замерено на настоящем BullMQ: без задержки первая попытка проигрывала установке каждый раз и
  стоила строки о повторе в логе на каждую установку), дальше повторы 5+10+20+40+80 с
  (`SYSTEM_USER_RETRY_OPTS`), на последней попытке тихий отказ `expired`, а не упавшая задача
  (исчерпанная легла бы в счёт падений очереди и будила бы оператора). Роут отвечает **403** сразу,
  если токен у нас есть и не совпал.
  ⚠ Это ЕДИНСТВЕННЫЙ путь, по которому в очередь попадает ещё не проверенное событие, поэтому у него
  **потолок**: не больше `MAX_DEFERRED_CLAIMS_PER_MINUTE` (30) несверенных заявок в минуту на весь
  сервис (счётчик в Redis). Иначе поток подделок с выдуманными порталами стал бы потоком задач в
  очереди установок с одним исполнителем по порядку. Настоящих заявок — по одной на установку; сверх
  потолка — 503 и мягкая потеря (элементы на установившем), в лог одна строка в минуту. Ещё три
  ограничителя того же пути (ревью безопасности #783): **форма полей проверяется до всего остального**
  (`member_id` и токен — буквы, цифры, `_`/`-` и не длиннее 64/128; домен — не длиннее 253 и без
  пробелов и управляющих символов, но НЕ проверка имени хоста: по нему на этом пути никуда не ходят,
  а строгий шаблон молча терял служебного пользователя коробки с `_` или кириллицей в адресе;
  `ts` — цифры),
  иначе поддельный запрос складывал бы мегабайты в ключи и данные Redis, а перевод строки в
  `member_id` подделывал бы целые строки лога; **предел размера задачи** в BullMQ (`sizeLimit`); и
  **отпечаток токена в id задачи**, чтобы подделка с тем же порталом и `ts` не заняла id настоящей.
  Счётчик потолка ждёт Redis не дольше 1,5 с: при недоступном Redis клиент очереди не отказывает, а
  ждёт. В логах непроверенная заявка названа хешем портала, а не `member_id`.
  ⚠ **Без Redis** (очередь выключена или лежит) — как у установки: заявка, уже сверенная роутом,
  пишется в базу синхронно; несверенную проверить позже негде, и она получает 503 — та же мягкая
  потеря.
- **Храним только id** — колонка `portal_tokens.system_user_id` (0 = не знаем), писатель
  `setSystemUserId`, **UPDATE-only** и ровно одна колонка: событие, опередившее установку, не
  создаёт регистрацию без токенов, опоздавшее событие удалённого портала ничего не воскрешает.
  ⚠ Долгоживущую авторизацию служебного пользователя событие тоже приносит, и **мы её не берём**:
  нужен ответственный, а не ещё один вечный ключ к порталу клиента. Это осознанное отступление от
  рекомендации документации — она советует сохранить `data.refresh_token` и вести фоновые вызовы под
  служебным пользователем; мы ведём их, как и прежде, токеном установившего и лишь ставим
  ответственного. Цена названа: если служебного пользователя однажды решат сделать отправителем
  сообщений вместо бота, его токены придётся получать заново — событие приходит только при установке.
- **Где события нет — установивший.** Локальным приложениям событие не отправляется (так сказано в
  документации события), то есть у клона на своём сервере так будет всегда; порталы, установленные
  до этой правки, пришлют его только при переустановке; портал, который этого события не знает,
  не пришлёт никогда. «Установивший» — это **отсутствие поля**: документация `crm.item.add` называет
  умолчание `assignedById` прямо — «идентификатор пользователя, который вызывает метод», а вызываем
  мы его сохранённым токеном установившего. Отдельного вызова ради того же ответа нет.
- **«Нет поддержки» второго вида — портал не принимает служебного пользователя ответственным.**
  Заранее это не замерить, поэтому ловится ответом: **создание элемента** (`crm.item.add`) со
  служебным пользователем отказано кодом неверного значения поля (`CRM_FIELD_ERROR_VALUE_NOT_VALID`)
  или запрета (`ACCESS_DENIED`) — оба из документации метода — → та же запись повторяется без поля,
  то есть на установившем. Повтор безопасен: писатели find-or-create по маркеру. ⚠ Коды —
  **разрешённый** список, а не «всё, кроме временных» (находка ревью #783): прежний пропускал коды,
  которые SDK ставит на сбой транспорта (`NETWORK_ERROR`, `REQUEST_TIMEOUT`, `ECONNRESET`), и один
  сетевой сбой переводил портал на установившего. Какой код портал вернёт на деле, не замерено;
  окажется другим — запись упадёт честно, с текстом портала в логе. Отказ запоминается только если
  повтор прошёл (это и доказывает, что мешал ответственный), ненадолго — 10 минут — и на **пару**
  «портал + служебный пользователь»: память живёт в контейнерах `worker`, а новый служебный
  пользователь записывается событием в `backend`, так что сбрасывать её событием было бы нечем —
  новый id просто даёт новый ключ (`withElementResponsible` в `server/utils/systemUser.ts`).
- **Ставится только при создании, и спрашивается только тогда.** Найденный по маркеру элемент
  ответственного не меняет и не спрашивает — сбой чтения базы не ломает дозапись колонок
  существующего элемента (находка ревью). Элементы, записанные до правки или до прихода события,
  остаются на прежнем.
- **Тесты:** разбор события и формы полей — `tests/b24Events.test.ts`; роут (сверка, потолок,
  дедлайн Redis, 403/400/503) — `tests/b24EventsHandler.test.ts`; сверка в воркере и выбор
  ответственного (коды отказа, отказ не на создании, память на пару) — `tests/systemUser.test.ts`;
  метод отказавшего вызова — `tests/portalError.test.ts`;
  шов с настоящим воркером (все четыре пути создания и отложенная дозапись спрашивают одного
  ответственного) — `tests/liveHandlerDepsElementResponsible.test.ts`; подписка на установке (без
  снятия чужого обработчика, разные тексты отказа) — `tests/nuxt/install.nuxt.test.ts`.
- **Как проверить на портале.** Подписка — строка диагностики `/install` (выше). Доставка и запись —
  лог контейнера **`backend`** (обработчик событий живёт там, на крон-инстансе, а не в `worker`):
  приём `system-user member_id=… (queued)` либо `system-user portal=<хеш> unverified (queued)`, если
  установка ещё не была записана; затем «служебный пользователь записан (id N)» — или отказы «НЕ
  прошло сверку токена приложения» / «НЕ записан — установки нет». Результат — ответственный нового
  элемента «Платежи» в карточке.

⚠ **Остаточный риск — сотрудник портала.** Проверка стоит на токене приложения, а его, судя по
документации `event.bind` («подписаться может любой пользователь»), может узнать любой сотрудник
портала с доступом к приложению: подписать СВОЙ обработчик на событие нашего приложения и прочитать
токен из присланного события. С ним он может выдать себя за служебного пользователя и стать
ответственным новых элементов — то есть увидеть платежи при правах «Свои». ⚠ Новой видимости это
не даёт: тот же сотрудник уже видит операции на экране приложения — «Последние операции» открыты
любому сотруднику портала (`/api/import/operations` не админский); добавляется лишь то, что элементы
встают на него в CRM. Тот же класс уже есть у удаления приложения (подделка стирает наши данные
портала) и не новый; проверять, что заявленный
пользователь действительно не виден в `user.get` (служебного, по документации, метод не отдаёт), мы
пока не стали — это ещё один непроверенный вызов. Не замерено.

⚠ **Не замерено** (замер коробки запрошен у владельца): дойдёт ли событие до нас на боевом портале;
примет ли `crm.item.add` служебного пользователя ответственным (не примет — сработает повтор без
поля выше) и как его покажет карточка; куда идёт автоматический обработчик и в каком порядке портал
шлёт `ONAPPINSTALL` и `ONAPPUSERREADY`; увидит ли
элементы на служебном пользователе НЕ-администратор, чей токен у нас лежит, — поиск по маркеру идёт
его правами, и при правах «Свои» промах дал бы второй элемент той же операции (тот же класс, что у
дела на чужом ответственном, `PROCESSING.md` §2).

### Защита REST-вызовов к порталу (SSRF)

`client_endpoint` приходит **внутри события** (управляем злоумышленником), поэтому
перед REST-вызовом backend проверяет его `isSafeClientEndpoint(endpoint)`: только
`https://`, без loopback/private/link-local хостов. (DNS-rebinding ловится уже в
рантайме — чистая функция отсекает очевидные литералы.)

### Запуск backend (docker)

`docker compose up` поднимает `db` (Postgres) и `backend` (node-сервер с эндпоинтом).
Перед стартом задать в `.env` (шаблон — `.env.example`):

- `B24_TOKEN_ENC_KEY` — ключ шифрования refresh, **обязателен**, ровно **32 байта**: 64 hex-символа
  (`openssl rand -hex 32`) или base64, декодирующийся в 32 байта. Обрезанное значение (напр. 31 байт)
  → шифрование падает и установка не сохранит токен.
- `B24_CLIENT_ID`/`B24_CLIENT_SECRET` — из карточки приложения; нужны для refresh access-токена,
  `app.option` и **самой установки**: без них `ONAPPINSTALL` отклоняется (503, #757).

Эти значения валидируются **на старте** (`server/plugins/envCheck.ts` → чистая `checkBackendEnv`):
неверная длина ключа, отсутствие `DATABASE_URL` (и незаданные OAuth-креды — предупреждением) дают внятный
`[env] …`-лог сразу, а не падение в хендлере.

Таблицы `portal_tokens`, `portal_tombstone`, `import_result`, `import_batch`, `metrics_counter`,
`bank_tokens` и `portal_app_rating` создаются автоматически на старте (`server/plugins/migrate.ts`;
снятый `allocation_fact` дропается идемпотентным `DROP TABLE IF EXISTS`, §9.3 #6).
Адрес обработчика события для портала — `https://<домен-backend>/api/b24/events`.

### Живой прогон на портале Bitrix24 (проверено)

Прогон выполнен на двух порталах (`b24-rvai7u.bitrix24.ru`, `bel.bitrix24.by`) — обе строки легли в
`portal_tokens` с разными per-portal `application_token` и зашифрованным refresh (мультитенант-bootstrap
работает). Порядок:

1. **Публичный HTTPS backend.** Б24 шлёт события на публичный URL (`localhost` из compose недоступен):
   деплой за nginx-proxy (`https://<домен>/api/b24/events`) либо туннель (`cloudflared`/`ngrok`) в dev.
2. **Регистрация локального приложения.** Путь установки = `https://<домен>/install`, обработчик (iframe)
   = `https://<домен>/app`, права `crm,sale,im,imbot,documentgenerator,userfieldconfig,user_brief,placement` (источник — `B24_REQUIRED_SCOPES` в `app/config/b24.ts`; **`userfieldconfig` обязателен** — без него провижининг смарт-процессов молча отказывает, #408; **`imbot`** — без него сообщения в чаты идут от имени сотрудника, а не приложения, #496). Обработчик события **отдельно указывать
   не нужно** — `/install` сам биндит `ONAPPINSTALL`/`ONAPPUNINSTALL` (до `installFinish`). Проверить —
   панель «Диагностика» на `/install` (блок «События») или `event.get`.
3. **Установить** → в логах `[b24-events] INFO: ONAPPINSTALL member_id=…` + `bootstrapped`; строка в
   `portal_tokens` (роль/база в нашем прод-compose — **`app`**, не `postgres`):
   ```
   docker compose -f docker-compose.prod.yml exec db psql -U app -d app \
     -c "select member_id, domain, left(application_token,6)||'…', (refresh_token_enc <> '') from portal_tokens;"
   ```
4. **Удаление** приложения с «очистить данные» (`CLEAN=1`) → `ONAPPUNINSTALL` → строка портала исчезает.

**Грабли, пойманные на живом прогоне (учтены в коде/доках):**
- `NUXT_PUBLIC_SITE_URL` в проде **обязателен** (репо-переменная GitHub Actions → build-arg): без него
  фронт печёт пустой `siteUrl` и `/install` отказывается биндить относительный URL.
- `B24_APPLICATION_TOKEN=CHANGE_ME` из старого `.env.example` → 403 на установке. Снято вместе с переменной (#757).
- `B24_TOKEN_ENC_KEY` не 32 байта → шифрование refresh падает (теперь ловит `envCheck`).
- `docker-compose.prod.yml` на сервере обновляется **вручную** (Watchtower тянет только образы) — легко
  отстать на несколько PR; напр. старый compose требовал `B24_APPLICATION_TOKEN` через `:?`.
- Переустановка на тот же портал (тот же `member_id`) поверх старой записи не перезапишет write-once
  `application_token` — перед сменой регистрации чистим строку (`truncate portal_tokens` / `delete … where member_id=…`).
