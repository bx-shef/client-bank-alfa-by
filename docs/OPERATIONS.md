# Операции: пост-запускной runbook (#246)

> Last reviewed: 2026-08-14

Как понять, что приложение живо, где смотреть диагностику, что делать при типовых сбоях,
как откатиться и куда эскалировать. Дополняет [`DEPLOY.md`](DEPLOY.md) (как деплоить) и

## Что крутится в проде

Один образ, поднимается несколькими сервисами (`docker-compose.prod.yml`):

| Сервис | Что делает | Роль по env |
|--------|-----------|-------------|
| `app` | nginx: статика лендинга/iframe-UI + прокси `/api/*` → `backend:3000` | — |
| `backend` | Nitro: API (вебхуки B24, настройки, импорт, health) + **крон** + единственный воркер `b24-events` (install/uninstall — на одном инстансе ради порядка) | `QUEUE_WORKERS=0` (API+крон), миграция (дефолт `RUN_MIGRATION=1`) |
| `worker` (×N) | BullMQ-воркеры: `bank-fetch`/`file-parse`/`crm-sync` (масштабируемая обработка; `b24-events` тут **не** крутится) | `QUEUE_CRON=0`, `RUN_MIGRATION=0` |
| `db` | Postgres (токены порталов и банков, статус и итоги импорта, метрики, состояние попапа оценки) | — |
| `redis` | шина очередей BullMQ (сеть `queuenet`, `internal: true`) | — |
| `crypto-gw` | **выключен по умолчанию** (закомментирован). BY-крипто TLS-шлюз к проду Приорбанка: внутрь обычный HTTP, наружу СТБ 34.101.65. Отдельный образ, своя сеть `cryptonet`, без host-порта. Устройство образа, гейты и специфичные отказы — [bx-shef/bee2-tls-gateway](https://github.com/bx-shef/bee2-tls-gateway) (⚠ формат лога без пути и allowlist путей держатся ТАМ, не у нас); включение и типовые сбои у нас — ниже в этом документе | — |

Обновления образов подхватывает хостовый **Watchtower** из GHCR (см. `DEPLOY.md`). Крон и
миграцию гоняет **ровно один** инстанс (`backend`); воркеры масштабируются `--scale worker=N`.

## «Живо ли» — health и первичная проверка

1. **Liveness backend:** `GET https://<DOMAIN>/api/health` → `{status:"ok", time, commit, commitUrl}`.
   `commit` = сборка, которая реально крутится (тот же SHA, что в подвале лендинга) — так видно,
   что Watchtower подтянул нужный образ. Без секретов; на нём же docker `healthcheck` backend'а.
   ⚠ **`/api/health` — только liveness процесса.** Он **не** проверяет Postgres, Redis и воркеры:
   при упавшем `db`/`redis` health остаётся **зелёным**, а приложение при этом мёртво (crm-sync
   падает, токены не читаются). Для проверки зависимостей — `/api/ready` (ниже).
2. **Readiness backend:** `GET https://<DOMAIN>/api/ready` → `200 {ready:true, status:"ok", checks:{db, redis}}`;
   при проблеме — `503` с `status:"down"` (Postgres недоступен — не работает ничего) или `status:"degraded"`
   (db жив, но настроенный Redis недоступен — API и события B24 работают через синхронный фолбэк, а
   импорт/опрос/crm-sync стоят). **Прощупывает Postgres** (`SELECT 1`) **и Redis** (`PING`, если очереди
   включены; `redis:null` = очереди выключены, не ошибка; таймаут пинга не даёт пробе зависнуть при
   недоступном Redis). Без секретов и без глубины очередей. Это то, что стоит вешать на аптайм-мониторинг
   (и кандидат для docker `healthcheck` вместо liveness). `db:false` → строка «Postgres упал»;
   `redis:false` → **«Redis недоступен»** (PING не прошёл). ⚠ Redis, живой но забитый (память/AOF), PING
   **проходит** → `redis:true` — это `/api/ready` не ловит, см. строку «Redis деградировал» (`logs redis`).
3. **Лендинг/статика:** `GET https://<DOMAIN>/` отдаёт 200 (nginx `app`).
4. **Контейнеры:** `docker compose -f docker-compose.prod.yml ps` — все `Up`/`healthy`.
   `backend` unhealthy → смотреть `docker compose logs backend` (частые причины — env-валидация,
   недоступный Postgres/Redis; см. ниже).

## Диагностика очередей

Импортёр — очередь-driven, поэтому «здоровье» = очереди разгребаются, а не растут.

- **Консольно (для оператора-админа сервера):** `bash scripts/queue-stats.sh` — читает
  `GET /api/queues` по токену `B24_APPLICATION_TOKEN` заголовком `X-Check-Token` (nginx снаружи
  `deny all`; токен не в URL-логах). Нужно задать `B24_APPLICATION_TOKEN` сильным значением.
  **Токен не набирать инлайном** (`B24_APPLICATION_TOKEN=… ./scripts/…` попадает в history и `ps`) —
  подтянуть из деплой-`.env`: `set -a; . ./.env; set +a` перед запуском.
- **В браузере (сотрудник):** страница `/queues` (за логином оператора, `PUBLIC_PAGE_BASIC_AUTH_PASS`
  + `SESSION_SECRET`) → живой график по `GET /api/ops/queues`. `?preview=1` — синтетика для скриншотов.
- **Что нормально:** `waiting`≈0 в покое; всплеск при опросе/импорте, затем разгреб. `failed` копится
  только на реальных сбоях (кап `removeOnFail` 5000).

### Сигналы, которые НЕ видны в дефолтных счётчиках

- **Учёт итогов ручных загрузок (#417).** Запись `import_batch` — best-effort: сбой не роняет джобу
  и потому невидим в `failed`. Grep: `import_batch save failed` / `import_batch error save failed`
  (в CRM записано, но экран сотрудника итога не дождётся) и `[retention] import_batch sweep failed`
  (записи с именами файлов перестали чиститься по TTL).

- **Падение джоба/воркера (#78).** У каждого BullMQ-воркера навешаны логи событий (без ПДн —
  только очередь/попытка/текст ошибки, **без** `job.data` и сырого jobId, где может быть номер счёта):
  - `[queue-job-failed] queue=<q> attempt=N/M FINAL error=…` — джоб **исчерпал ретраи** (loud, `error`);
    это то, на что вешать алерт (grep `queue-job-failed`). `[queue-job-retry] …` — промежуточная попытка
    (`warn`, ожидаемо).
  - `[queue-worker-error] queue=<q> error=…` — ошибка **уровня воркера** (обрыв Redis-соединения и т.п.).
  Без этих строк упавший воркер/джоб был бы **невидим** (спаны OTel — no-op без коллектора). Пусто в
  логах при растущем `failed` = смотреть глубже (сам процесс лога/воркера мог упасть — см. крэш-луп ниже).
- **Насыщение rate-limiter'а (A8).** Живой опрос Альфы капнут глобально (`QUEUE_FETCH_RATE_MAX`/
  `_DURATION_MS`, дефолт 100/60с). При превышении BullMQ **откладывает** лишние fetch-джобы (не
  теряет, попытку не жжёт) — на графике это рост `waiting`/`delayed` на `bank-fetch`, **неотличимый**
  от обычного бэклога. **Явный сигнал в логах:** крон после каждого опроса пишет
  `[queue] bank-fetch backlog N ≥ M — likely A8 rate-limit saturation …`, когда бэклог
  (`waiting+delayed`) переходит порог `QUEUE_FETCH_SATURATION_THRESHOLD` (дефолт 200) — так упор в кап
  виден по grep'у, а не только по графику. Поднимать лимит только если Альфа поднимет свой.
- **Крон не на том инстансе.** Крон/демо-нагрузку/keep-alive **и единственный воркер `b24-events`** поднимает
  только инстанс с `QUEUE_CRON=1` (по умолчанию `backend`). Два таких инстанса → дубли fetch-джобов. Проверить:
  `QUEUE_CRON` ровно на одном. **Следствие:** если `backend` лежит, `worker`-контейнеры разгребают
  `bank-fetch`/`file-parse`/`crm-sync`, но **события установки/удаления приложения (`b24-events`) не
  обрабатываются** — масштабирование `worker` их не подхватит (по замыслу — один инстанс ради порядка
  install→uninstall). Живой `backend` для приёма установок обязателен.
- **Keep-alive токенов (#175).** Раз в сутки (`TOKEN_KEEPALIVE_HOURS`) крон рефрешит простаивающие
  порталы у истечения refresh (~180 д). Гейт на `B24_CLIENT_ID/SECRET` — без них в логах warning
  «token keep-alive disabled», и простаивающие порталы теряют авторизацию на 180-й день.

## Быстрая проверка стенда одним прогоном

```bash
cd /home/bitrix/bank-import
bash scripts/prod-doctor.sh bank-import.bx-shef.by
```

Проверяет по порядку: что поднято, что здорово (плюс рестарты и OOM), отвечают ли `/`, `/api/health`
и `/api/ready` изнутри сети, заданы ли ключевые переменные, нет ли в логах `[env]`/`[auth]`/финальных
падений задач, и снаружи — лендинг, health, **401 на `/api/ops/*` без cookie** и 404 на
несуществующем адресе.

Две вещи, ради которых он написан именно так:

- **значения переменных не печатаются**, только «задано» и длина. `docker compose config` печатает
  их в открытую, и однажды это уже привело к тому, что пароль оператора и ключ подписи уехали в
  переписку (пришлось менять оба);
- **пустой вывод не считается успехом**: если контейнеров нет или логи не читаются, скрипт говорит
  «судить не по чему», а не «жалоб нет». Тотальная авария не должна выглядеть зелёной строкой.

Скрипт ничего не чинит и не перезапускает — только смотрит. Что делать с найденным — ниже.

## Частые сбои и что проверять

| Симптом | Вероятная причина | Что делать |
|---------|-------------------|-----------|
| Health зелёный, но crm-sync падает, токены не читаются/не пишутся | **Postgres упал** после старта (health его не проверяет) | `docker compose ps db` (не `Restarting`?), `logs db`, `logs worker` (ошибки соединения/`token`). Поднять `db`: `docker compose -f docker-compose.prod.yml up -d db`. Data-loss риск при полном диске — см. строку про диск |
| REST/авторизация порталов массово падает, в логах ошибки **дешифровки** (не `expired_token`) | `B24_TOKEN_ENC_KEY` сменили **без** `B24_TOKEN_ENC_KEY_OLD` — refresh-токены зашифрованы прежним ключом (envCheck проверяет только длину, не совпадение) | Вернуть прежний ключ в `B24_TOKEN_ENC_KEY_OLD` (расшифровка пробует оба) → `up -d backend worker`. Штатная процедура — раздел «Ротация ключа шифрования». Если прежний ключ утерян — токены осиротели, все порталы переустанавливают приложение. Реактивный рефреш SDK это **не** чинит (это не протухший access) |
| `backend` «healthy», но токены не сохраняются; в логах `[env] …` | env-валидация (`envCheck`) нашла проблему (битый `B24_TOKEN_ENC_KEY`/плейсхолдер `B24_APPLICATION_TOKEN`/нет `DATABASE_URL`), но **процесс не падает** — работает вхолостую | envCheck **логирует и продолжает** (health зелёный, `ps` healthy — не обманываться). Грепнуть `logs backend` на `[env]`. Исправить `.env` → **пересоздать**: `docker compose -f docker-compose.prod.yml up -d backend` (именно `up -d`, а не `restart` — `restart` **не** перечитывает `.env`) |
| Установка/удаление приложения «не дошли» | Redis недоступен | Онлайн-события B24 **не ретраятся**, поэтому роут пишет в БД **синхронным фолбэком** — данные не теряются. Поднять Redis: `docker compose -f docker-compose.prod.yml up -d redis`; проверить `docker compose -f docker-compose.prod.yml logs backend` |
| `waiting` растёт, **fetch/import** не проходят (события — доходят) | Redis **жив, но деградировал**: полон/AOF не пишет (диск)/eviction | BullMQ требует `noeviction`; при упоре в память enqueue падает. Синхронный фолбэк есть **только** у `b24-events`, не у fetch/import. Освободить память/диск Redis, проверить `logs redis` на OOM/`MISCONF`. Затем перепроверить очереди |
| Очереди не разгребаются, `waiting` растёт | Нет `worker`-контейнера (или `QUEUE_WORKERS=0` везде) | Сначала отличить от крэш-лупа (ниже): `docker compose ps worker`. Если контейнера нет — backend при `QUEUE_WORKERS=0` пишет warning «this instance does NOT process …». Поднять: `docker compose -f docker-compose.prod.yml up -d --scale worker=N` |
| `waiting` растёт, `worker` есть, но в статусе `Restarting`/растёт restart-count | Воркер **крэш-лупит** (OOM на крупном `crm-sync`/`file-parse` держит файл в памяти) | `docker inspect <worker> --format '{{.State.OOMKilled}} {{.RestartCount}}'`. Если OOM — поднять лимит памяти сервиса или `QUEUE_CONCURRENCY` вниз. «Поднять воркер» тут **не** поможет — он уже поднят и циклится |
| Миграция БД не прошла: health зелёный, но записи падают `relation/column does not exist` | Ошибка миграции на старте (`migrate.ts` **логирует и не роняет**; `worker` стартует до завершения миграции) | Грепнуть `logs backend` на итог миграции/ошибку. Починить БД/права, перезапустить `backend` (миграция идемпотентна — повторный прогон безопасен) |
| Опрос банков «пустой», ничего не пишется | Нет подключённых счетов (`bank_tokens` пуст) или `CRON_REAL_POLL≠1` | Ожидаемо до подключения счёта (A7) и включения реального опроса. `CRON_REAL_POLL` default-OFF — включать осознанно |
| Кнопка «Опросить сейчас» отвечает 503 / 429 / 403 | 503 — `MANUAL_POLL_ENABLED≠1` (или нет Redis); 429 — кулдаун (`MANUAL_POLL_COOLDOWN_SEC`, дефолт 60с); 403 — не админ портала (#54) | 503: включить `MANUAL_POLL_ENABLED=1` осознанно (частота регулируется app-side). 429: подождать кулдаун. 403: жать может только админ портала |
| Операция ушла «не туда» / в чат ошибок «клиент не определён» | Компания-плательщик по счёту не найдена → `unmatched`. Пишем в **вашу** компанию с пометкой + чат ошибок (#91); если и ваша компания не найдена — не пишем | Проверить реквизиты контрагента (`RQ_ACC_NUM`/ИИК) и что ваша компания заведена с `isMyCompany='Y'` + нашим счётом. Неоднозначные/ручные исходы разнесения тоже в чат ошибок |
| REST к B24 падает `expired_token` | Протух access-токен портала | SDK рефрешит реактивно сам; при повторе — проверить `B24_CLIENT_ID/SECRET` (без них рефреш невозможен) |
| Опрос банка не идёт: `bank-fetch` копит `failed`, в логах `[queue-job-failed] queue=bank-fetch … FINAL` | **Банк не отвечает** (недоступен, 5xx, троттлит 429) либо протухли банк-креды | Отличать по тексту ошибки: сетевые/5xx — сторона банка, `invalid_client`/`unauthorized` — наши креды. Крутить `QUEUE_FETCH_RATE_MAX` **вверх нельзя** — упор в лимит банка усугубит. При затяжном инциденте снять нагрузку: `CRON_REAL_POLL=0` + `up -d backend` (ручная загрузка выписки при этом работает). Эскалация владельцу — банк-креды у него |
| Один портал стабильно падает на рефреше: `invalid_grant` / keep-alive пытается его рефрешить, пока строка не выпадет из near-expiry-полосы (несколько прогонов), потом сигнал тихо исчезает | **Портал отозвал грант**: приложение удалили в портале, или подписка кончилась (`PAYMENT_REQUIRED`) | Это **не наша авария** и чинится только на стороне портала — переустановкой приложения. Пер-портальные ошибки изолированы, крон не падает. ⚠ Если `invalid_grant` пошёл **массово по всем порталам** — смотреть не порталы, а `B24_CLIENT_SECRET`: скорее всего сменили его |
| После смены банк-кредов подключения не работают | `restart` **не перечитывает** `.env`; креды продублированы у `backend` **и** `worker` | `up -d backend worker` (оба!). ⚠ Смена `client_id` инвалидирует **сохранённые** `bank_tokens` — все счета придётся подключать заново; смена только `client_secret` сохранённые токены не ломает |
| `no space left on device` | Кончилась дисковая квота | Освободить **образы**: `docker image prune -a` + `docker builder prune` (**без** `--volumes`). **НИКОГДА** `docker system prune --volumes` — снесёт тома `redisdata`/Postgres (потеря очередей/данных). Логи контейнеров — усечь json-файлы (`truncate -s0 /var/lib/docker/containers/*/*-json.log`) или настроить `max-size`; `docker compose logs` их **не** освобождает. ⚠ При полном диске Postgres (WAL) и Redis (AOF) уже могли встать в read-only — после освобождения **перепроверить** `logs db`/`logs redis` и health |
| TLS истёк / сайт не открывается | acme-companion не обновил cert | Проверить DNS A-запись `DOMAIN`, логи `acme-companion`; DNS должен указывать на сервер. При повторных неудачах — лимит Let's Encrypt (5 дублей серта/неделю): не долбить renew, сперва починить DNS |
| Контейнер `app` (или backend) **unhealthy сутками**, в healthcheck `wget: can't connect to remote host: Connection refused`, при этом сайт открывается | Проверка ходила на `localhost`, который резолвится ещё и в `::1`, а nginx слушает `listen 8080;` — **только IPv4** | Сначала убедиться, что сервер и правда живой: `docker exec <c> wget -qO- http://127.0.0.1:8080/ \| head -c 100`. Отвечает — поломки нет, чинится обновлением compose (healthcheck переведён на `127.0.0.1`) и `up -d app`. Не отвечает — смотреть `logs app` на ошибку старта nginx и `docker exec <c> ss -ltnp` (кто и на чём слушает) |
| В логе бэкенда `[auth] operator zone is LOCKED — PUBLIC_PAGE_BASIC_AUTH_PASS is not set` | Пароль оператора не задан в проде | Служебная зона (`/queues`, `/api/ops/*`) **закрыта**: ни данных, ни входа. Задать `PUBLIC_PAGE_BASIC_AUTH_PASS` и `SESSION_SECRET` (`openssl rand -hex 32`) в `.env` → `up -d backend worker` (именно `up -d`: `restart` не перечитывает `.env`). ⚠ Если в логе старая формулировка `zone is OPEN` — на сервере **прежний образ**, и зона реально открыта наружу: обновить как можно скорее, до обновления считать `member_id` порталов утёкшими |
| Странные окна опроса/keep-alive, токены «протухают» раньше срока | Расхождение часов хоста | Сверить `date` на хосте с NTP — окна near-expiry/опроса и валидность TLS завязаны на системное время |

## Выкат мажора bullmq (разово, при обновлении 5.x → 6.x)

Watchtower обновляет контейнеры **не атомарно**: воркеры (`QUEUE_WORKERS`, их несколько) и cron
какое-то время работают на разных версиях над одним Redis. bullmq регистрирует свои Lua-скрипты под
именем `<скрипт>:<версия пакета>`, а раскладка ключей между 5.x и 6.x изменилась (в 6.x пауза больше
не перекладывает задачи из `wait` в `paused`, а только ставит флаг в `meta`). Задачи при этом **не
теряются** — смешанный флот просто по-разному видит паузу, — но окно лучше закрыть осознанно:

- либо остановить воркеры, дать выкатиться всем образам, поднять обратно;
- либо принять короткий период рассинхрона (мы паузой не пользуемся, поэтому практического эффекта
  нет — но знать про это надо, чтобы не искать «пропавшие» задачи).

⚠ Если на момент выката очередь **стояла на паузе**, поставленной версией 5.x, задачи из старого
ключа `paused` вернутся в работу только после `resume` — 6.x разгребает legacy-ключ именно там.

Блокеров нет: минимальная версия Redis осталась 5.0 (у нас `redis:7-alpine`), а legacy repeatable
jobs — единственное, что 6.x отвергает жёстко, — мы не используем (периодика на `setInterval`).

## Процедура отката

Сейчас `docker-compose.prod.yml` тянет образы GHCR по тегу **`:latest`** (жёстко в файле), обновления
подхватывает Watchtower. Пока тег не параметризован env — откат делается пином тега в compose:

1. Найти рабочий SHA: `GET /api/health` до сбоя (поле `commit`), либо список тегов в GHCR —
   `gh api "/orgs/bx-shef/packages/container/client-bank-alfa-by/versions" --jq '.[].metadata.container.tags[]'`
   (или в вебе: GHCR-страница пакета). CI пушит тег на каждый `main`.
2. **Сначала отключить Watchtower** для этих контейнеров (иначе за ~5 мин он перекатит пин обратно на `latest`
   прямо посреди отката): добавить каждому сервису в `docker-compose.prod.yml` метку
   `labels: [ "com.centurylinklabs.watchtower.enable=false" ]`. Метка применится тем же `up -d` на шаге 4.
3. В `docker-compose.prod.yml` заменить `…/client-bank-alfa-by:latest` и `…-backend:latest` на
   `:sha-<первые 7 символов>` (оба образа — `app` и `backend`/`worker` — на один и тот же SHA).
   ⚠ **Тег короткий.** `/api/health` отдаёт ПОЛНЫЙ 40-символьный `commit`, а CI тегирует образы как
   `sha-<7 символов>` (`type=sha,prefix=sha-`). Пин по полному хешу упадёт «manifest unknown» —
   ровно посреди инцидента. Брать первые 7 символов: `commit=abc1234def…` → тег `sha-abc1234`.
4. `docker compose -f docker-compose.prod.yml pull && docker compose -f docker-compose.prod.yml up -d`.
5. Проверить `GET /api/health` → `commit` == откатанный SHA.
6. **После выпуска фикса вернуть `:latest` и убрать метку** — контейнер с выключенным автообновлением
   перестаёт получать патчи.

> **Улучшение (#246):** параметризовать тег через env (`APP_IMAGE_TAG`, дефолт `latest`), чтобы откат был
> правкой `.env`, а не compose. Пока — правка compose.

Миграции БД **аддитивны и идемпотентны** (`server/plugins/migrate.ts`), откат образа их не ломает
(старый код просто не использует новые колонки). Данные при откате образа не теряются.

## Диск / TLS / алерты

- **Приватность/retention:** выписки у себя не храним; содержимое (`file-parse`/`crm-sync` payload'ы)
  живёт в Redis ограниченно по возрасту (`STATEMENT_JOB_RETENTION`, #245). Модель — [`PRIVACY.md`](PRIVACY.md).
- **Диск:** тома `redisdata`/Postgres растут; `removeOnComplete/Fail` (1000/5000) капают историю
  очередей. Мониторить свободное место; при заполнении сначала чистить образы/логи, не тома.
- **TLS:** cert выпускает/обновляет `acme-companion` (общий reverse-proxy). Алерт — истечение <7 д.
- **Health-probe:** внешний аптайм-мониторинг вешать на `GET /api/ready` (200/503, прощупывает
  db+redis) — он ловит упавшую зависимость, в отличие от liveness `/api/health` (200 + свежий `time`).
  ⚠ Telegram-оповещения (#426) его **не заменяют**: они молчат ровно тогда, когда упал сам инстанс,
  внутри которого живёт проверка.

## Оповещения оператору (Telegram, #426)

Единственный канал, который **стучится сам**. Логи `[queue-job-failed]` и страница `/queues`
требуют, чтобы кто-то уже смотрел, — а это ровно то, ради чего заводят оповещения.

**Включение — по шагам.**

1. **Завести бота.** В Telegram открыть `@BotFather` → `/newbot` → имя → username, оканчивающийся
   на `bot`. В ответ придёт токен вида `123456789:AA…` — это `TELEGRAM_ALERT_BOT_TOKEN`.
2. **Выбрать, куда писать, и добавить туда бота.** Группа (или свой личный чат). Бота надо добавить
   **до** следующего шага: пока его нет в чате, Telegram не покажет id чата, а на отправку ответит
   403.
3. **Узнать chat id.** Написать в этот чат любое сообщение, затем:

   ```bash
   curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates" | jq '.result[-1].message.chat.id'
   ```

   Личный чат — положительное число, группа — отрицательное, супергруппа — вида `-100…`. Для
   канала можно вместо числа указать `@имя_канала` (бот должен быть админом канала).
4. **Прописать в `.env` рядом с `docker-compose.prod.yml` на сервере** (compose-файл Watchtower не
   обновляет — синхронизировать руками, см. [`DEPLOY.md`](DEPLOY.md)):

   ```bash
   TELEGRAM_ALERT_BOT_TOKEN=123456789:AA…
   TELEGRAM_ALERT_CHAT_ID=-1001234567890
   ```

   Только на сервисе `backend` — там живёт крон. На `worker` не класть: масштабированные реплики
   дадут по копии каждого сообщения.
5. **Применить:** `docker compose -f docker-compose.prod.yml up -d backend`.
6. **Проверить, что канал принят.** В логе старта не должно быть предупреждения:

   ```bash
   docker compose -f docker-compose.prod.yml logs backend --tail=200 | grep -iE 'оповещен|alert channel'
   ```

   Ожидаем `[queue] alert channel: telegram`. Строка `alert channel OFF` или предупреждение
   envCheck — переменные не приняты (опечатка/половина).
7. **Проверить доставку**, не дожидаясь аварии — тем же вызовом, что делает транспорт:

   ```bash
   curl -s "https://api.telegram.org/bot$TELEGRAM_ALERT_BOT_TOKEN/sendMessage" \
     -d chat_id="$TELEGRAM_ALERT_CHAT_ID" -d text="проверка канала оповещений"
   ```

   `{"ok":true,…}` — дойдёт. `403` — бот не в чате или выгнан. `400 chat not found` — неверный id.
   ⚠ Это проверяет **транспорт**, а не правила: сквозного «пробного алерта» в приложении нет
   (правила читают реальные очереди). Повторять после каждой смены токена или чата.

Fail-closed: не заданы обе переменные ⇒ канал выключен, аварии остаются в логе и на `/queues`.
Половинчатая настройка — **тоже** выключен, и `envCheck` предупредит об этом на старте. Это
опаснее выключенного канала: оператор считает, что за системой следят, а сообщения молча пропадают.

**О чём сообщает.** Проверка периодически читает все очереди (интервал — `QUEUE_HEALTH_INTERVAL_MS`
в `server/plugins/queue.ts`) и выносит три вердикта:

| Вердикт | Когда | Что делать |
|---|---|---|
| `unreadable` | очередь не читается вовсе | Смотреть Redis (`docker compose ps redis`, `redis-cli ping`). Это самый опасный случай: снимок счётчиков при мёртвом Redis отдаёт нули, то есть тотальная авария выглядела бы «пустой здоровой очередью» |
| `stalled` | самая старая незавершённая задача пережила бюджет своей очереди | Жив ли `worker`-контейнер; не завис ли портал/банк. Бюджеты **разные по очередям** — таблица `STALL_BUDGET_MS` в `server/utils/queueAlert.ts` |
| `failing` | несколько задач исчерпали все попытки за окно наблюдения (порог и окно — `queueAlert.ts`) | Смотреть `[queue-job-failed] … FINAL` в логах: это **наши** сбои — пер-портальные отказы (нет прав, `insufficient_scope`, `PAYMENT_REQUIRED`, портал разавторизован) из счёта исключены намеренно |

**Почему бюджеты «простоя» разные.** Плоский порог давал бы ложные тревоги на очередях, которые
медленные **по проекту**: `bank-fetch`/`bank-fetch-prior` придавлены глобальным лимитом банка (полный
обход = `счета / лимит` минут, на масштабе — часы), `trigger-fire` **сутками** ждёт в backoff, пока
админ портала зарегистрирует CODE (чужое действие, не наша авария), `feedback-post` ретраит GitHub
около часа. Быстрые пути (`b24-events`, `file-parse`, `crm-sync`, `b24-deletions`) держат короткий
бюджет. Конкретные значения и обоснование каждого — `STALL_BUDGET_MS` в `server/utils/queueAlert.ts`
(здесь намеренно не дублируются, чтобы не разъехались).

⚠ Бюджет есть у **каждой** очереди и он конечный. Освободить очередь от правила простоя (`null`)
заманчиво для медленных путей, но это делает её невидимой: при мёртвом воркере не сработает и
правило падений — некому исчерпывать попытки.

**Почему канал молчаливый.** Одно сообщение на **эпизод**, а не на замер: авария живёт дольше
интервала проверки, и канал, который повторяется, перестают читать — тогда он не сработает в тот
единственный раз, ради которого заведён. Повторное объявление той же поломки после её исчезновения
придавлено окном (`MIN_REANNOUNCE_MS`), иначе «мигающая» на пороге очередь завалила бы чат.
Восстановление тоже объявляется — иначе не отличить «починилось» от «мы замолчали». И «сломалось»,
и «восстановилось» помечаются доставленными **только** после успешной отправки, поэтому один 429 не
хоронит сообщение.

⚠ **Это не чат ошибок портала.** В `errorChat` (настройки приложения) идёт «этот платёж требует
человека» — адресат бухгалтер клиента. Сюда идёт «сервис сломан» — адресат мы. В сообщения канала
**никогда** не попадают суммы, счета, назначения и контрагенты: только имена очередей и счётчики
([`PRIVACY.md`](PRIVACY.md)).

**Чего канал НЕ ловит** — это важнее того, что ловит: иначе легко решить, что за системой следят.

- **Смерть самого backend/cron-инстанса.** Проверка живёт внутри него: нет процесса — нет и
  сообщений. **Тишина в канале не равна «всё хорошо».** Внешний аптайм-мониторинг на
  `GET /api/ready` остаётся первичным средством и каналом не заменяется.
- **Упавший Postgres при живом Redis** — очереди читаются, вердикт будет «здорово».
- **Проблемы отдельного портала или банк-подключения** — разавторизованный OAuth-токен,
  недовыданные права, `PAYMENT_REQUIRED`, истёкшее согласие банка. Исключены из правила `failing`
  намеренно: иначе один криво настроенный клиент пейджил бы вечно про то, что чиним не мы.
  Смотреть `/queues` и логи.
- **Массовый `invalid_grant` по всем порталам сразу** (сменили `B24_CLIENT_SECRET`) — это уже наша
  авария, но тем же фильтром она скрыта, а правило простоя её не поймает: такие задачи падают
  быстро, очередь продолжает разгребаться. Нужен отдельный сигнал — follow-up в #426.
- **Качество обработки** — платежи, ушедшие в ручной разбор или неопознанные. Это чат ошибок
  портала и метрики, не этот канал.
- **Рестарт крона обнуляет состояние эпизодов** — идущая авария будет объявлена повторно (осознанно:
  бэкенд, который перезапускается, сам по себе стоит внимания).

### Смена адреса банка — менять ТРОЙКУ, а не одну переменную

Модель — **шлюзовая** и она реализована ([bx-shef/bee2-tls-gateway](https://github.com/bx-shef/bee2-tls-gateway), #460): наш код ходит на
`http://crypto-gw:1080`, крипто-TLS поднимает шлюз. Процедура ниже применяется как есть при
включении шлюза и при любом переезде хоста. (Прежняя оговорка «может, подмена адреса не
понадобится» относилась к кандидату АВЕСТ — от него ушли.)

Актуально при переводе Приора на BY-крипто TLS-шлюз (#41/#455) и вообще при любой смене хоста.
`PRIOR_OAUTH_API_BASE`, `PRIOR_OAUTH_TOKEN_URL` и `PRIOR_OAUTH_AUTHORIZE_BASE` **независимы** — код
нигде не выводит одну из другой, поэтому «поправил одну, забыл вторую» проходит деплой без единой
ошибки, а ломается позже и в другом месте:

| Забыли | Когда всплывёт | Как выглядит |
|---|---|---|
| `PRIOR_OAUTH_TOKEN_URL` | через час-другой, на первом рефреше | опрос встал, в логах обычная ошибка обновления токена |
| `PRIOR_OAUTH_AUTHORIZE_BASE` | при следующем подключении счёта | у админа не открывается страница банка; на сервере **ошибки нет вообще** |
| `PRIOR_OAUTH_API_BASE` | сразу | выборка выписки падает |

Порядок: правим все три в `.env` → `docker compose -f docker-compose.prod.yml up -d backend worker`
→ смотрим стартовые предупреждения (`envCheck` ругается на рассинхрон `API_BASE`↔`TOKEN_URL`, на
внутренний адрес в authorize и на `http://` к публичному хосту) → проверяем **и** опрос, **и**
подключение нового счёта. ⚠ `PRIOR_OAUTH_AUDIENCE` не трогаем: это claim внутри подписанного JWT,
а не сетевой адрес — переставленный «за компанию», он даёт отказ, похожий на ошибку авторизации.

### Прод-Приор через крипто-шлюз — запуск и проверка

Боевой Open Banking Приорбанка говорит по СТБ 34.101.65: Node обрывается на `ServerHello`, и
единственный путь к нему — шлюз `crypto-gw`. По умолчанию сервис **выключен**
(закомментирован в `docker-compose.prod.yml`) — включается осознанно, порядком ниже.

⚠ Прежде чем включать: боевая регистрация приложения в банке (`client_id` + опубликованный `jwks`
с нашим `kid`) — отдельная процедура с банком, песочная регистрация не подходит.

✅ **Канал к БОЕВОМУ банку проверен живым прогоном (2026-08-13, #477).** Образ по digest из compose
поднят на прод-сервере отдельным контейнером против `apibel.priorbank.by:9345`:

```
[crypto-gw] корни ГосСУОК: 2 сертификат(ов) в /etc/crypto-gw/ca/gossuok-bundle.pem
[crypto-gw] проверка цепочки: bundle подтверждает эталонный сертификат банка — OK
nginx/1.30.4 … start worker processes
route=token method=POST status=401 upstream=401 bytes=101 rt=0.081 urt=0.081
```

`upstream=401` — ответ **самого банка** (`invalid_client`: аутентификацию мы намеренно не слали),
то есть рукопожатие по СТБ 34.101.65 состоялось, и переход на nginx 1.30.4 его не сломал. Заодно
подтверждены две вещи, которые до этого держались на замерах вне контейнера: CPU **0,00 %**
(правка busy-loop работает под трафиком) и строка лога **без пути запроса** — гарантия из
`PRIVACY.md` соблюдается на живом образе. Compose пинится по **digest**, а не по тегу: у шлюза
`v1` движется каждым мержем, и пин по нему означал бы согласие на молчаливую подмену
TLS-терминатора.

⚠ Проверен **канал**, а не вся интеграция: боевая регистрация приложения в банке (`client_id` +
опубликованный `jwks`) — по-прежнему отдельная процедура, см. абзац выше.

⚠ И общее про этот сервис: `make prod-redeploy` собран цепочкой `pull && up -d`, поэтому
провалившийся `pull` **обрывает весь выкат** — не передеплоятся заодно `app`, `backend` и `worker`.
Отсюда шаг 3 ниже: сперва убедиться, что образ тянется, и только потом запускать редеплой.

**Включение.**

1. Каталог с корнями на сервере (репозитория там нет — только `compose`, `Makefile`, `.env`):
   создать, положить `gossuok-bundle.pem` и `bank-leaf-reference.pem` из
   [`ca/` репозитория шлюза](https://github.com/bx-shef/bee2-tls-gateway/tree/main/ca), прописать путь в `PRIOR_GW_CA_DIR`. Дефолта нет намеренно:
   относительный путь docker создал бы **пустым каталогом**, и шлюз ушёл бы в restart-loop.
2. Раскомментировать **три** места: сервис `crypto-gw`, сеть `cryptonet` внизу файла и строки
   `- cryptonet` в `networks` у **backend и worker**. Забыть третье — шлюз поднимется, а
   обращаться к нему будет некому.
3. Адреса — по таблице выше (`API_BASE` и `TOKEN_URL` на шлюз, `AUTHORIZE_BASE` остаётся
   публичным, `AUDIENCE` не трогать), плюс `PRIOR_OAUTH_AUTH_METHOD=private_key_jwt`.
   Проверить, что образ тянется, **до** редеплоя (иначе провалившийся `pull` оборвёт весь выкат):
   `docker manifest inspect $(grep -oP 'ghcr\.io/bx-shef/bee2-tls-gateway@sha256:\S+' docker-compose.prod.yml)`.
4. `make prod-redeploy` (или `docker compose -f docker-compose.prod.yml pull && docker compose -f docker-compose.prod.yml up -d` — `-f` нужен КАЖДОЙ команде, иначе вторая половина не выполнится).
5. `GET /api/ready` → `checks.cryptoGw: true`. `null` здесь значит «шлюз не используется»: адреса
   переставить забыли, и трафик по-прежнему идёт мимо.

**Что должно быть в логах шлюза сразу после старта** (`docker logs client-bank-alfa-by-crypto-gw`):

```
[crypto-gw] корни ГосСУОК: 2 сертификат(ов) в /etc/crypto-gw/ca/gossuok-bundle.pem
[crypto-gw] проверка цепочки: bundle подтверждает эталонный сертификат банка — OK
nginx: the configuration file /tmp/crypto-gw.nginx.conf test is successful
[crypto-gw] апстрим: apibel.priorbank.by:9345; слушаю :1080; nice=19
```

**Типовые сбои.**

| Симптом | Причина | Что делать |
|---|---|---|
| Контейнер в restart-loop, `FATAL: корни ГосСУОК не читаются` | том не смонтирован либо `PRIOR_GW_CA_DIR` указывает в пустоту | создать каталог и положить bundle |
| `ВНИМАНИЕ: bundle НЕ подтверждает эталонный сертификат` и потом **сплошные 502** | в bundle нет промежуточного сертификата | пересобрать bundle (`scripts/by-ca-bundle.sh`, запускать из Беларуси) |
| То же предупреждение, но 502 нет | УЦ сменил корни, эталон устарел | это ожидаемо — см. #462 |
| Не стартует, `host not found in upstream` | DNS до банка недоступен в момент старта | шлюз резолвит апстрим один раз при старте; поднимется сам, когда DNS вернётся |
| Все запросы 502, в логе шлюза пусто | `GW_ERROR_LOG_LEVEL=crit` по умолчанию | поднять до `info` (`PRIOR_GW_LOG_LEVEL=info`), повторить, **вернуть обратно** — на уровне `error` nginx печатает строку запроса, а в ней номер счёта |
| 403 на запросах приложения | путь вне allowlist шлюза | шлюз проксирует только `/open-banking/v1.0/` и token-эндпоинт; всё прочее отбивает сам |
| Отказ авторизации, похожий на неверный ключ | в `aud` уехал адрес шлюза | `AUDIENCE` — claim, а не адрес; вернуть публичный issuer |
| Шлюз жрёт ядро CPU | **уже не должен** | вечный busy-loop в источнике энтропии bee2 устранён в образе (открытый патч апстрима на поток-счётчик jitter). `nice 19` и лимит `cpus` оставлены до живого прогона — замер сделан на голом bee2, не под трафиком. ⚠ Увидели, что жжёт, — сообщите в репозиторий шлюза: значит патч не долетел |

**Ручная проверка транспорта без приложения.** Дев-скрипт умеет ходить через шлюз, но порт наружу
не опубликован — на время проверки добавить `crypto-gw` временный `ports: ["127.0.0.1:1080:1080"]`
(только loopback), затем убрать:

```bash
pnpm prior:test --oidc \
  --base https://apibel.priorbank.by:9345 \
  --api-base http://127.0.0.1:1080 \
  --auth-method private_key_jwt
```

Скрипт печатает оба адреса и предупреждает, если их перепутали. `--base` — публичный банк
(authorize-ссылка и `aud`), `--api-base` — шлюз (куда идёт HTTP).

**Автоопрос включать последним.** `CRON_REAL_POLL=1` — только после успешного ручного «Опросить
сейчас» и появившегося дела в CRM. Иначе первый же тик пойдёт по всем подключённым счетам.

**Состояние шлюза видно в `/api/ready`** — поле `checks.cryptoGw`:

| Значение | Что значит |
|---|---|
| `null` | шлюз не используется (`PRIOR_OAUTH_API_BASE` не внутренний http-адрес) |
| `true` | шлюз отвечает на свой `/healthz` |
| `false` | шлюз не отвечает — Приор стоит |

⚠ `cryptoGw: false` **намеренно не делает приложение unready** и не меняет `status`. Шлюз
обслуживает один банк: события Б24, ручная загрузка и Альфа работают без него, а 503 на этом
эндпоинте увёл бы в аварию весь мониторинг и устроил бы restart-loop там, где `/api/ready`
подключён к healthcheck'у. Поле нужно, чтобы дежурный **увидел** состояние по тому же адресу,
куда и так идёт; алертинг по Приору — за оповещениями очередей.

⚠ Отдельного алерта «шлюз лёг» по-прежнему нет: авария всплывёт косвенно, через падающие джобы
`bank-fetch-prior` и порог Telegram-оповещений, но текст будет generic — тогда и смотреть
`checks.cryptoGw`.

### Ротация ключа шифрования

Ключ шифрует `refresh_token` порталов и банков. Просто заменить его **нельзя**: все сохранённые
токены станут нечитаемыми разом, то есть каждый портал переустанавливает приложение, а владелец
заново подключает банки. Сбой при этом тихий — `envCheck` проверяет только длину, поэтому подмена
выглядит успешным деплоем и обнаруживается на первом рефреше.

Поэтому расшифровка принимает **второй, прежний ключ**:

```bash
# 1. В .env: текущий ключ переносим в OLD, генерируем новый.
B24_TOKEN_ENC_KEY_OLD=<прежний ключ>
B24_TOKEN_ENC_KEY=<openssl rand -hex 32>

# 2. Пересоздать (именно up -d — restart не перечитывает .env):
docker compose -f docker-compose.prod.yml up -d backend worker
```

Дальше строки перешифровываются **сами**: пишем всегда новым ключом, а токен перезаписывается при
каждом рефреше.

⚠ **Сколько держать `OLD` — считайте по факту, а не по календарю.** Соблазнительно сказать «месяц»,
но это неверно: keep-alive рефрешит **не все** порталы подряд, а только попавшие в узкую полосу
near-expiry (`updated_at` старше 177 дней при TTL refresh-токена 180 — `tokenKeepAlive.ts`).
Простаивающий портал — тот, где нет банк-счетов, не идёт опрос и никто не открывает приложение, —
не делает REST-вызовов вообще, поэтому его строка перешифруется только на **177-й день**.
Календарная граница безопасности — **≥180 дней**, а точный критерий — «не осталось строк старше
момента ротации»:

```bash
docker compose -f docker-compose.prod.yml exec -T db psql -U app -d app -c \
  "select count(*) from portal_tokens where updated_at < '2026-07-31'"   -- дата ротации
```

Пока счётчик не ноль — `OLD` убирать нельзя. То же самое проверить по `bank_tokens`.

⚠ **Банк-токены сами по себе НЕ перешифровываются.** У них нет keep-alive: единственный рефреш —
`ensureBankToken`, а он вызывается только из опроса. При выключенном `CRON_REAL_POLL` (дефолт)
строки `bank_tokens` не обновятся никогда, сколько ключ ни держи. Варианты: включить опрос на время
ротации, нажать «Опросить сейчас» по каждому порталу — либо принять, что банк-подключения после
снятия `OLD` придётся переподключить вручную.

⚠ Прежний ключ — такой же секрет: пока переменная задана, компрометация старого ключа по-прежнему
опасна. Ротация «по подозрению на утечку» не завершена, пока `OLD` не убран.

## Бэкапы и восстановление

⚠ **Данные в `portal_tokens` и `bank_tokens` невосстановимы.** Их нельзя перевыпустить своими
силами: потеря тома означает, что **каждый портал** переустанавливает приложение заново, а владелец
портала заново проходит OAuth банка. Откат образа (раздел выше) от этого не спасает — он не трогает
данные, а здесь теряются именно они.

**Снимать дамп** (на хосте, рядом с прод-compose). Пишем во временный файл и переименовываем
только после успеха — иначе упавший `pg_dump` тихо оставит **пустой** файл, ротация вытеснит им
рабочие дампы, и обнаружится это на восстановлении:

```bash
set -e
tmp=$(mktemp backup-XXXX.dump)
docker compose -f docker-compose.prod.yml exec -T db \
  pg_dump -U app --format=custom app > "$tmp"
pg_restore --list "$tmp" > /dev/null      # дамп читается, а не просто «файл создан»
mv "$tmp" "backup-$(date +%F).dump"
```

**Расписание.** Раз в сутки по крону хоста, хранить 14 дней; складывать **вне этого сервера**
(бэкап на том же диске не переживёт отказ диска). Дамп содержит токены порталов и шифрованные
refresh банков — хранить его надо как секрет, не в публичном облаке без шифрования. Класть рядом с
дампом **копию `.env`**: без `B24_TOKEN_ENC_KEY` дамп бесполезен (см. ниже), а это два разных
артефакта, которые разъедутся на первой же ротации.

**Восстановление:**

```bash
# `app` тоже останавливаем: nginx иначе продолжит принимать POST /api/b24/events и отвечать 502,
# а онлайн-события Б24 НЕ РЕТРАЯТСЯ — установка/удаление, попавшие в это окно, пропадут молча.
docker compose -f docker-compose.prod.yml stop app backend worker
docker compose -f docker-compose.prod.yml exec -T db \
  pg_restore -U app -d app --clean --if-exists < backup-YYYY-MM-DD.dump
docker compose -f docker-compose.prod.yml start db app backend worker
```

⚠ `pg_restore --clean --if-exists` возвращает **ненулевой код на безобидных предупреждениях**
(DROP несуществующего объекта). Само по себе это не провал восстановления — смотреть надо на текст,
а не на код возврата.

⚠ Восстановление обязательно **проверять**: дамп, который никто ни разу не разворачивал, — это не
бэкап, а надежда. Раз в квартал разворачивать последний дамп на тестовом сервере и убеждаться, что
`GET /api/ready` отдаёт 200, а порталы на месте:

```bash
docker compose -f docker-compose.prod.yml exec -T db \
  psql -U app -d app -c 'select count(*) from portal_tokens'
```

⚠ `B24_TOKEN_ENC_KEY` в дамп **не входит** (он в `.env`). Восстановление БД со старым дампом и
**новым** ключом даст нечитаемые refresh-токены — ключ надо хранить и восстанавливать вместе с
дампом, иначе результат неотличим от потери данных.

**Redis не бэкапим намеренно.** В томе `redisdata` лежат payload'ы джоб — то есть содержимое
выписок (финансовые ПДн, [`PRIVACY.md`](PRIVACY.md)), и держать их копии противоречит всей модели
хранения. Цена потери тома: пропадут принятые, но ещё не обработанные импорты — их присылают
заново. Именно поэтому `docker system prune --volumes` на этом сервере недопустим: он снесёт и
`pgdata`.

## Логи и ротация

⚠ **Ретенция логов = ретенция номеров счетов.** Воркер пишет строки вида
`[recognize] op <счёт>|<docId>` на каждую операцию каждого импорта ([`PRIVACY.md`](PRIVACY.md)
это фиксирует), а docker по умолчанию (`json-file`) не ограничивает файл ничем. Без ротации
финансовые ПДн копятся бессрочно — вопреки постуре «выписки у себя не храним», — и попутно
переполняют диск, последствия чего описаны выше (read-only Postgres/Redis).

В `docker-compose.prod.yml` у каждого сервиса задан якорь `x-logging` (10 МБ × 5 файлов, сжатие).
Дополнительно стоит выставить тот же дефолт на уровне демона — он покроет и контейнеры, поднятые
мимо compose:

```json
// /etc/docker/daemon.json  (нужен `systemctl restart docker`)
{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "5" } }
```

⚠ При `--scale worker=N` лимит действует **на каждую реплику**, а не суммарно.

## On-call / эскалация

1. Первичная триада: `/api/ready` (зависимости живы? — db+redis; `/api/health` — только liveness) →
   `docker compose ps` (все контейнеры `Up`/`healthy`, никто не `Restarting`?) →
   `scripts/queue-stats.sh` (очереди разгребаются?).
   **Предусловие шага 3:** диагностика очередей требует заранее заведённого `B24_APPLICATION_TOKEN`
   (консоль) или операторского логина (`/queues`) — без них оба пути недоступны именно тогда, когда нужны.
2. Логи по сервису: `docker compose -f docker-compose.prod.yml logs <service> --tail=200`.
3. Эскалация — автор/владелец (`bx-shef`, контакты в подвале приложения); банк-инциденты
   (Альфа/Приор недоступны, сменились креды) — за владельцем (креды у него, в репо их нет).
