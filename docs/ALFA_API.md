> не показывала — она выдана другим удостоверяющим центром.

## Что используем

### 1. Авторизация — **Password Grant (ключ API)**

⚠ **ЭТО ЕДИНСТВЕННЫЙ ЖИВОЙ СПОСОБ.** Authorization Code Grant у Альфы **убран из кода** 2026-09-09
(#488): измерено дважды на боевом контуре, что цепочка его `refresh_token` живёт **ровно 10 часов от
авторизации** и не продлевается ни своевременным обновлением, ни обращениями к API — то есть
непрерывный импорт требовал бы входа владельца счёта в интернет-банк дважды в сутки. Разбор замера,
ответ банка и решение — ниже по документу (§«`invalid_grant: User session not alive`» и
§«РЕШЕНИЕ 2026-09-09»). Здесь — как работает то, что осталось.

| Шаг | Запрос | Ключевые параметры |
|---|---|---|
| (1) Ключ API | владелец счёта генерирует его в Альфа Бизнес Онлайн под наш `client_id` | ничего не вызываем; ключ бессрочен, отзывается клиентом |
| (2) Токены | `POST {base}/token` | `grant_type=password`, `username=<ключ API>`, `client_id`, `client_secret`, `scope=accounts` |
| (3) Refresh | `POST {base}/token` | `grant_type=refresh_token`, `refresh_token`, `client_id`, `client_secret` |
| (4) Переиздание | `POST {base}/token` | тот же шаг (2) — когда цепочка refresh умерла, ключ выпускает пару заново БЕЗ человека |

> **Пароля в этом типе авторизации нет** — в `username` едет ключ API, а не логин клиента от банка.
> Именно поэтому исходное возражение против Password Grant («держим у себя ключ от чужого банка»)
> к нему не относится: ключ выдан ПОД НАШ `client_id`, ограничен запрошенным scope и в кабинете
> клиента есть кнопки «Заблокировать»/«Отозвать».

> **Аутентификация токен-эндпоинта — креды в теле запроса** (`client_id` + `client_secret` в
> `application/x-www-form-urlencoded`), как в примере документации Альфы и в
> `app/utils/alfaOauth.ts`. На **sandbox** проходил и вариант HTTP Basic — т.е. песочница
> принимает оба. `client_secret` — только в теле, никогда в URL/логах.

- Ответ токена: `access_token`, `token_type` (default `Bearer`), `expires_in=3600` (1 ч, в коде —
  дефолт `parseTokenResponse`), `refresh_token`. TTL refresh — `ALFA_REFRESH_TOKEN_TTL_SEC` = 36000 с
  (10 ч; документация банка, и на Code Grant это же число подтвердилось замером до минуты).
- `redirect_uri` **не участвует вовсе** — редиректа в поток больше нет.
- `client_secret` — только в env сервера (никогда в репозиторий/логи/URL).
- **Ключ API** — не в env, а в строке подключения (`bank_tokens.api_key_enc`, шифрован тем же
  `B24_TOKEN_ENC_KEY`): он свой у каждого портала и открывает счета именно его клиента.

### 2. Счета и выписка

Все вызовы — с заголовком `Authorization: Bearer {access_token}`, scope `accounts`, на тот же
базовый хост `{base}` (`…:8273`), что и OAuth (sandbox/prod — см. блок-цитату выше).

> **Scope:** нам нужен только `accounts` (счета + выписка). У API «Авторизация» есть и другие
> области (profile, документы/платежи, карты, валютообмен и т.д.) — понадобятся, если будем
> подключать платежи/чат через Альфу; пока не запрашиваем.

| Метод | Назначение | Используем |
|---|---|---|
| `GET /partner/1.2.0/accounts/` | список счетов и остатков | да — выбор счетов |
| `GET /partner/1.2.0/accounts/statement` | выписка по счёту(ам) | да — основной поток |

**Ключевые поля ответа `GET /accounts/`** (`accounts[]`): `number` (номер счёта),
`currIso` (валюта, симв.), `amount` (остаток бухгалтерский), `type`/`isCard` (тип/карточный),
флаги `isArrested`/`isReserved`/`isOverdraft` (арест/бронь/овердрафт), `actualBalanceDate`
(на какую дату актуальны остатки).

**Параметры `GET …/accounts/statement`:**

| Параметр | Значение |
|---|---|
| `number` | номера счетов — несколько query-параметров `number=…` (до 50) |
| `dateFrom` / `dateTo` | период, формат **DD.MM.YYYY** |
| `transactions` | `1` = приход (кредит), `2` = расход (дебет), `0` = все |
| `pageNo` / `pageRowCount` | пагинация; `0` = «все» (нестандартная семантика Альфы). ⚠ **Не проверено, и есть основания сомневаться** — см. ниже |
| `amountFrom` / `amountTo`, `transactionType`, `cacheKey` | опционально (фильтры/кэш) |

**Ответ** — `page[]` (операции) + `statistics[]` (остатки/обороты) + `errors[]` (ошибки по счёту).
Из модели операции берём: `operType` (C/D → приход/расход), `amount`/`currIso`, `purpose`,
`corrName/corrUnp/corrNumber/corrBic/corrBank` (контрагент → поиск компании по корр-счёту),
`docId/docNum`, `operCodeName`, и даты: `acceptDate` — **timestamp** `2023-01-13T14:00:00.000`
(local, без TZ-суффикса), `operDate` — **дата** `DD.MM.YYYY`. `errors[]` обязательно проверяем
(не считать errored пустой `page` за «нет операций»).

> Печатные формы (`/statement/{format}` pdf/xlsx/…), аресты, брони, SWIFT, реестр — **пока не
> используем**; подключим по мере необходимости.

## Пример вызовов — ИСТОРИЯ прогона на sandbox (2026-06-30)

⚠ **Шаги 1-2 описывают УБРАННЫЙ поток** (Authorization Code, #488) и оставлены как запись того,
что было прогнано вживую, а не как инструкция. Шаги 3-5 (`/accounts/`, выписка, refresh) остаются
в силе — они одни и те же при любом типе авторизации.

Полный поток **OAuth (Authorization Code) → `/accounts/` → выписка → refresh** был прогнан
вживую на песочнике `developerhub.alfabank.by:8273` тестовыми `client_id/secret`.
Все значения ниже — маскированы. `base = https://developerhub.alfabank.by:8273`.

> ⚠ **Разведочный скрипт `scripts/alfa-oauth-test.mjs` (`pnpm oauth:test`) УДАЛЁН** вместе с
> authorize-потоком (#488) — он весь состоял из шагов 1-2 ниже, которых больше нет. Живая проверка
> подключения делается теперь на боевом стенде: `make poll-check` (что происходит с опросом) и
> `make alfa-page-probe` (пагинация выписки уже сохранённым access-токеном). Пример ниже оставлен
> как ИСТОРИЯ прогона 2026-06-30, а не как инструкция.

### 1. Authorize (браузер)

```http
GET {base}/authorize?response_type=code&client_id={clientId}
    &redirect_uri={redirectUri}&scope=accounts&state={state}
```

Пользователь логинится у Альфы и подтверждает доступ → редирект на
`{redirectUri}?code=1c00f727-…&state={state}`. `state` сверяем (CSRF), `code` короткоживущий.

### 2. Обмен `code` → токены

```http
POST {base}/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code={code}&redirect_uri={redirectUri}&client_id={clientId}&client_secret={clientSecret}
```
```jsonc
// HTTP 200
{
  "access_token":  "ibHZMkuo…",   // ~89 симв.
  "refresh_token": "J0k+lQXu…",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "accounts"             // выдаётся ровно запрошенный scope
}
```

GET {base}/partner/1.2.0/accounts/

### 4. Выписка — `GET /accounts/statement`

```http
GET {base}/partner/1.2.0/accounts/statement?number={acc}
    &dateFrom=01.01.2024&dateTo=31.12.2024&transactions=0&pageNo=0&pageRowCount=0
Authorization: Bearer {access_token}
```
```jsonc
// HTTP 200 → { page:[…], statistics:[…], errors:[…] }
{
  "page": [
    {
      "number": "BY…0000", "operType": "C",            // C = приход / D = расход
      "amount": 150, "currIso": "BYN",
      "purpose": "ОПЛАТА ЗА ТОВАРЫ СОГЛАСНО ДОГОВОРУ…",
      "corrName": "ИНДИВИДУАЛЬНЫЙ ПРЕДПРИНИ…", "corrNumber": "BY…0000",
      "docId": "…", "docNum": "…",
      "operDate": "13.01.2024", "acceptDate": "2024-01-13T14:00:00.000"
    }
  ],
  "errors": []   // ВАЖНО: errored-ответ может прийти с пустым page — проверять errors[]
}
```

Нормализуем ответ в `StatementItem` через `normalizeAlfaStatement()` (см.
`app/utils/alfaStatement.ts`); ошибки по счёту — `alfaStatementErrors()`.

> #### ⚠ `pageRowCount=0` = «все» — это строка в документации, а не измерение (#561)
>
> ⚠ **Улика «ровно 100 записей в сутки» оказалась ПРИОРОВОЙ, а не Альфиной** (разобрано 2026-08-22,
> #561/#573): выдачу по 100 с непрочитанным `links.next` режет Приорбанк, и постраничный обход там
> вернул 287 потерянных операций. По боевому счёту Альфы проходит порядка четырёх операций в сутки
> — то есть на этих данных вопрос «`0` это все или страница» **не проверяется вовсе**: обрезать
> нечего. Строка ниже про «теряли всё за сотней каждые сутки» была выведена из чужих чисел; сам
> вопрос к документации Альфы остаётся открытым, но доказанной потери у неё НЕТ.
>
> Признак страницы мы при этом никогда не читали: брали `page[]` и считали его всем ответом. Если
> `0` на деле значит «страница по умолчанию», мы теряли всё за сотней **каждые сутки** и узнать об
> этом не могли — дедуп по маркеру стирает разницу между «не было операций» и «не доехали».
>
> Поэтому `fetchAlfaStatementPages` **обходит страницы**, пока банк не кончится. Цикл безопасен при
> **обоих** прочтениях, и это его смысл: если `0` правда «все», страница 1 вернёт тот же набор, мы
> опознаем повтор и остановимся после одного лишнего запроса; если «страница» — заберём потерянное и
> скажем об этом **предупреждением**, потому что молчаливое восстановление скрыло бы, как долго это
> длилось.
>
> ⚠ **Останов смотрит на СЫРУЮ страницу, а не на результат дедупа**, и это несущее различие.
> «Страница не принесла ничего нового» выглядит равносильным и не является им: `dedupKey` при пустом
> `docId` переходит на контент-сигнатуру, а в неё **не входит имя плательщика**, — значит два разных
> плательщика с одинаковой суммой, общей датой пакета, шаблонным назначением и одним получателем
> дают один ключ. На прежнем однозапросном пути такая коллизия стоила одной операции; как условие
> останова она обрывала бы обход и стоила **всех оставшихся страниц** — то есть ровно та тихая
> массовая потеря, ради конца которой всё и написано. Поэтому обход прекращают только пустая
> страница и страница, чьи сырые строки повторяют уже полученную. Дедуп остался — но на **выходе**,
> где схлопнуть дубль это всё, что он может сделать.
>
> ⚠ **Хвост ограничен ДВУМЯ независимыми пределами, и оба слышны.** Потолок страниц
> (`MAX_ALFA_STATEMENT_PAGES` = 20) связывает быстрый банк, бюджет времени
> (`ALFA_WALK_BUDGET_MS` = 20 с, считается по реальным часам, включая ожидание банка) — медленный;
> между страницами платится пауза (`ALFA_PAGE_DELAY_MS` = 500 мс, и только когда страница была
> непустой, так что тихие сутки её не платят). Предел, до которого при штатных константах не
> добраться, — украшение: его нельзя проверить, и он молча перестаёт защищать, как только подкрутят
> соседнюю константу (урок `PRIOR_POLL_BUDGET_MS`). Упор в любой из двух печатает
> «ОБХОД СТРАНИЦ ОБОРВАН» — иначе усечение просто переезжает с сотни операций на двадцать страниц и
> снова становится невидимым.
>
> ⚠ Первый запрос при этом **не менялся**: `pageNo=0, pageRowCount=0` — байт-в-байт как раньше.
> Менять то, на что прод отвечает, не проверив у банка, — не то место для экспериментов.
>
> ⚠ Цена: задача Альфы стоит теперь **два** запроса на сутках с операциями, и лимитер это
> учитывает (`QUEUES.md`). ⚠ Два — **типичная** стоимость, не потолок: активный счёт под вторым
> прочтением пройдёт дальше. Ровно так же устроен и Приор (10 при потолке в 20 опросов) — хвост
> держит не эта константа, а пределы обхода выше, и оба они громкие.
>
> **Что закроет вопрос окончательно** — строка `[fetch]` в проде: если после выката появится
> «ПАГИНАЦИЯ ВЕРНУЛА ЕЩЁ N операций», значит верно второе прочтение и потери были. Тишина в этой
> строке при непустых окнах — значит `0` правда означает «все», и тогда стоимость задачи можно
> вернуть к единице (иначе хедж останется навсегда просто по инерции).
>
> ⚠ Читать прод — не единственный путь и не самый быстрый: тот же ответ даёт **разовый запрос
> `pageNo=1`** за один из «сотенных» дней, и он собран в готовую команду —
> **`make alfa-page-probe DAY=ГГГГ-ММ-ДД`** (`scripts/prod-alfa-page-probe.sh`).
> `bank_tokens.access_token` хранится в открытом виде (шифруется только `refresh_token_enc`) и
> живёт около часа, поэтому проба read-only и **не трогает refresh** — ротация при ручном
> обновлении рассинхронизировала бы нашу базу с банком (#505/#509; по той же причине
> `scripts/prior-host-probe.sh` намеренно refresh не трогает). ⚠ Регулярный опрос этот вопрос
> закрыть не может: окно у него `CRON_LOOKBACK_DAYS` (дефолт 1), то есть спросить про 18 августа
> он не умеет в принципе — только дождаться следующего такого дня.
>
> `statistics[]` (остатки/обороты) мы по-прежнему **не читаем** (`statistics?: unknown[]`, «not
> modeled yet»). Это встроенная арифметическая сверка ответа: банк в том же ответе сообщает обороты
> за период, и сумма разобранных операций проверяется против них на каждом прогоне. ⚠ Формат блока
> нигде не задокументирован, а моделировать сверку по выдуманным полям — значит получить ложное
> «недосчитались» на исправном проде; поэтому `make alfa-page-probe` теперь печатает **ключи**
> блока `statistics[]` (значения — нет: там суммы, а вывод команды пересылают). Как только владелец
> пришлёт ключи с живого стенда — сверка моделируется по факту, а не вслепую (#561).

### Замечания по sandbox

- **Песочница отдаёт фиксированные данные, игнорируя `dateFrom/dateTo` и номер счёта** —
  одна и та же выписка на каждый год. Фильтр по периоду проверяется только на проде.
- **Часть тестовых счетов отвечает `HTTP 500`** на `/statement` (серверная сторона
  песочницы) — транспорт должен это переживать и не считать ошибку за «нет операций».
- Лимит **~100 запросов/мин** на API (пилот; по данным на 2026-06-30, уточняй в договоре /
  на developerhub) — при массовом опросе нужна пауза/троттлинг.
  ⚠ Лимит на **OAuth-клиента**, а не на счёт и не на портал. У приложения ОДИН `client_id`
  Альфы, значит эту сотню делят все обслуживаемые порталы, и она **не растёт с числом клиентов**.
  ⚠ Наш глобальный лимитер (A8, общий на все реплики через Redis) держит **80 %** от этой цифры,
  а не саму цифру (`DEFAULT_FETCH_RATE_MAX`, решение владельца 2026-08-20). Причина: лимитер
  считает то, что мы СТАВИМ В ОЧЕРЕДЬ, банк — то, что ПОЛУЧАЕТ, и совпадают эти счёта никогда
  (ретрай после сетевого блипа, опрос на краю окна, расхождение часов между репликами). Стоя ровно
  на границе, первое же расхождение даёт 429 — а 429 на выписке читается как «банк лежит», а не
  как «мы спросили на чуть-чаще». Запас ничего не стоит: один счёт Альфы — **один** запрос за
  прогон. ⚠ Сама цифра пилотная и может отличаться в договоре; запас — единственное, что стоит
  между «опубликованное число было оптимистичным» и вставшим импортом.

### ✅ Официальный ответ банка (2026-09-07) — модель подтверждена

Переписка с `api@alfa-bank.by`. На прямой вопрос «является ли ожидаемым, что `refresh_token`
перестаёт приниматься одновременно с истечением `access_token`» — **«Да. Поведение ожидаемое.»**

Дословно, из нескольких писем:

> «Access и Refresh токены работают в паре, проще говоря, один без другого существовать не может.
> Соответственно, если вы успешно обновляете Access каждые максимум 60 минут, Refresh будет
> работать столько времени, сколько вы обновляете вплоть до 10 часов.»

> «Refresh token существует и отрабатывает максимум 10 часов при условии, если есть активный Access
> Token, если Access истек (более 60 минут), необходима повторная авторизация и получение новой
> пары токенов.»

> «Сессия завершается по истечению срока жизни Access token (через час), или Refresh token (через
> 10 часов).»

> «При первой авторизации выдается пара ключей Refresh и Access. Оба ключа живут час… Обновлять
> через refresh token нужно каждый час, однако **до 10 часов с момента первой авторизации**, после
> сессия закрывается автоматом и необходима повторная авторизация. Это требование безопасности.»

**Модель банка целиком:**

1. пара выдаётся на час;
2. обмен `refresh_token` внутри этого часа выдаёт НОВУЮ пару и продлевает сессию;
3. пропустили час — refresh не поможет, нужна повторная авторизация владельца счёта в браузере;
4. потолок сессии — 10 часов от ПЕРВОЙ авторизации.

⚠ **Число 36000 в документации описывает ПОТОЛОК СЕССИИ, а не срок жизни refresh-токена.** Строка
«время жизни refresh_token — 36000 сек» читается ровно наоборот, и на этом потеряно три недели: наш
порог продления (половина от десяти часов = пять часов) выведен именно из неё и потому опаздывал
ВСЕГДА. Правильное прочтение — «обновляться не реже раза в час, и так до десяти часов».

⚠ **Замер и слова банка совпали полностью.** Лестница пауз дала: 1 мин — `200`, 30 мин — `200`,
60 мин — `400 invalid_grant` (два независимых прогона, 6 и 7 сентября). Это же объясняет все прежние
наблюдения без остатка: при включённом опросе токен продлевался по дороге каждые несколько минут —
всегда внутри часа; при выключенном крон приходил раз в пять часов — всегда снаружи.

### ⚠ Открытый вопрос: продлевает ли сессию ИСПОЛЬЗОВАНИЕ токена

Замер выше ни разу не обращался к API: счёт в подключении не был выбран, выписка не запрашивалась —
двадцать раз подряд менялись токены, и ничего ими не делалось.

А в августе, когда подключение прожило шестеро суток, счёт был выбран и опрос ходил за выпиской
каждые пять минут. **Это единственное различие между двумя случаями.**

Отсюда вопрос, который до замера сформулировать было нельзя: продлевает ли сессию использование
`access_token`? У шлюзов этого класса такое поведение обычно — сессия живёт от активности, а не от
факта обмена токенами.

⚠ Оговорка про это лежала в конце файла с самого начала («какое из двух действий держало грант —
обновление или поход за выпиской, — из наблюдения не следует»). Тогда она читалась как придирка к
строгости. После замера это единственный оставшийся вопрос: чистое обновление, как выяснилось, не
держит, значит если шесть суток были реальны — держало обращение к API.

**Два исхода, противоположные по последствиям:**

| если | то |
|---|---|
| использование ПРОДЛЕВАЕТ | потолок бьёт только по простаивающим подключениям; при живом опросе всё работает, и остаётся одна правка — обновлять внутри часа |
| НЕ продлевает | владелец счёта обязан заново входить в интернет-банк каждые 10 часов; кодом это не лечится, вопрос продуктовый |

**Как проверяется.** Та же лестница: после каждого удачного обмена проба делает один реальный вызов
`GET …/accounts/` тем самым свежим `access_token` (`oauth-refresh-probe.sh`, только для Альфы).
Дойдёт до 24-й ступени — использование держит сессию; упадёт снова около 20-й — не держит.

⚠ Исход вызова на вердикт ступени **не влияет**: лестница отвечает на «принимает ли банк обмен», а
вызов — отдельное действие, чьё влияние и меряется. Смешать их значило бы записать отказ API как
отказ в продлении.

⚠ Номера счетов в вывод не идут — только код ответа и количество: журнал пробы копируют в переписку.

⚠ Лестницу запускают **только на свежем подключении**: неудачный обмен грант сжигает, и следующий
прогон упрётся в мёртвый токен на первой же ступени — «отказ» будет про грант, умерший ДО опыта.
Проверять `make bank-history` перед стартом.

### Что это меняет

Вся конструкция #488/#489 построена на модели «refresh-токен живёт ~10 часов, надо успеть
продлить его вовремя». Замер эту модель **опровергает**: банк отказывает не потому, что вышел срок
токена, а потому, что не жива **пользовательская сессия**.

Числа замера (портал `11f3b7`, боевой контур):

| событие | время | прошло от подключения |
|---|---|---|
| счёт подключён (успешный OAuth) | 06:00 | — |
| наступил срок продления (половина от 10 ч) | 11:00 | 5 ч |
| крон пошёл в банк и получил отказ | 11:48 | **5 ч 48 мин** |

То есть грант был мёртв **задолго до** документированных 10 часов, и число 36000 с описывает не тот
механизм. Отсюда [#660](https://github.com/bx-shef/client-bank-alfa-by/issues/660): флаг
`BANK_REFRESH_TTL_MEASURED['alfa-by'] = true` не просто слабо обоснован — он моделирует не ту
сущность.

### Что при этом ИСКЛЮЧЕНО (а не предположено)

Отметка попытки (`last_attempt_at`) ставится **после** проверки кредов и наличия refresh-токена и
**до** запроса в банк. Раз она проставилась — значит:

- креды Альфы настроены (без них выход происходит раньше отметки);
- refresh-токен непустой (без него тоже выход раньше);
- запрос собран и отправлен, ответ получен.

Сломано не в нашем отборе, не в настройках и не в хранилище. Крон **приходит** — это тоже замер, а
не предположение: `прогонов продления за 24h: 7, попыток: 1, отказов банка: 1`.

### Догадка, помеченная как догадка — ✅ ЗАКРЫТА ответом банка

Альфа стоит за шлюзом WSO2 (мы уже видели его конверт `{fault:…}` в ответах). У WSO2 refresh-грант

### Что именно мы вызываем (для обращения в поддержку банка)

⚠ Держим здесь дословно, потому что при разговоре с банком спрашивают именно это, а собирать
состав вызовов по коду в момент аварии — терять часы. Секреты в обращение НЕ вставляем: для
диагностики они не нужны.

**1. Авторизация владельца счёта (браузер):**

```

    &redirect_uri=<redirect_uri>&state=<одноразовый CSRF-токен>
```

**2. Обмен кода на токены (сервер, сразу после возврата)** — билдер `buildTokenExchangeBody`,
удалённый вместе с потоком:

```
POST https://ibapi2.alfabank.by:8273/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=…&redirect_uri=…&client_id=…&client_secret=…
```

Ответ приходит успешно: `access_token`, `refresh_token`, `expires_in=3600`.

**3. Обновление токена (сервер, по расписанию)** — `buildRefreshBody`, без дополнительных
заголовков (секрет в теле, не Basic):

```
POST https://ibapi2.alfabank.by:8273/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token=…&client_id=…&client_secret=…
```

⚠ **Существенная деталь замера:** между шагом 2 и шагом 3 не было НИ ОДНОГО обращения к API — ни
`/accounts`, ни `/statement`. Счёт в приложении не был выбран, поэтому фоновая выгрузка не
запускалась (в логе `[fetch] опрашивать нечего: 2 без выбранного счёта`). То есть `access_token`
не использовался вообще, а `refresh_token` предъявлялся впервые — и всё равно получил отказ. Это
исключает версию «сессию закрыл какой-то наш запрос».

### ✅ РЕШЕНИЕ 2026-09-09: Альфа переведена на Password Grant

Владелец: «переделаем всё на Password Grant — мои текущие приложения на нём работают более 4 лет».
OAuth Code Grant у Альфы **убирается из кода**; в документации остаётся пометка, что он работал для
разработки, а на проде даёт окно 10 часов от авторизации.

⚠ **Прежнее решение (2026-09-06, «остаёмся на Code Grant») отменено, и посылка, на которой оно
принималось, оказалась неверной.** Тогда считалось, что Code Grant заработает, как только мы
починим свой код. Замерено дважды: цепочка refresh живёт **ровно 10 часов от авторизации** и не
продлевается ни своевременным обновлением, ни обращениями к API. Это не наш дефект и кодом не
лечится.

⚠ **Название типа авторизации вводит в заблуждение, и это существенно.** Пароля в нём нет: в
`username` едет **ключ API**, который владелец счёта генерирует у себя в кабинете под наш
`client_id` и там же может заблокировать или отозвать. Логин от банка клиент нам не отдаёт — то
есть исходное возражение против Password Grant («приложение держит ключ, которым клиент входит в
свой банк») к этому механизму не относится.

⚠ **Сроки те же, значит десятичасовой потолок, вероятно, остаётся и здесь.** Разница в том, что он
перестаёт быть фатальным: ключ бессрочен, поэтому мёртвая цепочка переиздаётся запросом
`grant_type=password` без человека (`ensureBankToken`, переиздание после отказа обновления).

#### Что делает владелец счёта

Настройки → вкладка **Open API** → **«Сгенерировать ключ API»** → **НАЗВАНИЕ** любое,
**CLIENT ID** — наш, **ТИП КЛЮЧА** — **Постоянный ключ** → согласиться с условиями →
**«Сгенерировать ключ»** → раскрыть строку → **«Скопировать ключ»**.

Готовый ключ показывается как «ПРИЛОЖЕНИЕ: <наше>, БЕССРОЧНЫЙ», статус «Действителен», рядом кнопки
**«Заблокировать»** и **«Отозвать»** — это и есть выключатель на стороне клиента.

⚠ `client_id` показывается в нашем интерфейсе рядом с полем ключа: диалог банка его спрашивает, а
взять его бухгалтеру больше неоткуда — он живёт в переменных окружения нашего сервера.

⚠ **Ключ хранится в строке подключения (`bank_tokens.api_key_enc`), зашифрованным**, а НЕ в
переменной окружения: он у каждого клиента свой и открывает его счета. Один ключ на весь флот
означал бы доступ к счетам одного клиента для всех остальных.

### Два типа авторизации у Альфы — справочно (2026-09-06)

Документация Alfa Developer Hub («Авторизация», раздел «Code Grant или Password Grant») описывает
**два** способа получить токен:

| | **Code Grant** — используем и остаёмся на нём | **Password Grant** |
|---|---|---|
| как получают доступ | владелец счёта вводит логин Альфа Бизнес Онлайн **в браузере** | владелец генерирует **ключ API** у себя в кабинете |
| участие человека | при каждой авторизации | однократно |
| запрос | `grant_type=authorization_code` | `grant_type=password&username=<ключ API>` |

⚠ **ОТМЕНЕНО 2026-09-09** (см. блок «Альфа переведена на Password Grant» выше): посылка «Code
Grant заработает, когда мы починим свой код» опровергнута замером. Текст ниже оставлен как запись
хода решения.

⚠ **Решение владельца 2026-09-06: остаёмся на OAuth (Code Grant).** Password Grant означает, что
приложение держит у себя ключ, которым клиент входит в свой банк, — при множестве клиентов это
неприемлемо. Записано здесь, чтобы к вопросу не возвращались: тип авторизации выбран, и менять его
в ответ на затруднение с продлением — не решение, а обход.

⚠ **Соблазн был мой, и он разобран как ошибка рассуждения.** Увидев `User session not alive`, я
предложил сменить тип авторизации — то есть менять постановку задачи вместо того, чтобы найти
дефект. Владелец вернул к вопросу «что не так мы шлём», и это было верно.

⚠ Ещё из документации, чего у нас нет: список scope шире `accounts` — `profile`, `read_documents`,
`create_documents`, `sign_documents`, `cards`, `read_currency`, `create_currency`, `read_employees`,
`create_employees`, `read_acquiring_partner`. Для выписки хватает `accounts`; остальное упомянуто,
чтобы при расширении не изобретать имена заново.

### Что документация говорит про сроки, и почему наш отказ ей противоречит

Дословно: «Время жизни access_token составляет 3600 сек, refresh_token — 36000 сек». Срок одинаков
у обоих типов авторизации.

⚠ **РАЗРЕШЕНО ответом банка (2026-09-07): расходится документация, а не наш запрос.** Прежний вывод
из этого абзаца — «наш запрос обязан был сработать» — неверен: по правилам банка он не мог сработать
никогда, потому что access к тому моменту был мёртв почти пять часов. Ни про сессию, ни про
обязанность обновляться чаще часа в документации по-прежнему нет ни слова, и это её дефект, а не
наш. Строку про 36000 с читать как «потолок сессии», см. блок «Официальный ответ банка».

⚠ **Осторожность из этого абзаца оправдалась дважды, и по-разному.** Наблюдение «пока шёл опрос,
подключение жило шестеро суток, а без опроса умирало» было названо корреляцией с изъяном: при опросе
мы не только обновляли токен, но и ходили в API за выпиской, и какое из двух действий держало грант
— из наблюдения не следовало.

Проверка (`P=alfa make refresh-now`, #664, затем лестница пауз #669) ответила: дело **во времени**.
Обмен проходит внутри часа на свежем подключении, к которому не было ни одного обращения в API, — то
есть поход за выпиской грант не держит, держит своевременное обновление.

⚠ А затем то же самое наблюдение стало **уликой в другую сторону** — и тут же было побито прямым
замером: потолок в 10 часов ИЗМЕРЕН и настоящий (см. блок выше). Значит шесть суток объясняются не
тем, что потолка нет, а тем, что его что-то отодвигало, — и единственный кандидат снова тот же самый,
про который эта оговорка и написана: обращения к API за выпиской. Круг замкнулся.

⚠ Полезно помнить: одно и то же наблюдение бывает слабым доказательством для одного утверждения,
сильным опровержением для второго и подсказкой для третьего. Ценность оговорки «какое из двух
действий держало грант» оказалась не в осторожности, а в том, что она СОХРАНИЛА развилку до момента,
когда её стало можно проверить.

⚠ Число 36000 **не опровергнуто, а переистолковано**: банк говорит, что это потолок СЕССИИ (сколько
её можно продлевать), а не срок жизни refresh-токена в отрыве от access. Отсюда прямое следствие для
[#660](https://github.com/bx-shef/client-bank-alfa-by/issues/660): `BANK_REFRESH_TTL_SEC['alfa-by']`
= 36000 моделирует не ту сущность, а порог «половина срока» из неё выводить нельзя вовсе — срок,
который надо успевать, равен ЧАСУ, а не десяти.

⚠ В песочнице вместо ключа API в запросе используется буквальное значение `API` (справочно, к
нашему пути не относится).
