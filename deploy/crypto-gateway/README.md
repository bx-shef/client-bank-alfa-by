# Крипто-шлюз до Приорбанка (BY-крипто TLS)

> Last reviewed: 2026-08-13

Образ, который позволяет нашему backend'у ходить в боевой Open Banking Приорбанка
([#460](https://github.com/bx-shef/client-bank-alfa-by/issues/460)). Внутрь — обычный HTTP,
наружу — TLS по СТБ 34.101.65 (BTLS) на **открытой** реализации
[bee2 + bee2evp](https://github.com/bcrypto/bee2evp) (Apache 2.0), без проприетарного СКЗИ
([#41](https://github.com/bx-shef/client-bank-alfa-by/issues/41),
[#457](https://github.com/bx-shef/client-bank-alfa-by/issues/457)).

```
worker/backend ──HTTP──▶ crypto-gw ──TLS 0xFF1x──▶ apibel.priorbank.by:9345
   (Node)        :1080    (nginx)     DHE-BIGN…       (боевой Приор)
```

## Зачем вообще шлюз

Боевой хост банка отвечает белорусским шифронабором. Node — и любой стоковый TLS-стек —
обрывается на `ServerHello` с `unknown cipher returned`. Патчить Node нечем: BTLS живёт в
libssl, а Node несёт свой OpenSSL. Отдельный процесс с пропатченным OpenSSL — единственный
способ, не переписывая приложение.

## Почему nginx, а не stunnel/socat

| | TCP-туннель | nginx |
|---|---|---|
| Заголовок `Host` | не переписывает — банк увидит `Host: crypto-gw:1080` | `proxy_set_header Host` |
| Переиспользование сессии | по соединению | `keepalive` — см. замер ниже |
| Проверка собеседника | `verifyChain` без `checkHost` принимает **любой** сертификат того же УЦ | `proxy_ssl_verify on` — цепочка И имя одной директивой |
| Ограничение путей/методов | нет | allowlist location'ов |

Замер keepalive — с контролем, два прогона отличаются **только** механикой keepalive
(«банк» — nginx с BTLS-сертификатом, потому что `openssl s_server -www` закрывает соединение
после каждого ответа и на нём keepalive не показать в принципе):

| | TLS-соединений у «банка» на 10 запросов |
|---|---|
| keepalive **включён** | **1** (все 10 запросов на одном соединении) |
| keepalive **выключен** | **10** (по одному запросу на соединение) |

⚠ Это доказывает, что **шлюз** переиспользует соединение. Будет ли его держать **банк** — зависит
от их балансировщика и проверяется только живым прогоном ([#461](https://github.com/bx-shef/client-bank-alfa-by/issues/461)).

## Живой прогон против боевого банка (2026-08-12)

Шлюз собран на прод-сервере и направлен на `apibel.priorbank.by:9345`. Запрос к токен-эндпоинту
заведомо неверными кредами (`client_id: probe`) вернул:

```
{"error_description":"A valid OAuth client could not be found for client_id: probe","error":"invalid_client"}
HTTP 401
2026-08-12T14:45:23+00:00 route=token method=POST status=401 upstream=401 bytes=120 rt=0.087 urt=0.088
```

**`upstream=401` — это и есть доказательство.** 401 пришёл ОТ БАНКА, а не выдуман nginx, значит
последовательно отработало всё: рукопожатие TLS по СТБ 34.101.65 (`DHE-BIGN…`), проверка цепочки
сертификата банка по корням ГосСУОК (`proxy_ssl_verify on`), сверка имени хоста, подстановка `Host`.
Тело ответа — от боевого сервера авторизации Приорбанка. Полный цикл 87 мс.

Контроль на том же хосте несколькими минутами раньше: `openssl s_client -connect
apibel.priorbank.by:9345` → `CONNECTED`, 90 байт `ServerHello`, `unknown cipher returned`,
`Cipher: 0000`. То есть разница именно в шлюзе, а не в сети.

Этим закрыта **кодовая часть [#41](https://github.com/bx-shef/client-bank-alfa-by/issues/41)**:
белорусский криптографический TLS работает на открытом bee2evp, без покупки проприетарного СКЗИ и
без ключа ГосСУОК (аутентификация банка односторонняя, наша — `private_key_jwt`).

⚠ Что этим НЕ закрыто:
- **DCR через шлюз не пройдёт** — `/open-banking-dcr/` не в allowlist
  ([#473](https://github.com/bx-shef/client-bank-alfa-by/issues/473)); боевая регистрация приложения
  требует либо расширения allowlist, либо отдельного пути.
- **Страницу авторизации открывает БРАУЗЕР администратора**, а не backend, и шлюз ему не помощник.
  Если боевой `GET /oauth2/authorize` живёт только на `:9345`, браузеру нужен свой BY-крипто TLS —
  это вопрос к банку, и от ответа зависит, работает ли продукт в проде вообще. Проксировать страницу
  входа в интернет-банк через свой домен — **не выход**: пользователь вводил бы банковские креды на
  чужой странице, это ровно форма фишинга.
- Держит ли банк keepalive-соединение (замер в таблице выше — про наш шлюз, не про их балансировщик).

## Быстрый старт

```bash
docker build -t crypto-gw deploy/crypto-gateway
docker run --rm -p 127.0.0.1:1080:1080 \
  -e GW_UPSTREAM_HOST=apibel.priorbank.by -e GW_UPSTREAM_PORT=9345 \
  -v "$PWD/deploy/crypto-gateway/ca:/etc/crypto-gw/ca:ro" \
  crypto-gw
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:1080/healthz   # 200
```

## Включение в проде

1. Положить на сервер корни. Репозитория там нет — только `docker-compose.prod.yml`, `Makefile` и
   `.env` (см. [`docs/DEPLOY.md`](../../docs/DEPLOY.md)), поэтому файлы качаем поштучно, тем же
   способом, что и сам compose-файл:

   ```bash
   mkdir -p ~/crypto-gw-ca && cd ~/crypto-gw-ca
   curl -fsSL -O https://raw.githubusercontent.com/bx-shef/client-bank-alfa-by/main/deploy/crypto-gateway/ca/gossuok-bundle.pem
   curl -fsSL -O https://raw.githubusercontent.com/bx-shef/client-bank-alfa-by/main/deploy/crypto-gateway/ca/bank-leaf-reference.pem
   ```
2. В `.env` задать `PRIOR_GW_CA_DIR` (путь из шага 1), при необходимости `PRIOR_GW_UPSTREAM_HOST`/
   `PRIOR_GW_UPSTREAM_PORT`.
3. В `docker-compose.prod.yml` раскомментировать: сервис `crypto-gw`, сеть `cryptonet` внизу и
   строки `- cryptonet` в `networks` у **backend и worker** (иначе шлюз поднимется, а обратиться
   к нему будет некому).
4. Расставить адреса. Их **три, и они независимы** — сколько из них переезжает на шлюз, зависит от
   того, какие API банк держит за BY-крипто TLS:

   | переменная | что по ней ходит | куда ставить |
   |---|---|---|
   | `PRIOR_OAUTH_TOKEN_URL` | токен (`Open-banking-authorize`) | на шлюз — этот API банк называет «сервером авторизации» |
   | `PRIOR_OAUTH_API_BASE` | согласия, счета, выписка (`Open-banking`) | на шлюз **только если** банк подтвердил, что и этот API за BY-крипто |
   | `PRIOR_OAUTH_AUTHORIZE_BASE` | страница входа | **всегда публичный адрес банка** |

   ⚠ Страницу открывает браузер администратора: внутренний адрес здесь убивает подключение **молча**
   — сервер такой запрос не делает и ошибки не видит никто. `PRIOR_OAUTH_AUDIENCE` не трогать: это
   claim внутри подписанного JWT, а не адрес.

   ⚠ **`TOKEN_URL` и `API_BASE` могут указывать на разные хосты — это законно.** Инструкция банка
   (стр. 4) и его ответ ограничивают требование `:9345` **API `Open-banking-authorize`**: «для
   взаимодействия с сервером авторизации». Про ресурсный `Open-banking` и про DCR такого нигде не
   сказано. Поэтому `envCheck` ругается не на сам факт разных адресов, а только на ПОЛОВИНЧАТЫЙ
   переезд (одна переменная внутрь сети, вторая наружу) — предупреждение о законной конфигурации
   приучало бы пролистывать предупреждения.

   Расщепление адресов — [#455](https://github.com/bx-shef/client-bank-alfa-by/issues/455), правила в
   `app/utils/bankGatewayUrl.ts`.
5. `make prod-redeploy` (или `docker compose -f docker-compose.prod.yml up -d`).

⚠ **Технический чек-лист выше — не разрешение включать.** Канал работает, но признаёт ли банк
несертифицированную реализацию — вопрос владельческий и на момент написания открыт. Включать в
проде только после письменного ответа банка: иначе через месяц кто-нибудь пройдёт этот список как
инструкцию и включит шлюз, не зная, что юридическая половина не закрыта.

## ⚠ Один поток всегда жжёт процессор

**Измерено, не предположение.** Процесс, который просто загрузил движок bee2evp и больше
ничего не делает:

```
  PID NLWP %CPU  COMMAND
20018    2 96.8  openssl          ← процесс целиком
      TID %CPU
    20018  1.1   ← основной поток простаивает
    20020  100   ← второй поток крутится
```

Причина в исходниках, а не в нашей сборке: `bee2evp_init()` зовёт `rngCreate()`, тот
безусловно опрашивает **все** источники энтропии, включая `timer` и `jitter`, а те поднимают
поток `tmCtrLoop` — буквально `while (_tm_ctr_loop) _tm_ctr_ticks++;`
(`bee2/src/core/rng/rng_timer.c`). Закрывается он только через `utilOnExit`, то есть **при
выходе процесса**. Пока шлюз живёт — поток крутится.

Что с этим сделано:

- **`nice -n 19`.** Измерено на одном общем ядре: приоритетный сосед забирает 97% CPU,
  шлюз довольствуется остатком. Крипто это не трогает вообще — только планировщик.
- **Крутится только master nginx.** Поток не переживает `fork()`, поэтому worker (тот, что
  реально обслуживает запросы) — `NLWP=1`, `0.0% CPU`. Проверено:

  ```
  25666  master  NLWP=2  99.7%  ni=19
  25669  worker  NLWP=1   0.0%  ni=19
  ```

- **Лимит в compose.** `cpus: '1.5'` — потолок, чтобы бесконечный цикл не мог утащить больше
  одного ядра плюс запас на работу.

⚠ **Не разворачивать на burstable-инстансах** (AWS t3/t4, аналоги с CPU-кредитами): непрерывный
100% одного ядра сожжёт кредиты за часы, и деградирует вся машина, а не только шлюз.

Чинить это должен upstream (остановить поток после посева либо сделать timer/jitter
опциональными). Патчить генератор случайных чисел в платёжном контуре ради процента CPU мы не
будем — цена ошибки несопоставима.

## ⚠ Граница доверия

Шлюз **никого не аутентифицирует**. Кто дотянулся до порта — тот ходит в банк. Поэтому:

- **никаких `ports:` наружу** — только внутренняя сеть compose (`cryptonet`);
- разрешены **только используемые пути и методы**, всё остальное отдаётся 404/403 самим
  шлюзом и до банка не доезжает:

  | запрос | ответ |
  |---|---|
  | `POST /open-banking-authorize/v1.0/oauth2/token` | проксируется |
  | `GET`/`POST /open-banking/v1.0/…` | проксируется |
  | `GET /open-banking-authorize/v1.0/oauth2/token` | `403` |
  | `DELETE /open-banking/v1.0/…` | `403` |
  | `/`, `/admin`, что угодно ещё | `404` |

  (это фактический вывод прогона, а не намерение);
- сам по себе доступ к шлюзу ничего не даёт: **каждый вызов банка требует Bearer-токена**,
  которого у постороннего нет.

Общий shared-secret между приложением и шлюзом — осознанно **не** в этой версии: он требует
правок транспортного слоя (`bankFetch.ts`), а внутренняя сеть + allowlist + Bearer закрывают
тот же класс. Кандидат на [#461](https://github.com/bx-shef/client-bank-alfa-by/issues/461),
если шлюз когда-нибудь окажется на общей сети.

## Что попадает в логи

Access-лог написан **без пути**: `route=ob method=GET status=200 upstream=200 bytes=… rt=… urt=…`.
Причина конкретная — в пути едет номер счёта (`/open-banking/v1.0/accounts/<IBAN>/statements`).

Error-лог nginx формат менять не умеет и на уровне `[error]` печатает строку запроса целиком
(проверено). Поэтому по умолчанию `GW_ERROR_LOG_LEVEL=crit`: диагностика отказов остаётся в
access-логе (`status=502`), а идентификатор счёта в поток не уходит. На живой прогон уровень
поднимают до `info` и возвращают обратно. Модель хранения финансовых ПДн —
[`docs/PRIVACY.md`](../../docs/PRIVACY.md).

## Что проверяется на сборке и на старте

Три гейта в `Dockerfile` + два в `entrypoint.sh`. Все они есть потому, что без них поломка
всплывает на первом обращении к банку — самое дорогое место.

| Где | Проверка | Что ловит |
|---|---|---|
| build | `openssl engine -t bee2evp` + наличие `DHE-BIGN…`/`DHT-BIGN…` | патч BTLS не применился |
| build | `ldd nginx \| grep /opt/btls/lib` | nginx собрался против **системного** OpenSSL |
| build | те же шифры **повторно, в финальном образе** | в рантайм скопировали не тот набор файлов (гейты 1–2 смотрели на полное дерево сборки) |
| build | `openssl verify -no_check_time -CAfile bundle bank-leaf-reference.pem` | **bundle без промежуточного**: `x509 -subject` и `nginx -t` его проходят, а `verify` даёт `error 20 unable to get local issuer certificate` — воспроизведено |
| start | bundle читается и содержит ≥1 сертификат | том не смонтирован / пустой файл — **фатально** |
| start | bundle подтверждает эталонный сертификат банка | не хватает промежуточного — **громко, но не фатально**: ровно так же выглядит легальная ротация корней ([#462](https://github.com/bx-shef/client-bank-alfa-by/issues/462)), и падать в этот момент значит устроить простой самим себе |
| start | `nginx -t` над отрендеренным конфигом | опечатка в шаблоне, незаполненная переменная. ⚠ Резолвит хост банка, поэтому DNS-сбой в момент старта не даст контейнеру подняться — с `restart: unless-stopped` это restart-loop до восстановления DNS |
| CI | `docker run` + `/healthz` + проверка allowlist и uid | сборка образа **не** доказывает, что контейнер стартует: рендер конфига, гейты, переход на непривилегированного пользователя и healthcheck выполняются только при запуске |
| unit | `tests/cryptoGatewayConfig.test.ts` | рассинхрон allowlist `envsubst` с плейсхолдерами шаблона (`envsubst` молча оставит `${GW_…}` текстом), путь в формате лога, отключённая проверка TLS, порядок шифров, расширение allowlist маршрутов |

`healthcheck.sh` спрашивает **свой** `/healthz` и намеренно не трогает ни DNS, ни банк: иначе
авария на их стороне превращалась бы у нас в restart-loop.

## Пины и воспроизводимость

| Что | Значение | Кто следит |
|---|---|---|
| база | `debian:12-slim@sha256:abd67ffc…` | Dependabot (запись `/deploy/crypto-gateway`) |
| bee2evp | коммит `2ae3c71e8b24b6904367850e5963933236a1539f` (он же пинит `bee2` как submodule) | **вручную** |
| OpenSSL | `openssl-3.5.6` — ветка **LTS до 2030** | **вручную** |
| nginx | `1.28.0`, sha256 тарбола сверяется на сборке | **вручную** |

⚠ **Три пина из четырёх Dependabot не видит** и увидеть не может: он читает строки `FROM`, а
nginx/OpenSSL/bee2evp здесь — сборочные `ARG`. Это ручная работа, и её надо делать: регламент —
[#470](https://github.com/bx-shef/client-bank-alfa-by/issues/470). Зеркало исходников на случай
исчезновения апстрима — [#471](https://github.com/bx-shef/client-bank-alfa-by/issues/471).

⚠ **Не откатывать OpenSSL на 3.3.1**, даже если у bee2evp больше CI-прогонов на нём: ветка 3.3
вышла из поддержки 09.04.2026 и несёт CVE-2024-6119 — падение в **проверке имени в сертификате
собеседника**, то есть ровно в том, что этот образ делает при каждом запросе к банку
(`proxy_ssl_verify on` + `proxy_ssl_name`). На 3.5.6 проверено: движок доступен, 8 наборов BTLS,
цепочка ГосСУОК проходит.

Сертификаты (sha256 самих сертификатов, не файлов):

| Сертификат | Отпечаток |
|---|---|
| РУЦ ГосСУОК (промежуточный) | `46:BC:10:37:DC:5B:A3:F0:9D:10:DA:74:C3:2B:2E:C9:C7:BD:53:B5:11:A5:CE:BF:9A:ED:B5:09:CE:DA:D9:04` |
| КУЦ ГосСУОК (корень) | `C5:9F:45:9F:66:BA:58:98:62:5D:05:DF:D1:4B:D3:C3:43:59:A0:99:F5:A1:8C:2E:44:69:41:AD:74:DC:8C:5B` |
| `apibel.priorbank.by` (эталон) | `59:5E:01:C3:6B:83:9D:43:30:34:81:2D:CE:7F:F1:25:DA:CE:09:88:1E:D7:E5:1B:30:8C:CB:66:0A:D3:DF:36` |

⚠ **Баг сборочного скрипта bee2evp, обойдён в `Dockerfile`.** `scripts/source.sh` выбирает тип
сборки через `[[ "$build_type" -eq "Debug" ]]` — `-eq` это **числовое** сравнение, bash приводит
обе строки к нулю, условие всегда истинно, и OpenSSL **всегда** конфигурируется с `--debug`
(`-O0`, без оптимизации; видно в логе сборки). Для шлюза, вся работа которого — дорогое
рукопожатие BIGN, это не косметика. Правим оператор сравнения, крипто не трогаем.

## Чего пока нет

- **Активного АЛЕРТА «шлюз лёг».** Видимость появилась: `GET /api/ready` отдаёт `checks.cryptoGw`,
  а в `docs/OPERATIONS.md` есть раздел с таблицей значений. Но это проба «по запросу» — её надо
  пойти и посмотреть. Косвенно авария всплывёт сама: джобы `bank-fetch-prior` начнут падать, а
  классификатор тревог считает сетевую ошибку «нашим сбоем», так что Telegram-канал пробьёт порог —
  только сообщение будет generic, без подсказки «проверь контейнер».
- **Общего секрета между приложением и шлюзом.** Шлюз никого не аутентифицирует, см. «Граница
  доверия». Требует правок транспортного слоя — тоже #461.
- **Калибровки таймаутов и поведения под конкурентностью.** `15s`/`60s` и `GW_KEEPALIVE=4`
  выбраны под `QUEUE_PRIOR_CONCURRENCY=4`, но нагрузочно не проверялись.
